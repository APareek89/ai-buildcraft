Why RAG exists

Start here — the problem before the machinery.

⏱ ~1 min read

A language model only knows what it saw in training. Ask it about your internal docs and it will often answer fluently and wrongly. RAG exists to ground answers in retrieved, real text.

The confidently-wrong problem

In plain wordsAn ungrounded LLM is like a smart intern who never says 'I don't know' — they'll answer your billing question with total confidence, inventing the policy.

A language model predicts likely text. Ask it something outside its training and it still produces a fluent answer — that is a . fixes this by fetching real passages from your documents and instructing the model to answer only from them.

Before reading on, predict: if your help-center changes a refund window from 14 to 30 days, why might a plain (non-RAG) chatbot still say 14?

A customer asks: 'Can I return a sale item?'

  • Without RAG: the model guesses from generic e-commerce norms — sometimes right, sometimes inventing your policy.
  • With RAG: it retrieves your actual 'Sale & clearance returns' article and answers from that exact wording, with a citation.

How this breaks: RAG is only as fresh as its index. If you forget to re-index after a policy change, retrieval returns the OLD passage and the model grounds confidently in stale truth. Re-indexing on publish is part of the system, not an afterthought.

The RAG pipeline

Now the moving parts that turn docs into grounded answers.

⏱ ~1 min read

RAG is a pipeline: ingest documents, split them into chunks, embed each chunk into a vector, store the vectors, then at query time retrieve the closest chunks and generate an answer from them.

Chunking & embeddings

The indexing half — make meaning searchable.

⏱ ~1 min read

Retrieval quality is mostly decided here. Chunk too big and you retrieve noise; too small and you lose context. Embeddings place chunks in a space where 'near' means 'similar in meaning'.

  • Explain what an embedding represents

Meaning as coordinates

In plain wordsAn embedding is like placing every passage on a map where related ideas are neighbors — 'refund' sits near 'return', far from 'shipping speed'.

An is a list of numbers positioning a chunk by meaning. then ranks chunks by distance to the question's embedding, so it matches on meaning, not just keywords.

Nearest in meaning

Pick a query — its three nearest passages light up. Notice meaning, not exact words, drives closeness.

index.py · python
from my_rag import load_docs, chunk, embed, VectorStore

docs = load_docs("help_center/")
chunks = chunk(docs, size=400, overlap=50)

store = VectorStore(dim=1536)
for c in chunks:
    store.add(vector=embed(c.text), text=c.text, meta=c.meta)

store.save("help.index")
Syntax breakdown
chunk(docs, size=400, overlap=50)
Splits documents into ~400-token passages, repeating 50 tokens between neighbors so facts on a boundary aren't lost.
embed(c.text)
Turns a chunk's text into its meaning-vector.
store.add(vector=..., text=..., meta=...)
Saves the vector alongside the original text and metadata so retrieval can return readable, citable passages.
Predict: What breaks if you set size=4000 with no overlap?
Chunks get huge: each retrieved passage carries lots of irrelevant text (lower precision), and a fact split across a boundary can be missed entirely because there is no overlap to capture it.

Retrieve & generate

The query half — answer from what you found.

⏱ ~1 min read

At query time you embed the question, pull the top-k nearest chunks, and assemble a prompt that tells the model to answer only from those passages. Get this contract right and grounding holds.

The grounding contract

Retrieve the nearest chunks, paste them into the prompt, and instruct: 'Answer only from the context; if it's not there, say you don't know.' Keep k small enough to fit the with room for the answer.

answer.py · python
store = VectorStore.load("help.index")

def answer(question):
    hits = store.search(embed(question), k=4)
    context = "\n---\n".join(h.text for h in hits)
    prompt = (
        "Answer ONLY from the context. If absent, say you don't know.\n\n"
        f"Context:\n{context}\n\nQuestion: {question}"
    )
    return llm(prompt), [h.meta for h in hits]
Predict: A user asks something your docs don't cover. With this prompt, what should happen?
Retrieval still returns the 4 closest chunks, but none contain the answer — so the instruction 'if absent, say you don't know' should make the model decline instead of inventing one. That refusal is the system working, not failing.
Use when
Top-k retrieval already surfaces the right passage in the first few hits.
Avoid when
The right chunk often ranks 8th–15th — then add a re-ranker to reorder a larger candidate set.
Rule of thumb
Start simple: k=4, no re-ranking. Add re-ranking only when you measure recall problems.

Decision checklist

  • Memory vs retrieval: is this question grounded in docs?
  • Chunk size & overlap chosen for precision vs context
  • k and re-ranking decided by measured recall
  • Vector store matched to your constraints
