Agent Frameworks Crash Course

Seven frameworks, one sitting. Every section is anchored to what you already know: each framework's concepts are translated to their LangChain / LangGraph equivalents, then shown in real code with use cases, when-to-choose guidance, and gotchas. Read the Overview, then jump around.

Assumed known: LangChain + LangGraph (StateGraph, nodes, edges, checkpointers, tools)

The landscape in one idea

Every agent framework answers the same question — “who decides what happens next?” — differently. LangGraph's answer is: you do, with an explicit graph. The other frameworks move that decision somewhere else.

3Also on the radar (know these exist)

OpenAI Agents SDK

prod-readypython + TS

Minimal, opinionated successor to Swarm: Agents + Handoffs + Guardrails + Sessions, with tracing built in. ~4 primitives total, by design.

vs LangGraph: delete your graph. Routing happens through handoffs — a specialist agent is exposed to the LLM as something it can “transfer” to, so the model is your conditional edge. You trade explicit control for radically less wiring.

2Code — support triage with handoffs + a guardrail

from pydantic import BaseModel
from agents import (Agent, Runner, function_tool, input_guardrail,
                    GuardrailFunctionOutput, SQLiteSession)

@function_tool
def order_status(order_id: str) -> str:
    """Look up shipping status for an order."""
    return f"Order {order_id}: shipped, arriving Thursday"

class RefundCheck(BaseModel):
    is_abusive: bool
    reasoning: str

guard_agent = Agent(name="Abuse check", instructions="Flag abusive refund demands.",
                    output_type=RefundCheck)

@input_guardrail
async def refund_guard(ctx, agent, user_input):
    result = await Runner.run(guard_agent, user_input)
    return GuardrailFunctionOutput(
        output_info=result.final_output,
        tripwire_triggered=result.final_output.is_abusive)

refunds = Agent(name="Refunds agent",
                instructions="Process refund requests. Max auto-refund $100.",
                input_guardrails=[refund_guard])

shipping = Agent(name="Shipping agent",
                 instructions="Answer delivery questions.", tools=[order_status])

triage = Agent(name="Triage",
               instructions="Route to the right specialist. Never answer yourself.",
               handoffs=[refunds, shipping])   # <- the LLM sees these as transfer options

session = SQLiteSession("user_42")             # memory across turns, zero plumbing
result = Runner.run_sync(triage, "Where is order 8121?", session=session)
print(result.final_output)                     # ran: triage -> handoff -> shipping -> tool

The loop, tool schemas, handoff mechanics, history injection and tracing are all handled by Runner. In LangGraph this file would be ~3× longer.

3Use cases that fit it

Support / triage systems

Classic triage-agent → specialist handoffs; guardrails for policy; sessions per customer.

Deep-research clones

Planner agent hands off to search agents, then a writer agent; agents-as-tools for parallel fan-out.

Voice agents

Same Agent objects plug into the Realtime API for speech-to-speech pipelines.

4Decision

CHOOSE IT WHEN

  • You're on the OpenAI stack and want the shortest path to a multi-agent prod app
  • Routing decisions are genuinely judgment calls (LLM-routed is fine)
  • You want guardrails + tracing without extra vendors

SKIP IT WHEN

  • You need deterministic, auditable control flow → LangGraph / workflows
  • Multi-provider portability is a hard requirement (it works via LiteLLM, but it's OpenAI-first)
  • Heavy custom state beyond chat history

GOTCHAS

  • Handoffs are model decisions — test them; a vague triage prompt = nondeterministic routing.
  • Traces upload to the OpenAI platform by default — disable/redirect for sensitive data.
  • Sessions append everything; long threads need pruning or you pay in tokens.

CrewAI

fast to demopython

Role-playing teams: declare who (Agents with role/goal/backstory) and what (Tasks), pick a Process, call kickoff(). Independent of LangChain — its own lightweight core.

vs LangGraph: you stop writing control flow entirely. A Crew is a cast + a to-do list; the framework sequences it. When you miss determinism, CrewAI's newer Flows give you back an event-driven graph — think “LangGraph-lite with @listen decorators.”

1Primitives → LangGraph translation

CrewAIWhat it is≈ in LangGraph
Agent(role, goal, backstory)Persona-prompted worker; can delegateNode + system prompt (persona auto-generated)
Task(description, expected_output)Unit of work assigned to an agentA node's input contract, written in prose
Crew(process=…)sequential = pipeline; hierarchical = manager LLM delegatesLinear graph / supervisor pattern
Task(context=[…])Pipe one task's output into anotherState keys passed between nodes
Flow + @start/@listenEvent-driven deterministic orchestration w/ typed stateStateGraph, honestly

2Code — two-agent research crew

from crewai import Agent, Task, Crew, Process
from crewai_tools import SerperDevTool

researcher = Agent(
    role="Market Research Analyst",
    goal="Find recent, credible facts about {topic}",
    backstory="Ex-consultant. Obsessive about primary sources.",
    tools=[SerperDevTool()],          # web search
    verbose=True)

writer = Agent(
    role="Briefing Writer",
    goal="Turn research into a crisp exec brief",
    backstory="Writes for CEOs. Allergic to fluff.")

research_task = Task(
    description="Research {topic}: market size, 3 key players, 2 risks.",
    expected_output="Bulleted findings with source URLs",
    agent=researcher)

brief_task = Task(
    description="Write a 300-word brief from the research.",
    expected_output="Markdown brief: TL;DR, landscape, risks",
    agent=writer,
    context=[research_task])          # <- receives researcher's output

crew = Crew(agents=[researcher, writer],
            tasks=[research_task, brief_task],
            process=Process.sequential)

result = crew.kickoff(inputs={"topic": "AI video generation market"})
print(result.raw)

And when you need determinism, a Flow: @start() methods fire first, @listen(step) methods fire on completion, self.state is typed shared state. Crews can be embedded inside Flow steps — that combination (Flow skeleton, Crew muscles) is the recommended production shape.

3Use cases that fit it

Content pipelines

Research → outline → draft → edit. The canonical Crew; excellent output-per-hour-of-dev.

Lead enrichment / GTM ops

Scrape → qualify → personalize outreach, one task each.

Stakeholder demos

Nothing produces a convincing multi-agent demo faster — great for PM prototyping.

4Decision

CHOOSE IT WHEN

  • The job decomposes into role-shaped sequential work (pipelines)
  • Speed-to-working-demo matters more than fine control
  • Team includes non-engineers who can read role/goal/task prose

SKIP IT WHEN

  • You need tight control of every LLM call → the persona layer adds hidden prompt text
  • Complex branching/looping state → you'll rebuild LangGraph inside Flows anyway
  • Token budget is tight (chatty by default)

GOTCHAS

  • Role/goal/backstory get compiled into prompts you don't fully see — inspect with verbose=True before blaming the model.
  • Process.hierarchical adds a manager LLM that can mis-delegate; give it an explicit manager_llm and tight task descriptions.
  • expected_output is load-bearing — vague ones are the #1 cause of garbage results.

AutoGen → Microsoft Agent Framework

research → enterprisepython + .NET

AutoGen pioneered conversation as orchestration: agents talk in a group chat until a termination condition fires. Microsoft has now folded AutoGen + Semantic Kernel into one product — the Microsoft Agent Framework (MAF): AutoGen's agents + graph-based workflows + enterprise plumbing (Azure identity, observability, threads).

vs LangGraph: AutoGen replaces your graph with a conversation policy — “round robin until someone says APPROVE” is the whole orchestration. MAF's workflow layer, meanwhile, is a direct LangGraph competitor: typed data flowing through explicit executor nodes with checkpointing and human-in-the-loop.

1Primitives → LangGraph translation

AssistantAgentLLM agent with system message + toolsNode + prompt + bound tools
RoundRobinGroupChatAgents take turns in fixed orderA cyclic graph with a static router
SelectorGroupChatAn LLM picks who speaks nextSupervisor pattern
TextMentionTerminationStop when a token like APPROVE appearsConditional edge to END
MAF WorkflowBuilderTyped graph of executors, fan-out/fan-in, checkpointsStateGraph (closest cousin in this whole document)

2Code — writer–critic reflection loop (AutoGen AgentChat)

import asyncio
from autogen_agentchat.agents import AssistantAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_agentchat.conditions import TextMentionTermination
from autogen_ext.models.openai import OpenAIChatCompletionClient

model = OpenAIChatCompletionClient(model="gpt-5")

writer = AssistantAgent("writer", model_client=model,
    system_message="Write marketing copy. Revise when the critic gives feedback.")

critic = AssistantAgent("critic", model_client=model,
    system_message="Critique for clarity and punch. Reply APPROVE when it's good.")

# orchestration = a conversation policy, not a graph
team = RoundRobinGroupChat([writer, critic],
    termination_condition=TextMentionTermination("APPROVE"))

async def main():
    result = await team.run(task="Landing-page hero copy for an AI photo editor")
    print(result.messages[-2].content)   # last writer draft before APPROVE

asyncio.run(main())

The same shape in MAF: ChatAgents created from an AzureOpenAIChatClient, composed either into group chats or into an explicit WorkflowBuilder graph when you need LangGraph-style determinism. If you're starting fresh on Microsoft's stack, start with MAF, not classic AutoGen.

3Use cases that fit it

Reflection loops

Writer–critic, coder–reviewer, analyst–skeptic. Conversation is the natural shape for iterative refinement.

Research prototyping

Emergent multi-agent behavior studies; AutoGen remains a favorite in papers.

Azure-native enterprise agents

MAF + Azure AI Foundry: identity, compliance, observability out of the box; .NET support your bank will love.

4Decision

CHOOSE IT WHEN

  • The task is naturally iterative debate/refinement between roles
  • You're a Microsoft/Azure/.NET shop (MAF is the obvious default there)
  • You want one framework spanning simple chat agents → typed workflows

SKIP IT WHEN

  • You need tight cost control — group chats burn tokens fast
  • Non-Azure prod stack and you already have LangGraph muscle
  • You dislike platform churn (AutoGen 0.2 → 0.4 → MAF migrations were real)

GOTCHAS

  • API history matters when googling: 0.2-era (UserProxyAgent, initiate_chat) vs 0.4+ async API vs MAF — check which docs you're reading. AG2 is a community fork of the old API.
  • Always set termination conditions; two polite LLMs will thank each other forever.
  • Group-chat transcripts are your only “state” in classic AutoGen — export/persist them deliberately.

PydanticAI

production DXpython

From the Pydantic team: “FastAPI feeling, but for agents.” One typed Agent class, validated structured outputs with automatic retry, dependency injection, model-agnostic, Logfire observability.

vs LangGraph: LangChain gives you with_structured_output; PydanticAI makes the validated output the contract of the whole agent — if the model returns junk, the framework re-prompts with the validation error until it type-checks. Deps replace LangGraph's config/state threading with real dependency injection you can swap in tests.

1Primitives → LangGraph translation

PydanticAIWhat it is≈ in LangGraph
Agent("provider:model", …)Typed agent, generic over deps + outputCompiled graph (single-node loop)
output_type=ModelValidated result schema, auto-retriedwith_structured_output + retry loop you'd write
deps_type + RunContextInjected dependencies (db, http, user)config["configurable"] / state, but type-safe
@agent.toolTool receiving ctx.deps@tool, minus manual wiring of context
message_history=…You own persistence explicitlyCheckpointer (but bring-your-own storage)

2Code — bank support agent with typed risk output

from dataclasses import dataclass
from pydantic import BaseModel, Field
from pydantic_ai import Agent, RunContext

@dataclass
class Deps:                      # injected, swappable in tests
    customer_id: int
    db: "DatabaseConn"

class SupportOutput(BaseModel):  # the agent's CONTRACT
    advice: str = Field(description="Plain-English advice for the customer")
    block_card: bool
    risk: int = Field(ge=0, le=10)

agent = Agent(
    "anthropic:claude-sonnet-5",
    deps_type=Deps,
    output_type=SupportOutput,
    instructions="You are first-line support at a bank.")

@agent.tool
async def customer_balance(ctx: RunContext[Deps]) -> float:
    """Current account balance for this customer."""
    return await ctx.deps.db.balance(ctx.deps.customer_id)

deps = Deps(customer_id=123, db=DatabaseConn())
result = await agent.run("I just lost my card!", deps=deps)

result.output              # SupportOutput — GUARANTEED valid or the run failed
if result.output.block_card:
    freeze_card(deps.customer_id)      # downstream code trusts the types

Invalid model output → PydanticAI feeds the validation error back and retries automatically. Your business logic never sees malformed data.

3Use cases that fit it

Agents inside real backends

Anything where agent output feeds code, not humans: risk scoring, routing decisions, CRM updates.

Extraction APIs

Documents/emails → validated schemas, deployed like any FastAPI endpoint.

Test-heavy teams

Deps injection + TestModel = agents you can actually unit-test in CI without API calls.

4Decision

CHOOSE IT WHEN

  • Structured, validated output is the product
  • You want Python-engineer DX: types, DI, testability, mypy passing
  • Model-agnostic single agents with tools (most real apps!)

SKIP IT WHEN

  • You need rich multi-agent orchestration today (pydantic-graph is young)
  • You lean on LangChain's huge integration catalog (loaders, retrievers, stores)

GOTCHAS

  • API renamed as it matured: result_type → output_type, result.data → result.output — old blog posts will bite you.
  • Conversation memory is manual: pass message_history yourself; there's no checkpointer magic.
  • Strict schemas + weak models = retry loops; keep output models as flat as you can.

smolagents

~1k LOC corepython · Hugging Face

One radical idea: instead of emitting JSON tool calls, the agent writes Python code as its action, which is executed and observed. Fewer round-trips, natural composition (loops, variables, chaining tools in one step). First-class support for open models.

vs LangGraph: a LangGraph ToolNode executes one declared tool per step. A CodeAgent step might write a for-loop that calls three tools, aggregates with pandas, and returns a number — one model call instead of six. The tradeoff: you are now executing model-written code, so sandboxing becomes a real concern.

smolagentsWhat it is≈ in LangGraph

ToolCallingAgentClassic JSON tool-calling variantStandard tool-calling agent
@tool functionsDocstring + type hints become the schema@tool (nearly identical)
InferenceClientModel / LiteLLMModelModel adapters (HF Hub, any provider, local)ChatModel classes
managed_agents=[…]Manager agent can call sub-agents like functionsSupervisor + subgraphs

2Code — data-crunching agent

from smolagents import CodeAgent, InferenceClientModel, WebSearchTool, tool

@tool
def shipping_cost(weight_kg: float, zone: str) -> float:
    """Compute shipping cost for a parcel.
    Args:
        weight_kg: parcel weight in kg
        zone: 'domestic' or 'international'
    """
    return weight_kg * (4.0 if zone == "domestic" else 11.5)

model = InferenceClientModel()          # default open model on HF; or LiteLLMModel(...)
agent = CodeAgent(
    tools=[WebSearchTool(), shipping_cost],
    model=model,
    additional_authorized_imports=["pandas"])   # allowlist, not open season

agent.run("Price out shipping 3 parcels (2kg domestic, 5kg intl, 1.2kg domestic) "
          "and give me the total and the average cost per kg.")

# The agent's ACTION will literally be generated code like:
#   costs = [shipping_cost(2, "domestic"), shipping_cost(5, "international"), ...]
#   total = sum(costs); print(total, total / 8.2)
# ...executed, observed, then answered. One step, three tool calls.

For untrusted workloads, swap the local executor for a sandbox: CodeAgent(..., executor_type="e2b") (or Docker/WASM) — treat this as mandatory in production.

3Use cases that fit it

Data analysis agents

Computation-shaped tasks (aggregation, math, transforms) where JSON tool-calling is painfully chatty.

Open-model deployments

Best-in-class ergonomics for Qwen/Llama-class models, local or HF Inference.

Web research on a budget

The GAIA-benchmark-style browse + compute combo, in ~20 lines.

4Decision

CHOOSE IT WHEN

  • Tasks are computational and multi-tool per step (code-as-action shines)
  • You want open/local models without fighting your framework
  • You value a core small enough to read in an afternoon

SKIP IT WHEN

  • Long multi-turn conversations with complex memory
  • Compliance forbids executing generated code, even sandboxed
  • You need rich structured outputs and typed contracts → PydanticAI

GOTCHAS

  • Tool docstrings ARE the schema — missing an Args: section literally raises an error.
  • Local executor is restricted-but-not-a-sandbox; use E2B/Docker for anything internet-facing.
  • Weaker models sometimes write broken code and burn steps retrying; cap max_steps.

LlamaIndex (Agents + Workflows)

RAG-nativepython + TS

The data-framework-turned-agent-framework. Two layers you care about: agents (FunctionAgent/ReActAgent) whose superpower is treating query engines over your documents as tools, and Workflows — event-driven orchestration used across its ecosystem.

vs LangGraph: Workflows invert the graph. In LangGraph you wire edges between nodes; in a Workflow each @step declares which Event types it consumes and emits, and the runtime wires the DAG for you. Same power (branches, loops, parallelism, checkpoints) — different ergonomics: you think in events, not edges.

1Primitives → LangGraph translation

LlamaIndexWhat it is≈ in LangGraph

QueryEngineToolAn index/RAG pipeline exposed as a toolA retriever tool, but industrial-grade
Workflow + @stepSteps consuming/emitting typed EventsNodes + edges (edges inferred from event types)
ContextSerializable shared state across steps/runsState + checkpointer
AgentWorkflowMulti-agent system w/ handoffs over shared stateSupervisor/swarm patterns

2Code — agentic RAG over contracts

from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.agent.workflow import FunctionAgent
from llama_index.llms.anthropic import Anthropic

# 1. Classic LlamaIndex: docs -> index -> query engine (3 lines)
docs = SimpleDirectoryReader("./contracts").load_data()
index = VectorStoreIndex.from_documents(docs)
qe = index.as_query_engine(similarity_top_k=5)

# 2. Expose RAG as a tool the agent can decide to use
async def search_contracts(query: str) -> str:
    """Answer questions from the contract corpus."""
    return str(await qe.aquery(query))

async def flag_for_legal(contract: str, reason: str) -> str:
    """Escalate a contract to the legal team."""
    return f"Flagged {contract}: {reason}"

agent = FunctionAgent(
    tools=[search_contracts, flag_for_legal],
    llm=Anthropic(model="claude-sonnet-5"),
    system_prompt="Contract analyst. Search before answering; escalate real risks.")

resp = await agent.run("Which vendor contracts auto-renew in the next 60 days, "
                       "and do any have non-standard liability caps?")
print(resp)   # multi-hop: search -> reason -> search -> maybe flag -> answer

Custom orchestration is the same mental model with events: define class ChunksRetrieved(Event), write @step methods that take StartEvent → emit ChunksRetrieved → emit StopEvent; the runtime connects steps by matching event types.

Document-heavy agents

Contracts, filings, research corpora — anywhere “the tool” is really “my documents.”

Existing RAG → agent that plans queries, retries retrieval, cross-checks sources.

Ingestion + extraction pipelines

4Decision

CHOOSE IT WHEN

  • Retrieval quality over private data is the core problem
  • You want one framework covering ingestion → index → agent
  • Event-driven style fits your team (or you stream a lot — events map to UI updates beautifully)

SKIP IT WHEN

  • No documents in sight — plain tool agents are simpler elsewhere
  • You want ONE obvious way to do things (LlamaIndex often has three)

GOTCHAS

  • Old tutorials use deprecated OpenAIAgent/AgentRunner; current path is FunctionAgent/AgentWorkflow on Workflows.
  • Pass and persist Context explicitly for multi-turn memory — agents are stateless by default.
  • Big integration surface = version churn; pin versions and read release notes on upgrade.

Claude Agent SDK

harness includedpython + TS

Anthropic's inversion of the framework idea: you don't build the agent loop — you get Claude Code's production harness as a library. Context gathering, file/bash/web tools, permissions, sessions, compaction, subagents, MCP: all shipped. You configure and extend it.

vs LangGraph: LangGraph hands you a loom; this hands you the finished loop (gather context → act → verify → repeat) with batteries. You give up orchestration control and provider choice; you gain a hardened harness that already solved context management, tool safety and memory. Closer to “programmable Claude Code” than to a framework.

2Code — an ops agent with a custom tool

import asyncio
from claude_agent_sdk import (query, ClaudeAgentOptions, tool,
                              create_sdk_mcp_server)

@tool("get_alerts", "Fetch active pager alerts", {"service": str})
async def get_alerts(args):
    alerts = await pagerduty.active(args["service"])
    return {"content": [{"type": "text", "text": str(alerts)}]}

ops_server = create_sdk_mcp_server(name="ops", tools=[get_alerts])

options = ClaudeAgentOptions(
    system_prompt="You are an SRE. Diagnose, propose a fix, apply it if safe.",
    mcp_servers={"ops": ops_server},
    allowed_tools=["Read", "Grep", "Bash", "Edit",       # built-ins, pre-hardened
                   "mcp__ops__get_alerts"],
    permission_mode="acceptEdits",     # auto-accept file edits; gate the rest
    cwd="/srv/payments-service")

async def main():
    async for msg in query(
        prompt="payments-service is alerting: high 5xx. Investigate and fix.",
        options=options):
        print(msg)          # streamed thinking, tool calls, diffs, final result

asyncio.run(main())
# The SDK handled: context gathering, tool schemas, permission gating,
# retries, session state, context compaction. You wrote ~30 lines.

Subagents are one more option away (agents={"reviewer": AgentDefinition(...)}); persistent memory = a CLAUDE.md in the working directory.

3Use cases that fit it

Coding & repo agents

Code review bots, migration runners, test fixers — the harness was literally built for this.

SRE / ops automation

Agents that read logs, run commands, and edit configs with permission gates and audit hooks.

“Computer-work” agents

Anything shaped like “operate on files + shell + APIs in a loop” — research, data wrangling, CI chores.

4Decision

CHOOSE IT WHEN

  • The agent acts on real environments (files, shells, repos, tools)
  • You want production hardening (permissions, sandboxing, compaction) for free
  • You're all-in on Claude anyway

SKIP IT WHEN

  • Multi-provider flexibility is required (Anthropic-only)
  • You need lightweight embedded inference (it spawns the Claude Code runtime)
  • Fine-grained custom orchestration is the point → LangGraph

GOTCHAS

  • Renamed from claude-code-sdk → claude-agent-sdk; old imports and defaults differ (notably: the SDK no longer inherits Claude Code's system prompt unless you ask).
  • Costs scale with the harness's thoroughness — scope allowed_tools and CWD tightly.
  • Design permission modes early; retrofitting bypassPermissions habits is how incidents happen.

Choosing without a bake-off

Frameworks are ~20% of an agent product's success (evals, data and UX are the rest) — so pick fast, pick boring, and move on. Use the matrix for constraints, the scenarios for instinct.

3Check yourself (click to reveal)

1. In the OpenAI Agents SDK, what plays the role of LangGraph's conditional edges — and what's the catch?
Handoffs. The LLM decides when to transfer control to another agent, so routing is a model judgment call — flexible, but nondeterministic; you test prompts instead of asserting edges.
2. Your CrewAI crew gives vague results. What's the first thing to fix?
expected_output on each Task. It's the load-bearing prompt. Second: run verbose=True to see the hidden persona prompt compiled from role/goal/backstory.
3. What is orchestration in classic AutoGen, and what must you never forget to set?
The conversation itself (group chat policy like round-robin or LLM-selected speaker). Always set a termination condition — otherwise agents loop politely forever, at your expense.
4. What does PydanticAI do when the model's answer fails schema validation?
Feeds the validation error back to the model and retries automatically until it validates (or retries run out). Downstream code only ever sees the typed result.output.
5. Why can a smolagents CodeAgent solve in 1 step what takes a JSON tool-caller 6?
Its action is generated Python: one step can loop, call several tools, and aggregate with variables. Cost: you're executing model-written code — sandbox (E2B/Docker) in production.
6. In LlamaIndex Workflows, how do steps get connected if you never define edges?
By event types: each @step declares which Event it consumes and emits, and the runtime infers the wiring. Events ≈ edges, Context ≈ state + checkpointer.
7. What do you give up and gain by choosing the Claude Agent SDK over LangGraph?
Give up: orchestration control and provider choice (the loop is fixed, Anthropic-only). Gain: a hardened production harness — context management, safe file/bash tools, permissions, sessions, subagents, MCP — with near-zero code.
8. Team ships .NET on Azure and wants both quick chat agents and typed graph workflows. One framework?
Microsoft Agent Framework — the AutoGen + Semantic Kernel successor: ChatAgents for the simple cases, WorkflowBuilder graphs (very LangGraph-like) with checkpointing for the rest.
Retention plan (90 minutes total): pick TWO — the one closest to your stack (likely Claude Agent SDK) and the one most unlike LangGraph (smolagents or CrewAI). Port one small thing you've already built in LangGraph to each. Translating a known artifact teaches more than any course.
