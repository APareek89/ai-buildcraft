What is the cloud, really?

The cloud is other people's computers, rented by the second, over the internet. Amazon, Google, and Microsoft own hundreds of giant, anonymous-looking buildings around the world, each packed with hundreds of thousands of computers stacked in racks, with industrial cooling and backup power. Instead of buying a server, waiting weeks for delivery, installing it in your office, and hiring someone to maintain it — you run one command and have a computer working for you eleven seconds later, in Mumbai or Virginia or Frankfurt, and you stop paying the moment you switch it off.

A tiny bit of history makes the "why" obvious. Around 2006, Amazon (the shopping company) had built enormous computing infrastructure for its own store, and realized it could rent the spare capacity out. That became AWS — Amazon Web Services. It solved a real pain: before this, every startup had to spend lakhs on servers before writing a line of product code, and had to guess capacity months ahead. Google and Microsoft followed with Google Cloud Platform (GCP) and Azure.

Analogy
The cloud did to computing what the electricity grid did to power. In 1900, factories ran their own generators — expensive, unreliable, and someone had to maintain them. The grid made power a utility: plug in, pay per unit, and the utility company worries about the machinery. Computing is now a utility. And just like electricity, the bill rewards those who switch things off.

Capex vs opex — the business reason clouds won

Two finance words you should genuinely know, because interviewers use them and executives think in them:

  • Capex (capital expenditure) — big money spent upfront to own an asset. Buying ₹50 lakh of servers is capex. Risky: you pay before you know if your product will succeed, and the hardware ages whether used or not.
  • Opex (operational expenditure) — ongoing pay-as-you-go spending, like rent or electricity. Cloud bills are opex. You pay in proportion to actual usage, and can stop anytime.

Cloud converts capex into opex. That's why a two-person startup can serve a million users: they never had to buy the million-user hardware — they rented it the month the users showed up.

The 20 words that unlock everything

Read this section slowly — every later tab (and every interview) assumes these.

Client, server, request, response

A client is the program asking for something — your browser, your mobile app, a Python script. A server is the program (and by extension, the computer) answering. The client sends a request ("give me the homepage", "answer this chat message"); the server sends back a response. That's the entire internet: billions of request–response pairs. The frontend is the part users see (runs on their device — HTML/JS, a mobile app); the backend is your logic running on servers.

HTTP and HTTPS

HTTP is the language clients and servers speak — a strict format for requests and responses. A request names a method (GET = read something, POST = send/create something) and a path (/chat); a response carries a status code — a 3-digit result: 200 OK, 404 not found, 429 too many requests (you'll meet this one constantly in AI work — it means "slow down"), 500 server crashed. HTTPS is HTTP with encryption — the padlock — so nobody between the user and the server can read the data. Everything you build should be HTTPS; the cloud makes certificates free and automatic.

API and JSON

An API (application programming interface) is a service's menu of things other programs may ask it to do. When your app "calls the LLM API", it sends an HTTP request like POST /v1/messages with data, and gets structured data back. That data is almost always JSON — a simple text format both humans and programs read easily:

{ "model": "claude-sonnet-4-5",
  "messages": [ { "role": "user", "content": "Summarize this ticket..." } ] }

If you remember one framing: websites are for people, APIs are for programs — same servers, different consumers.

IP address and DNS

Every machine on a network has an IP address (like 3.7.45.12) — its phone number. A public IP is reachable from the whole internet; a private IP works only inside your own network (your cloud servers talk to each other on private IPs — safer and cheaper). DNS (domain name system) is the phonebook that turns a human name (chat.acme.com) into an IP address. You'll see this pipeline again in tab 7.

Latency, throughput, bandwidth
  • Latency — how long ONE request takes, in milliseconds (ms). Distance matters: light in fiber crosses ~100 km per millisecond, so Mumbai→Virginia and back is ~200ms before any work happens. This is why you choose regions near users.
  • Throughput — how MANY requests you can handle per second. A system can have great latency and terrible throughput (fast, but collapses under crowd) or vice versa.
  • Bandwidth — how much data per second a connection can carry (a pipe's width). Matters when moving big files, datasets, or model weights.
Availability and durability — different promises
  • Availability — the % of time a service answers. Counted in "nines": 99.9% availability still allows ~8.8 hours of downtime per year; 99.99% allows ~53 minutes. Each extra nine costs real architecture (more copies, more zones).
  • Durability — the probability your stored data is never lost, even if the service is temporarily down. Object storage advertises "eleven nines" (99.999999999%) of durability: statistically, store ten million files for ten thousand years and expect to lose one. A service can be briefly unavailable while your data stays perfectly durable.
Scalability and elasticity — the interview favorite

Scalability is the ability to handle more load by adding resources. Elasticity is doing that automatically in both directions — growing at 11am, shrinking at 3am, so cost tracks demand. Two ways to scale:

  • Vertical scaling (scale up) — a bigger machine. Simple, but has a ceiling (there's a biggest machine) and usually needs a restart.
  • Horizontal scaling (scale out) — more copies of the machine/app behind a load balancer. No ceiling, no downtime, and it's how the cloud wants you to think. Requires your app to be stateless (next word).
Stateless vs stateful

A stateless app keeps no memory on the machine between requests — every fact it needs, it reads from a database or storage. Why care? Because stateless copies are interchangeable: any of 50 copies can answer any request, machines can be killed and replaced freely, and horizontal scaling just works. A stateful app (user session stored in the machine's memory, files saved to its local disk) breaks the moment a second copy exists or the first one dies. Rule you'll see all over this guide: state lives in databases and object storage, never in the app machine.

Synchronous vs asynchronous

Synchronous (sync) — the caller waits for the answer, like a phone call. Asynchronous (async) — the caller drops a request and moves on; the work happens later and the result arrives via a callback, notification, or polling — like WhatsApp. AI apps are full of slow jobs (a 5-minute video generation must not freeze a browser tab), so async patterns get their own tab (tab 6).

Managed vs self-managed

A managed service means the cloud runs the software for you — installs, patches, backs up, scales, replaces failed hardware — and you just use it (a managed Postgres, a managed Kubernetes). Self-managed means you install software on rented VMs and own every 3am problem. The recurring theme of this entire guide: default to managed; self-manage only with a strong reason (control, cost at extreme scale, special requirements).

Regions, availability zones, and edge — where things physically live

Every cloud divides the planet into regions — independent clusters of data centers in one geographic area (Mumbai ap-south-1, Frankfurt, Virginia, Singapore…). Each region contains 2–6 availability zones (AZs): physically separate buildings, kilometers apart, each with its own power, cooling, and network, connected to each other by very fast private fiber (~1–2ms). On top of that, clouds run hundreds of small edge locations in cities everywhere — not full regions, just caching outposts used by CDNs (tab 7).

Why this three-level design exists

  • AZs protect you from building-level disasters. A fire, flood, or power failure takes out one AZ; an app running copies in 2–3 AZs keeps serving. "Multi-AZ" is the standard baseline for anything serious — managed databases offer it as a checkbox (a standby copy in another AZ, automatic failover).
  • Regions protect you from city-level disasters and serve latency/legal needs. Users in India get a Mumbai region; EU personal data can stay in EU regions (data residency — a real legal constraint in many industries, and a frequent interview point).
  • Edge locations make static things fast everywhere without you running servers everywhere.

How to choose a region (in priority order)

  1. Latency — closest to your users.
  2. Service & model availability — not every service/GPU/AI model exists in every region; check before committing (classic GenAI gotcha: your chosen LLM isn't live in Mumbai yet).
  3. Compliance — where is the data legally allowed to live?
  4. Price — the same VM can cost 10–30% more in some regions.
Worth remembering
Region = city (isolated cluster). AZ = building(s) within it (failure isolation). Edge = neighborhood cache. Multi-AZ is the default for production; multi-region is an advanced, expensive choice for the biggest apps (tab 11).

The three clouds — personalities, not just names

  • AWS — first mover (2006) and market leader (~30% share). The deepest catalog (200+ services), the most third-party tooling, the most job postings. GenAI hub: Bedrock — a marketplace of models (Anthropic Claude, Meta Llama, Amazon's own Nova, Mistral…) behind one API. Culture: many small building blocks you compose yourself.
  • Google Cloud (GCP) — (~11–13% share) born from Google's internal engineering; invented Kubernetes and TensorFlow. Strongest reputation in data analytics (BigQuery) and AI tooling; famously clean developer experience (Cloud Run is widely loved). GenAI hub: Vertex AI — Gemini models plus a Model Garden (including Claude and open models).
  • Azure — (~20–25% share) Microsoft's cloud; the default wherever a company already lives in Microsoft 365, Windows, and Active Directory. Famous for the exclusive OpenAI partnership. GenAI hub: Azure OpenAI within Azure AI Foundry — GPT-4o family and o-series plus a large open-model catalog.

Real-world choosing logic (also a good interview answer): startups often pick whatever the founding engineers know, or GCP for developer experience; enterprises often pick Azure because procurement and identity already live with Microsoft; AI-first teams pick by which models and GPUs they need. Multi-cloud (using two+) is common at big companies but adds real complexity — the standard advice is: pick one primary cloud, design portably (containers, Postgres, S3-compatible storage), and only go multi-cloud for a concrete reason.

Interview corner — try answering aloud before you click
What is cloud computing, in one crisp answer?

"Cloud computing is on-demand access to computing resources — servers, storage, databases, AI models — over the internet, with pay-as-you-go pricing. Instead of buying and maintaining hardware (capex), you rent exactly what you use (opex), and can scale resources up and down in minutes. Providers like AWS, GCP, and Azure run the physical infrastructure across global regions."

That's ~4 sentences: definition, economic angle, elasticity, providers. Interviewers want structure, not an essay.

What's the difference between scalability and elasticity?

Scalability is the ability to handle growth by adding resources (a scalable system CAN grow). Elasticity is automatically adjusting resources both up AND down to match current demand — grow for the 11am rush, shrink at 3am so you stop paying. Elasticity is what makes cloud economics work; a data center can be scalable but is never elastic — you can't return servers you bought.

Explain regions vs availability zones. Why do both exist?

A region is an isolated geographic cluster of data centers (e.g., Mumbai). An availability zone is one or more physically separate buildings within a region, with independent power/cooling/network, linked by ~1–2ms private fiber. AZs exist for high availability: run copies across 2–3 AZs and a building fire doesn't take you down, while the low latency between AZs keeps the app fast. Regions exist for disaster isolation, user latency, and legal data residency. Baseline production posture: multi-AZ. Multi-region is reserved for the most critical systems because it costs and complicates a lot more.

Why would a company move to the cloud — and when would it NOT make sense?

For: no upfront hardware (capex→opex), elasticity for spiky demand, global reach in minutes, managed services that remove undifferentiated work (backups, patching), and access to hardware you could never buy (latest GPUs, planet-scale storage).

Against (say this too — it shows judgment): very steady, predictable, high-volume workloads can be cheaper on owned hardware at scale; strict data-sovereignty or air-gapped requirements; huge existing data-center investments; and egress-heavy workloads where data-transfer fees dominate. Many large companies land on hybrid.

IaaS vs PaaS vs SaaS — with one example each?

IaaS: raw infrastructure you configure — EC2. PaaS: a platform that runs your code, you bring only the app — Cloud Run. SaaS: finished software you just use — Gmail. The ladder is "how much you manage vs how much the provider manages". FaaS (Lambda) is an even thinner slice of PaaS: you bring individual functions. Modern teams build with as much PaaS/managed as possible and drop to IaaS only for special control (e.g., custom GPU serving).

1

The concept, in detail

What a server physically is

A server is a computer built to run 24/7 without a screen or keyboard — a flat metal box slid into a rack (a tall shelf holding dozens of them) in a data center hall with industrial air conditioning, diesel backup generators, and multiple internet connections. You interact with it only over the network. When people say "the cloud", they mean millions of these boxes.

Virtualization — how one machine becomes twenty

A physical server is usually far more powerful than any single customer needs. A layer of software called a hypervisor splits one physical machine into many isolated virtual machines (VMs). Each VM believes it is a real computer with its own CPU share, memory, disk, and operating system; the hypervisor schedules them onto the real hardware and keeps them strictly walled off from each other — you can never see another customer's VM even though it may sit on the same physical board. This is the technology that makes renting-by-the-second possible: creating a VM is just software bookkeeping, not screwdrivers.

Analogy
A physical server is a building; the hypervisor is the builder who partitions it into flats. Every tenant gets their own locked flat (VM) with a private meter. "Noisy neighbors" exist here too — a tenant hammering the shared walls (heavy disk/network use on the same physical host) can occasionally be felt — clouds engineer hard to minimize it, and dedicated/bare-metal options exist for those who want the whole building.

CPU — the general-purpose brain

  • A CPU contains cores — independent workers. 8 cores = 8 tasks progressing truly simultaneously.
  • Most cores run 2 threads each ("hyperthreading") — two task-slots sharing one core's machinery. Cloud sellers count these slots: 1 vCPU = 1 thread, so a "4 vCPU" VM is usually 2 physical cores' worth. (Interviewers like this distinction.)
  • Clock speed (e.g., 3.5 GHz) = how many billions of operation-cycles each core performs per second — a rough per-worker speed rating.
  • CPUs are optimized for versatility: run Python, parse JSON, query a database, encrypt traffic — thousands of different small jobs, switched between millions of times a second. Your web/API backend is CPU-work.
  • Architecture families: x86 (Intel, AMD — the traditional standard) and ARM (the phone-chip architecture, now in servers: AWS Graviton, GCP Axion, Azure Cobalt). ARM instances are typically 20–40% cheaper for the same performance; nearly all modern languages and containers run on them unchanged. Choosing ARM is one of the easiest cost wins in the cloud — remember it for cost questions.

RAM — the working desk

RAM (memory) holds everything the machine is actively working on: the operating system (~0.5–1 GB), your app's runtime, every in-flight request, and any data you load. It is ~100,000× faster to access than disk but is wiped on power-off. Sizing intuition: a small Python API might live happily in 512 MB–1 GB; loading a data file eats its full size in RAM; every concurrent request adds its share. When RAM runs out, Linux's OOM killer (out-of-memory killer) abruptly kills your process — if your app "randomly dies under load", suspect memory first. In AI work, RAM also matters for data preprocessing and for running small models on CPU.

GPU — the parallel math engine (the star of the AI era)

A CPU has a few fast, clever cores. A GPU (graphics processing unit) has thousands of simple cores that all execute the same instruction on different pieces of data at once. Invented to color millions of screen pixels simultaneously, it turned out perfect for neural networks — which are, at the metal, gigantic matrix multiplications: multiply-and-add the same way across millions of numbers. A GPU does in one tick what a CPU would queue up thousands of ticks for.

  • VRAM is the spec that matters most. It's the GPU's own onboard memory; the model's weights must fit in it. Rule of thumb: at standard 16-bit precision a parameter takes 2 bytes, so a 7B-parameter model ≈ 14 GB, 70B ≈ 140 GB (needs multiple GPUs). Quantization shrinks weights to 8-bit or 4-bit (1 or 0.5 bytes/param) with modest quality loss — a 4-bit 7B model fits in ~4–5 GB. You also need headroom beyond weights for the working state of active requests (the KV cache — tab 8), so never size VRAM exactly at model size.
  • Know the GPU ladder by name: NVIDIA T4 (16 GB, older, cheap) → L4 (24 GB, efficient modern inference) → A10G (24 GB) → A100 (40/80 GB, serious training/inference) → H100/H200 (80–141 GB, the current workhorse of big AI) → B200 (newest generation). Price scales steeply: an L4-class VM is a few dollars/hour; H100-class machines are tens of dollars/hour.
  • Inference vs training: serving a model (inference) needs enough VRAM + good throughput — L4/A10G class often suffices for small models. Training/fine-tuning needs far more memory and compute — A100/H100 class, often several linked together.
  • Google's TPU is an alternative accelerator family (tensor processing units), GCP-only, excellent price/performance for large training jobs if your stack supports it (JAX/TensorFlow, increasingly PyTorch).

Disk — the cupboard

VM disks are usually network-attached SSD volumes ("block storage" — tab 4): they survive restarts and can be snapshotted, but every read crosses a wire. Performance is measured in IOPS (operations/second) and throughput (MB/s), and you pay for provisioned size. Some instance types add local NVMe — SSDs physically inside the host: blazing fast but their data is lost when the VM stops; use them as scratch space (e.g., staging training data), never as the only copy.

Example — business and code

Business scenario: your company wants an internal product-photo generator using an open-source image model. Ten designers will use it during work hours. Let's size and launch it like professionals.

Sizing walk-through (say this kind of math aloud in interviews): the model needs ~10 GB VRAM at 16-bit → an L4 (24 GB) or A10G (24 GB) gives comfortable headroom for the model plus generation workspace. Ten occasional users need no farm — one GPU with a small queue is plenty. General CPU/RAM needs are modest → the smallest VM size that carries that GPU. On AWS that's g6.xlarge (or g5.xlarge); GCP g2-standard-4; Azure NC4as_T4_v3 at the budget end.

# AWS: launch the GPU VM from a Deep Learning image (drivers preinstalled)
aws ec2 run-instances \
  --image-id ami-0abc123deeplearning \
  --instance-type g6.xlarge \
  --key-name my-laptop-key \
  --block-device-mappings '[{"DeviceName":"/dev/sda1","Ebs":{"VolumeSize":100}}]' \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=imggen}]'

# Connect and verify the GPU is visible
ssh -i my-laptop-key.pem ubuntu@<public-ip>
nvidia-smi        # shows GPU model, VRAM used/total, running processes

# Run the model server as a container (tab 3 explains containers)
docker run -d --gpus all -p 8000:8000 my-team/imggen-api:latest

# THE HABIT THAT SAVES THE MOST MONEY IN AI TEAMS:
aws ec2 stop-instances --instance-ids i-0123456789   # every evening
aws ec2 start-instances --instance-ids i-0123456789  # every morning (script it)

# GCP equivalent (one command, custom-fit machine)
gcloud compute instances create imggen \
  --zone=asia-south1-a --machine-type=g2-standard-4 \
  --accelerator=type=nvidia-l4,count=1 \
  --image-family=common-cu124 --image-project=deeplearning-platform-release \
  --boot-disk-size=100GB --provisioning-model=STANDARD

Cost sanity check: an L4-class VM ≈ $0.7–1.2/hour. Left running 24/7 ≈ $600–850/month; stopped nights and weekends (≈ 50 working hours/week) ≈ $150–250/month. Same hardware, 3–4× difference — purely operational discipline.

Key considerations

  • Size GPU by VRAM first (weights + per-request working memory), then check throughput. If it doesn't fit, nothing else matters.
  • GPU quotas start at zero on all three clouds — file the quota-increase request days before you need the hardware, and have a second region in mind (GPU availability varies by region week to week).
  • Stop what idles. Schedule off-hours shutdown for dev/internal GPU machines. Terminate what's abandoned — stopped VMs still pay for disks.
  • Spot for interruptible work only — training with checkpoints, batch generation, evaluations. Never for a live user-facing API without careful fallback design.
  • Prefer ARM (Graviton/Axion/Cobalt) for ordinary CPU services — a near-free 20–40% saving; containers make switching trivial.
  • Automate machine setup (startup scripts or baked images) — a hand-configured "pet" server becomes unreproducible; autoscaling and disaster recovery both depend on machines being stampable "cattle".
  • Don't run databases or file servers by hand on VMs — tabs 4–5's managed services exist so 3am disk failures are the cloud's problem.
  • Co-locate compute with its data (same region, ideally same AZ) — for latency and to avoid cross-location transfer fees.
Interview corner
What's the difference between a vCPU and a core?

A physical core is an independent processing unit. Most server cores run two hardware threads (hyperthreading), and clouds sell each thread as one vCPU — so 4 vCPUs typically means 2 physical cores running 4 threads. Two threads on one core share its execution machinery, so 4 vCPUs is less than 4 full cores' power for CPU-saturated work. For most web/API workloads (which wait on I/O a lot) the distinction rarely bites; for compute-heavy work it does.

Why are GPUs better than CPUs for AI? When are they NOT the right tool?

Neural networks reduce to enormous matrix multiplications — the same multiply-add repeated across millions of numbers. GPUs have thousands of simple cores that execute the same instruction across data in parallel, so they chew through matrix math orders of magnitude faster than a CPU's few sophisticated cores. VRAM also keeps the whole model close to those cores.

Not the right tool when: the workload is branchy, sequential, general-purpose logic (APIs, databases); the model is tiny (small classifiers run fine on CPU); or utilization would be low (a GPU idling at 5% is money on fire — batch work to fill it, or use a model API instead of owning the GPU at all).

Spot vs on-demand vs reserved — how would you combine them for an AI product?

Rule: match the pricing model to the workload's interruptibility and predictability. Steady baseline (the API servers that always run) → reserved/committed for ~30–60% off. Spiky/unpredictable traffic above baseline → on-demand via autoscaling. Interruptible heavy work — nightly batch embedding, fine-tuning with checkpoints, evaluations — → spot at 60–90% off, engineered to resume after eviction. A strong answer names all three plus the checkpoint caveat for spot training.

What happens when you stop a VM vs terminate it?

Stop: the machine powers off; compute billing stops; the disk persists (small storage charge); RAM contents are lost; on restart you get the same disk — but an auto-assigned public IP will be different (an Elastic/static IP avoids that). Terminate/delete: instance is destroyed and by default its boot disk too — recovery only from snapshots/images. Interview add-on: "that's why anything important lives off the VM — in object storage or a managed database — and why we snapshot disks."

How would you choose an instance type for a new service?

Start from the workload's bottleneck: web/API → general purpose; CPU-bound processing → compute-optimized; in-memory data → memory-optimized; model inference/training → GPU sized by VRAM. Prefer the newest generation (better price/performance) and ARM where compatible. Start one size smaller than instinct suggests, measure real CPU/RAM under load, then right-size — the cloud makes resizing a reboot, not a purchase order.

A 70B-parameter model — roughly what does it take to serve it yourself?

Weights alone: 70B × 2 bytes (fp16) ≈ 140 GB — beyond any single GPU, so it's sharded across several (e.g., 2× H100 80 GB minimum, realistically more for the KV cache and concurrent users). Quantized to 4-bit it's ~35–40 GB — one 80 GB GPU can hold it with headroom. This math — params × bytes/param, plus working-memory headroom — is exactly what interviewers want to hear, followed by the honest conclusion: below large scale, renting the model per-token (tab 8) usually beats owning GPUs.

Containers and serverless — how code actually ships

You will almost never run a real product by SSH-ing into a VM and typing commands. This tab covers how deployment really works in 2026 — and the story interviewers love to hear you tell.

~20 min read
1

The concept, in detail

The 20-year story in four steps (a great interview narrative)

  1. Bare metal (1990s–2000s): one app per physical server. Buying and racking hardware took weeks; servers ran at 10% utilization.
  2. Virtual machines (2000s–): the hypervisor packs many isolated VMs onto one machine. Provisioning drops to minutes, utilization rises. But each VM drags a full operating system — gigabytes of weight, minutes to boot.
  3. Containers (2013–, Docker): package just the app + its dependencies, sharing the host's OS kernel. Megabytes instead of gigabytes, milliseconds-to-seconds to start, identical everywhere.
  4. Serverless (2014–): stop thinking about machines entirely. Hand the platform code or a container; it runs, scales, and bills per actual use — including down to zero.

Each step trades control for convenience — and the professional skill is knowing which rung a given workload belongs on.

Containers, precisely

The problem containers solve: your app works on your laptop but breaks on the server, because the server has different Python versions, missing libraries, different OS packages. A container packages your code together with its entire environment — language runtime, libraries, system tools — into one sealed, portable unit that runs identically on any machine with a container engine. Docker is the standard tooling.

  • An image is the sealed package — built once from a recipe file (the Dockerfile), then immutable.
  • A container is a running instance of an image. One image can run as a hundred identical containers.
  • A registry stores and distributes images (like GitHub, but for built apps). You push after building, servers pull to run. Images are tagged (myapp:v1.4.2); avoid deploying the floating tag :latest in production — you can't tell what's actually running or roll back precisely.

Container vs VM — the exam-grade distinction: a VM virtualizes hardware and carries a whole guest operating system; a container virtualizes just the process environment and shares the host's OS kernel. Hence:

Reading a Dockerfile like a native

FROM python:3.12-slim            # start from a base image (slim = smaller = faster deploys)
WORKDIR /app                     # cd inside the image
COPY requirements.txt .          # copy ONLY the dependency list first...
RUN pip install -r requirements.txt   # ...so this expensive layer is CACHED
COPY . .                         # then copy the (frequently changing) code
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]  # what runs on start

Images are built in layers — one per instruction — and unchanged layers are reused from cache. That's why dependencies are copied and installed before the code: edit your code and rebuild, and only the last layers rebuild in seconds. Keep images small (slim base images, no build tools in the final image — "multi-stage builds" do the compiling in a throwaway stage): small images pull faster, which directly shortens cold starts and deploy times.

Kubernetes — the fleet manager (know what it is; don't start with it)

One container on one machine is easy. A real company runs hundreds of containers across dozens of machines — something must decide placement, restart crashes, roll out new versions gradually, and scale copies with load. Kubernetes (K8s) is that operating system for fleets. Its words, so they don't scare you: a node is a machine in the fleet; a pod is the smallest deployable unit (one or more containers that live together); a deployment declares "I want 5 replicas of this pod — keep it true"; a service gives pods one stable internal address; the horizontal pod autoscaler adds/removes replicas from metrics. You describe the desired state in YAML files; K8s continuously reconciles reality to match.

Its power is real, and so is its cost: steep learning curve, cluster upgrades, networking complexity. All three clouds sell managed Kubernetes (they run the control plane; you still design everything on top). Honest professional guidance — and a good interview line: "Kubernetes when you have many services, a platform team, or special needs like custom GPU scheduling; serverless containers otherwise."

Serverless — the platform runs the machines

Serverless containers (Cloud Run, App Runner, Container Apps): you supply an image and limits; the platform launches containers per incoming traffic, load-balances, autoscales — including to zero when idle — and bills per request-time. Functions (FaaS) (Lambda, Cloud Run functions, Azure Functions) go smaller: single-purpose code triggered by events — an HTTP call, a file landing in storage, a queue message, a schedule. No image required, tight limits (Lambda: 15 minutes max, up to 10 GB RAM).

Cold starts, demystified: when scaled to zero, the first request must wait for: pull the image (if not cached) → start the container → load your app (imports, model clients). That's ~0.5–5s for slim apps, worse for fat ones. Mitigations, in order of effectiveness: keep a warm minimum (min-instances 1), shrink the image, defer heavy initialization, and for Lambda specifically, provisioned concurrency. Scale-to-zero is a gift for internal tools and a hazard for user-facing chat — choose per audience.

Where GenAI workloads land (decision tree)

  • App calls a model API (the common case — tab 8): your backend is ordinary CPU work → serverless containers. Done.
  • Self-hosting a small open model: GPU serverless where available (Cloud Run with L4 GPUs) or a GPU VM behind a queue.
  • Self-hosting big models / many models: Kubernetes with GPU nodes + a serving engine (vLLM is the standard name to know) — this is specialist territory (tab 10).
  • Event glue (file uploaded → extract text; nightly batch → summarize): functions, every time.

Key considerations

  • Default to serverless containers for GenAI backends; escalate to Kubernetes only for a concrete reason (many services, custom GPU scheduling, platform team exists).
  • Statelessness is non-negotiable: no user data on container disks, no in-memory sessions you can't lose. Files → object storage; state → databases; then any copy can die anytime and nobody notices.
  • Set min-instances for user-facing latency; max-instances always — the max is your blast-radius control for both traffic spikes and runaway bugs.

  • One process per container; compose services, don't build monolith containers — the API, the worker (tab 6), and the scheduled jobs deploy separately and scale independently.

Interview corner
Containers vs virtual machines — explain the difference and when you'd use each.

A VM virtualizes hardware: each carries a full guest OS on a hypervisor — gigabytes, minutes to boot, hardware-grade isolation. A container virtualizes the process environment and shares the host kernel — megabytes, sub-second start, hundreds per host. They compose rather than compete: clouds run your containers on VMs. Choose raw VMs when you need OS control, special drivers (GPUs historically), or strong tenant isolation; choose containers as the packaging for essentially all application code.

What problem does Kubernetes solve? Why might you deliberately avoid it?

It solves running many containers across many machines: scheduling/placement, self-healing restarts, service discovery, rolling deployments, and autoscaling — declared as desired state that the system continuously reconciles. Avoid it when a managed serverless-container platform already gives you those outcomes without the operational tax (cluster upgrades, YAML sprawl, networking). Strong closer: "I'd start on Cloud Run/Container Apps and adopt K8s when we have a platform team or requirements those platforms can't express — like custom GPU bin-packing for self-hosted models."

What is a cold start, and how do you mitigate it?

The latency penalty when a scaled-to-zero service receives its first request: the platform must pull the image, start the container, and initialize the app before serving. Mitigations: keep a warm floor (min instances / provisioned concurrency), shrink the image, lazy-load heavy resources, and keep initialization out of the request path. Mention the product angle: for a chat UI, a 3-second cold start reads as "broken", so user-facing AI services usually pay for one warm instance.

On AWS: ECS vs EKS vs Fargate vs Lambda — untangle them.

ECS: Amazon's own, simpler container orchestrator. EKS: managed standard Kubernetes (portable skills/configs). Fargate: the serverless compute layer that runs containers for ECS or EKS with no visible EC2 machines. Lambda: functions, not services — event-triggered code with a 15-minute ceiling. Rule of thumb: Lambda for event glue, ECS-on-Fargate (or App Runner) for services, EKS when you specifically want Kubernetes.

Why must a horizontally scaled app be stateless? What do you do with the state?

Because with N interchangeable copies behind a load balancer, consecutive requests land on different copies, and copies are killed/created constantly by autoscaling and deploys. Any state trapped in one copy's memory or disk is lost or inconsistent. So state is externalized: sessions → a cache or signed tokens; files → object storage; records → databases. Then scaling, deploys, and failures all become non-events.

When is serverless the WRONG choice?

(1) Steady, high, predictable load — always-on reserved VMs/containers can be cheaper than per-request pricing. (2) Ultra-latency-sensitive paths where even rare cold starts are unacceptable and you'd pay for so much warm capacity that the model stops making sense. (3) Very long-running or specialized jobs (multi-hour training on specific GPUs). (4) Workloads needing deep OS/hardware control. Showing you know serverless's limits is worth as much as knowing its strengths.

Storage — where every file in your AI app lives

Datasets, user uploads, PDFs, generated images, model weights, logs — all files, all needing a home with the right speed, price, and safety. This tab is about files; queryable records come next.

1

The concept, in detail

First, know your data's shape

  • Structured — rows and columns with a fixed schema (orders, users) → databases (tab 5).
  • Semi-structured — flexible but parseable (JSON, logs) → databases or object storage.
  • Unstructured — images, video, audio, PDFs, model weights: the bulk of AI data by volume → object storage, the hero of this tab.

Object storage — the workhorse, in depth

Object storage holds objects (files + metadata) inside buckets (top-level containers with globally unique names). Every object is addressed by its key — its full name, like uploads/cust-42/2026-07/invoice-991.pdf. Crucial mental shift: there are no real folders. The slashes are just characters in the key; the console draws a folder UI as a convenience. This "flat namespace" is what lets a bucket hold trillions of objects without slowing down — there is no directory tree to walk, just a giant key-value lookup.

  • Capacity: effectively infinite. You never provision size; you just pay per GB stored per month.
  • Objects are immutable: you don't edit an object; you overwrite it with a new version. (With versioning enabled, old versions are kept — your undo button against bad overwrites and accidental deletes.)
  • Durability — the famous eleven nines: 99.999999999% yearly durability means if you stored 10 million objects, you'd statistically expect to lose one every 10,000 years. How: every object is automatically stored as redundant fragments across multiple availability zones; background processes constantly verify checksums and heal any corrupted fragment. You get this without doing anything.
  • Durability ≠ availability: the service might be unreachable for a few minutes a year (availability ~99.9–99.99%) while your data remains perfectly safe. Two different promises — a favorite interview trap (see the corner).
  • Consistency: modern object stores (S3 since 2020, GCS, Azure Blob) are strongly consistent — the instant your write succeeds, every read sees it. (Older interview material says S3 was "eventually consistent" — outdated.)
  • Big files: uploads above ~100 MB use multipart upload — the file is split into chunks uploaded in parallel and reassembled; SDKs do this automatically. This is how multi-GB model weights move around.
  • Event notifications: a bucket can emit an event when an object arrives — the trigger that starts serverless pipelines ("PDF uploaded → Lambda extracts text → index for RAG"). This one feature wires tabs 3, 6, and 9 together.
  • Static website hosting: a bucket can directly serve your frontend's HTML/JS/CSS — with a CDN in front (tab 7), that's the standard way to host a React/Vue app with zero servers.

There are also auto-tiering classes (S3 Intelligent-Tiering, GCS Autoclass) that move objects based on observed access — the lazy person's correct choice for unpredictable access patterns.

Block storage — the VM's disk

Block storage is the virtual SSD attached to a VM (tab 2): the machine sees raw disk blocks and puts a filesystem on them. Attached to one VM at a time, provisioned by size (pay for 500 GB even if 50 used), with performance in IOPS (read/write operations per second) and MB/s throughput. Tiers exist (AWS: gp3 general SSD vs io2 high-IOPS for demanding databases). Snapshots — incremental point-in-time backups stored in object storage — are cheap; take them before risky changes and on schedule.

File storage — the shared drive

File storage is a managed network drive (NFS/SMB protocols) that many machines mount simultaneously and see as a normal folder. Slower and pricier per GB than object storage, but sometimes exactly right: a training job across 8 GPU machines all reading the same dataset via ordinary file paths, or legacy software that insists on a filesystem.

Moving data costs money — the egress rule

The pricing rule that surprises everyone: data flowing IN to a cloud is free; data flowing OUT is billed (~$0.09–0.12/GB to the internet, cheaper between regions, small fees even between AZs for some paths). For an image/video AI product serving big files to users, egress can rival compute costs. Levers: serve through a CDN (cheaper per GB + caching), compress/resize outputs, and keep processing next to the data instead of moving the data.

Interview corner
Object vs block vs file storage — the classic. Answer it well.

Block: raw disk volumes attached to one machine — the VM's own filesystem lives on it; highest IOPS; provisioned by size (EBS/Persistent Disk/Managed Disks). File: a managed network share many machines mount over NFS/SMB simultaneously (EFS/Filestore/Azure Files). Object: a flat, HTTP-accessed store of immutable objects in buckets — effectively infinite, eleven-nines durable, cheapest per GB (S3/GCS/Blob). Rule of thumb: OS and databases → block; shared POSIX access (e.g., multi-node training) → file; everything else, at scale → object.

What's the difference between durability and availability?

Durability = will my data still exist, long-term (protection against loss/corruption). Availability = can I access it right now (uptime). S3-class storage offers ~11 nines durability but "only" ~99.9–99.99% availability: it may be briefly unreachable, yet essentially never loses data — achieved by storing redundant, checksummed fragments across multiple AZs with continuous background repair. Naming both numbers and the mechanism is a complete answer.

How do pre-signed URLs work, and why are they the right pattern?

The backend, which has permission on the bucket, generates a URL containing a cryptographic signature covering the exact object, action (GET or PUT), and expiry. Anyone holding the URL can perform just that action until it expires — the storage service verifies the signature statelessly. Right because: the bucket never becomes public, permissions are per-object and time-boxed, and large files flow directly between the user and storage instead of through (and billing/tying up) your app servers.

Your storage bill keeps climbing. What do you look at?

In order: (1) lifecycle — is anything expiring or tiering, or does data only accumulate in Standard? (2) What's actually big — storage-class analysis / inventory reports to find the heavy prefixes. (3) Versioning bloat — old versions and incomplete multipart uploads (there's a lifecycle rule to purge those). (4) Egress vs storage split on the bill — maybe it's transfer, not storage; add/tune the CDN. (5) Regenerable artifacts (thumbnails, cached outputs) — delete-and-recompute beats storing forever.

Databases and vector databases

Files hold blobs; databases hold facts you can question, safely, from a thousand places at once. And AI adds a new member to the family — the database of meaning.

~22 min read
1

The concept, in detail

Why not just use files?

Imagine 200 app copies (tab 3) all appending orders to one orders.json. Two write at the same instant — one overwrites the other. The app crashes halfway through writing — the file is half-garbage. You want "orders above ₹5,000 this month" — you must read everything. Databases exist to solve exactly these: safe concurrent access, all-or-nothing changes, and fast targeted questions.

ACID — the four safety guarantees (a certified interview classic)

Relational databases promise transactions — groups of changes with ACID properties. Learn it with a bank transfer (₹500 from A to B = subtract from A + add to B):

  • A — Atomicity: all steps happen or none do. Crash after the subtraction? The whole transaction rolls back — money never vanishes mid-flight.
  • C — Consistency: every transaction moves the DB from one valid state to another — rules (balances can't go negative, IDs must exist) are never left violated.
  • I — Isolation: concurrent transactions don't see each other's half-done work; the result is as if they ran one-by-one.
  • D — Durability: once the DB says "committed", the change survives crashes and power loss — it's on disk, not just in RAM.

Relational databases (SQL) — the default

Data lives in tables with typed columns and rows. A primary key uniquely identifies each row; a foreign key in one table points at rows of another (an order's user_id → the users table) — that's the "relational" part. You ask questions in SQL:

SELECT u.name, SUM(o.amount) AS total
FROM   orders o JOIN users u ON u.id = o.user_id   -- stitch two tables together
WHERE  o.created_at > now() - interval '30 days'
GROUP  BY u.name ORDER BY total DESC LIMIT 10;      -- top 10 customers this month

Indexes are the speed secret: without one, a query scans every row; with one, the DB jumps straight to matches — a phonebook (sorted, jump to "Sharma") vs reading every page. Index the columns you filter and join on; each index slightly slows writes, so don't index everything. The single most common cause of "our app got slow as data grew" is a missing index — and the command that reveals it is EXPLAIN (shows the query's plan). PostgreSQL is the engine to default to: open-source, powerful, and — via extensions like pgvector — surprisingly future-proof.

How relational databases scale
  1. Vertically first — a bigger machine gets you shockingly far (terabytes, tens of thousands of queries/sec).
  2. Read replicas — live copies that serve reads (most apps are 90% reads); the single primary takes all writes. Replication is usually asynchronous → replicas can lag by milliseconds–seconds; don't read-your-own-write from a replica.
  3. Caching in front (below) to absorb repeated reads.
  4. Sharding — splitting rows across multiple databases (users A–M here, N–Z there) — last resort; adds real application complexity. Saying "sharding is a last resort" is itself a good interview signal.

NoSQL — different shapes for different jobs

  • Key-value / document stores (DynamoDB, Firestore, Cosmos DB): JSON-ish records fetched by key, schema-flexible, effortlessly horizontal — data is spread across many machines by a partition key (choose it so traffic spreads evenly; a "hot" key that everyone hits defeats the design). Single-digit-millisecond lookups at any scale; weaker at ad-hoc cross-record queries and joins.
  • Wide-column (Cassandra, Bigtable): huge write-heavy time-series/telemetry workloads.
  • Graph (Neptune, Neo4j): data that IS relationships (social networks, knowledge graphs, fraud rings).

CAP theorem, in plain words (asked constantly): when a network Partition cuts a distributed database's nodes off from each other, each node must choose: refuse to answer (Consistency — never serve stale data) or keep answering possibly-stale data (Availability). You can't have both during the partition. Systems pick a bias: classic SQL setups lean consistent; Dynamo-style stores lean available with eventual consistency — replicas converge shortly after writes, so a read a moment later might briefly see the old value. Real products mix both: strong consistency for money, eventual for feeds and likes.

Caches — RAM speed in front of the database

A cache (Redis / Valkey being the standard) keeps hot data in memory for ~0.1ms reads. The standard cache-aside pattern:

def get_user(uid):
    if (u := cache.get(f"user:{uid}")):        # 1. try cache
        return u                               #    hit → microseconds
    u = db.query("SELECT ... WHERE id=%s", uid)  # 2. miss → real DB
    cache.set(f"user:{uid}", u, ttl=300)       # 3. store for 5 min
    return u

The hard part is invalidation — stale cache after data changes. Practical rules: short TTLs are underrated; delete cache keys on writes; never cache what must be exactly fresh (balances). Caches also do rate-limit counters, sessions, queues-in-a-pinch, and — new in the AI era — semantic caching: cache LLM answers keyed by the embedding of the question, so "reset my password?" hits the cached answer for "how do I change my password" (tab 11 revisits this as a cost lever).

Vector databases — the database of meaning

Recap from the AI side: an embedding model (tab 8) turns any text (or image) into a vector — a list of, say, 1,536 numbers — positioned so that similar meanings land near each other. "My card was charged twice" and "duplicate payment on my account" share almost no words but sit close in vector space. Similarity is measured with cosine similarity — how aligned two vectors' directions are (1 = same direction, 0 = unrelated).

A vector database stores millions of these and answers "give me the k nearest vectors to this one" in milliseconds. Comparing against every row would be too slow, so it builds an ANN index (approximate nearest neighbor). The intuition for the most common one, HNSW: a multi-level "highway network" — top levels are sparse express roads that get you to the right neighborhood in a few hops; lower levels are dense streets for the final approach. "Approximate" is the honest word: you trade a tiny bit of recall (occasionally missing a true nearest neighbor) for 100–1000× speed; index parameters tune that trade.

Two upgrades that turn demos into products: metadata filtering — every vector carries fields (tenant, source, date, language) and the search is "nearest neighbors where tenant = 42" (also your multi-tenant privacy wall); and hybrid search — run keyword search and vector search, merge the ranked lists (a simple, standard trick called reciprocal rank fusion), so exact tokens like "error 4012" or "PB-30" aren't lost by pure semantics. A final optional reranker model re-orders the top ~50 candidates with a more careful (slower) relevance model — tab 9 shows where it slots in.

Key considerations

  • Managed, always — with multi-AZ enabled and point-in-time recovery on for anything production. Test a restore once; an untested backup is a hope, not a backup.

Interview corner
SQL vs NoSQL — how do you actually choose?

Choose by data shape, query needs, and consistency needs. SQL when data is relational, you need ad-hoc queries/joins/aggregations, and ACID matters (orders, billing) — and it scales further than people assume (vertical + replicas + cache). NoSQL when access patterns are known and simple (fetch by key), scale is massive and horizontal, schema flexibility matters, and per-record consistency suffices. Strong closer: "Default Postgres; adopt DynamoDB-style stores for specific high-scale key-lookup paths — many real systems use both."

Explain ACID with a concrete example.

Use the bank transfer: atomicity — debit and credit commit together or not at all; consistency — no rule (like non-negative balance) is ever left broken; isolation — a concurrent report can't see the money missing from both accounts mid-transfer; durability — once committed, a crash can't unwind it. One sentence each, anchored to the example, beats reciting definitions.

Explain CAP theorem simply. What is eventual consistency?

In a distributed store, when a network partition splits nodes, you must pick per-system: stay consistent (refuse possibly-stale answers → some unavailability) or stay available (answer with possibly-stale data). Eventual consistency is the available-side behavior: replicas converge to the same value shortly after writes stop, so a read may briefly see old data. Example: a like-count can be eventual; an account balance cannot. Bonus point: CAP only bites during partitions — normal operation offers both.

Read replica vs cache — when each?

Both offload reads. A replica is a full live copy of the DB — serves any query, seconds of lag possible, roughly doubles DB cost; right for heavy/diverse read traffic and reporting. A cache stores specific hot results in RAM — microsecond reads, tiny cost, but only helps repeated lookups and introduces invalidation work; right for "same small set of things read constantly". Real systems: cache for the hot path + replica for breadth.

The app is fast with 1,000 rows, slow with 10 million. Walk me through your debugging.

(1) Find the slow queries (slow-query log / performance insights). (2) EXPLAIN them — look for full table scans ("Seq Scan"). (3) Add indexes matching the filter/join columns; re-check. (4) Fix N+1 patterns (100 queries in a loop → one query with a join or IN-list). (5) Cache genuinely hot reads; move reporting to a replica. (6) Only then talk hardware. This ordered list — measure, explain, index, restructure, cache, then scale — is exactly the maturity interviewers probe for.

How does a vector database find "similar meaning" so fast?

Texts are embedded into high-dimensional vectors where semantic similarity = geometric closeness (cosine similarity). Instead of comparing the query against every stored vector, an approximate-nearest-neighbor index like HNSW navigates a small-world graph — sparse "express" layers hop to the right region, dense layers refine — returning near-certainly-the-nearest neighbors in milliseconds at the cost of a small recall trade-off, tunable via index parameters. Add metadata filtering (tenant/date) and optionally hybrid keyword+vector fusion for production-grade retrieval.

pgvector vs a dedicated vector database (Pinecone/Qdrant) — trade-offs?

pgvector: one system for facts + vectors (joins! transactions! one backup story!), zero new infrastructure, plenty fast to ~millions of vectors — the right default. Dedicated: better at extreme scale (tens/hundreds of millions), advanced index tuning, built-in hybrid/rerank features, but adds a second datastore to sync, secure, and pay for. Answer with a number: "I'd start pgvector and revisit past ~5–10M vectors or if p95 retrieval latency breaches our budget."

Queues, events, and async work

AI jobs are slow — generations take seconds to minutes, model APIs throttle you, batches number in millions. The pattern that makes all of that feel instant to users is asynchronous processing. Interviewers probe this area hard.

~18 min read
1

The concept, in detail

The problem, concretely

A user clicks "generate video". The job takes 4 minutes of GPU time. If your API handles it synchronously — holding the connection open until done — you get: a frozen browser tab, a timeout somewhere in the chain (tab 7), a lost job if the worker dies at minute 3, and a collapse the moment 50 users click together against your 4 GPUs. Every one of those problems has the same cure: decouple accepting work from doing work.

The queue — a waiting line for work

A message queue is a managed holding area. Producers (your API) drop small messages — "job 812: generate video with these settings" — and return to the user instantly with a job ID. Consumers/workers (separate processes, tab 3) pull messages when free, do the heavy work, and record results. The queue in between gives you, for free:

  • Instant user experience — accepting a job takes 20ms regardless of how long the job runs.
  • Spike absorption — 5,000 requests in one minute? The queue holds them; your 4 GPU workers chew through at their own pace. Nothing falls over; things just take longer. (The formal word: backpressure handling.)
  • Failure recovery — worker dies mid-job? The message reappears for another worker (mechanics below).
  • Independent scaling — scale workers on queue depth: 0 messages → 0 workers; 10,000 → 40 workers.
Analogy
A busy restaurant doesn't have waiters cook. Waiters (your API) take orders in seconds and pin tickets to the kitchen rail (the queue); cooks (workers) pull the next ticket when a burner frees up. A sudden tour bus (traffic spike) means a longer rail, not a collapsed kitchen — and if a cook faints mid-dish, the ticket goes back on the rail.

The mechanics interviewers actually ask about

  • Visibility timeout: when a worker takes a message, it isn't deleted — it becomes invisible for a set period. Worker finishes → explicitly deletes it. Worker crashes → the timeout expires and the message reappears for someone else. That's the failure-recovery magic. Corollary: set the timeout longer than your longest job (and extend it via heartbeats for very long jobs), or a slow-but-alive job gets duplicated.
  • At-least-once delivery: that same mechanism means a message can occasionally be delivered twice (worker finished but crashed before deleting). "Exactly-once" is, in practice, marketing — the honest engineering answer is to make processing idempotent: doing the job twice must be harmless. Standard trick: an idempotency key — check "job 812 already completed?" before working, write results keyed by job ID so a repeat overwrites identically.
  • Retries with backoff: transient failures (LLM API returned 429/500) → put the message back and retry after an increasing delay (1s, 4s, 16s… — "exponential backoff", plus randomness/"jitter" so a thundering herd doesn't retry in lockstep).
  • Dead-letter queue (DLQ): a message that fails N times (a corrupt PDF, an impossible job — a "poison message") is moved aside to a special queue instead of clogging the line forever. You alarm on DLQ depth, inspect, fix, and replay. A system without a DLQ retries garbage forever.
  • Ordering: standard queues don't guarantee order (and are massively parallel). FIFO/ordered modes exist but cap throughput — only demand ordering where the business truly needs it (rarely).

Pub/sub — one event, many listeners

A queue is one line of work for one pool of workers. Publish/subscribe flips the shape: a producer publishes an event to a topic ("video 812 finished"); every subscriber gets a copy — one updates the database, one notifies the user, one records analytics. The publisher doesn't know or care who's listening — that's decoupling: adding a fourth reaction later means adding a subscriber, not editing the publisher. The classic composition is fan-out: topic → multiple queues, one per consumer team, each with its own retries and DLQ.

Two relatives to recognize

  • Event bus / scheduler (EventBridge, Cloud Scheduler+Tasks, Event Grid): a router with rules — "when event type = payment.failed, invoke this function" — plus cron ("every night at 2am, start the re-index job"). The glue of serverless architectures.
  • Streams (Kafka, Kinesis, Pub/Sub in stream-mode, Event Hubs): a replayable, ordered log of events kept for days — consumers read at their own pace and can rewind. For analytics pipelines, clickstreams, telemetry at huge scale. Queue = task to do once; stream = history to read. Knowing that one sentence is usually enough.

The async job pattern for AI (memorize this shape)

  1. API receives request → writes a job row (status=pending) in the DB → enqueues job ID → returns 202 Accepted + job ID immediately.
  2. Worker pulls → sets status=processing → calls the GPU/LLM (the slow part) → writes output to object storage → sets status=done + result URL. On repeated failure → status=failed + DLQ.
  3. The user's app either polls GET /jobs/812 every few seconds (simple, fine) or gets a push via websocket/webhook (fancier).

This one shape covers video generation, bulk embedding, document processing, report generation, fine-tuning kicks — half of applied AI engineering is this diagram wearing different hats.

Key considerations

  • Anything slower than ~2–3 seconds should probably be async — return a job ID, do the work behind a queue. (Streaming chat is the notable exception — that's a live connection by design, tab 7.)
  • Design workers idempotent from day one — at-least-once delivery is a promise of duplicates eventually; a cheap "already done?" check makes them harmless.
  • Visibility timeout > worst-case job time, or slow jobs silently double-run (the classic subtle bug: two watermark-removed images, one bill… twice).
  • Always attach a DLQ + alarm. A poison message without a DLQ retries forever, burning money and blocking honest work.
  • Autoscale workers on queue depth, not CPU — depth is the true demand signal for job systems (this is also how you drive GPU worker pools; KEDA is the Kubernetes tool-name for it).
  • Use the queue as your LLM rate-limit shock absorber — workers pull at exactly the rate your model quota allows (tab 8); bursts pile up harmlessly instead of raining 429s.
  • Keep messages small: IDs and object-storage keys, not payloads — queues cap message sizes (SQS 256 KB) and big blobs belong in storage anyway.
  • Don't demand FIFO without a reason — ordering costs throughput; most AI jobs are order-independent.
Interview corner
When would you make an API asynchronous, and what does the client experience?

When work is long (> a few seconds), bursty beyond processing capacity, or depends on flaky/throttled downstreams. The API validates, persists a job record, enqueues, and immediately returns 202 with a job ID; the client polls a status endpoint or receives a push (websocket/webhook) on completion. Users get instant acknowledgment and a progress bar instead of a spinner and a timeout — and the backend gets retries, spike absorption, and independent worker scaling.

Queue vs pub/sub topic — what's the actual difference?

A queue delivers each message to one consumer from a competing pool — it distributes work. A topic delivers each event to every subscriber — it broadcasts facts. They compose: publish "order placed" to a topic fanned out to three queues (email, inventory, analytics), each queue processed by its own workers with its own retries/DLQ. One-line version: queues share out tasks; topics announce news.

What is a dead-letter queue and why is it essential?

A side queue that receives messages after N failed processing attempts. Without it, a "poison" message (corrupt input, permanent bug) cycles forever — wasting compute, delaying good messages, and flooding logs. With it, the main line stays healthy, and the DLQ becomes an inspectable inbox of failures: alarm on depth > 0, diagnose, fix the cause, replay the messages. It's the difference between a self-healing system and a silently degrading one.

Exactly-once delivery — possible? How do you handle duplicates?

True exactly-once delivery is effectively impossible in distributed systems (a worker can complete work and crash before acknowledging — the system must redeliver or risk loss; queues choose redeliver = at-least-once). The achievable goal is exactly-once effect: idempotent processing. Techniques: an idempotency key checked before work, upsert-style writes keyed by job ID, and conditional operations ("create if not exists"). Saying "at-least-once delivery + idempotent consumers" is the industry-standard answer.

How do you scale a worker fleet, and how is that different from scaling an API?

APIs scale on request-pressure signals (concurrency, CPU, latency) because clients wait. Workers scale on queue depth (or age of oldest message) because that measures accumulated demand: target e.g. 100 messages per worker, scale 0→N and back. Add a max bound (cost/GPU quota), and for spot-based GPU workers rely on visibility-timeout replay to survive evictions. Mentioning depth-based autoscaling + spot workers + idempotency in one breath is a very strong systems answer.

Getting traffic to your app — DNS, load balancers, gateways, CDN

The journey from a user typing your URL to your container answering — every hop explained, plus the GenAI special requirement: streaming. Contains the single most-asked interview question in existence.

~20 min read
1

The concept, in detail

The full journey of one request (learn to narrate this)

  1. DNS lookup. The browser must turn chat.acme.com into an IP address. It asks its resolver, which walks the DNS hierarchy (root → .com → your domain's name servers) and returns the answer, cached for the record's TTL (time-to-live, e.g. 300s). Record types worth knowing: A (name → IP address), CNAME (name → another name, e.g. → your load balancer's hostname).
  2. TCP + TLS. The browser opens a connection to that IP and performs the TLS handshake — the server proves its identity with a certificate, and both sides agree on encryption keys. Result: the padlock; nobody in between can read or tamper. Clouds issue and renew certificates automatically (ACM / Google-managed certs / App Service certs) — free, no OpenSSL wrestling.
  3. Load balancer. The IP the user reached isn't your app — it's the stable front door. The LB picks one healthy backend copy and forwards the request.
  4. Your app (tab 3) does its work — DB reads (tab 5), LLM calls (tab 8) — and the response streams back through the same path.

Load balancers, properly

  • Layer 4 vs layer 7 (the "layers" are network-stack levels): an L4 LB forwards raw TCP connections — fast, dumb, protocol-agnostic. An L7 LB understands HTTP — it can route by path (/api → backend A, /admin → backend B), inspect headers, terminate TLS, and retry. Default to L7 (ALB / Cloud Load Balancing HTTP / Application Gateway) for web apps; L4 (NLB) for raw performance or non-HTTP protocols.
  • Health checks: the LB probes each backend (GET /healthz every few seconds); failing copies are pulled from rotation, and autoscaling replaces them. Keep the endpoint instant and dependency-light — a health check that calls your LLM turns provider hiccups into full outages.
  • Distribution: round-robin or least-outstanding-requests. Sticky sessions (pinning a user to one backend) exist for stateful legacy apps — you shouldn't need them, because your app is stateless (tab 3); mentioning that unprompted is a good signal.
  • Idle timeouts: LBs kill silent connections (often ~60s default). Long LLM generations that stream nothing for minutes get cut mid-answer — raise the timeout and/or stream tokens (below) so the connection is never "silent".

API gateway — the receptionist with a rulebook

In front of APIs specifically, a gateway adds what an LB doesn't: API keys and auth checks, rate limiting and quotas per key/user, request validation, path-based routing to services, response caching, and usage analytics. The standard rate-limit mental model is the token bucket: each user's bucket refills at (say) 1 token/sec up to a burst capacity of 5; each request spends a token; empty bucket → 429. For GenAI products the gateway is literally your wallet's bodyguard — every request it declines is LLM tokens not purchased. It's also where API versioning lives (/v1/, /v2/) so you can evolve without breaking old clients.

CDN — the worldwide photocopy network

A content delivery network operates hundreds of edge locations (tab 1). Static files — your frontend bundle, images, generated videos — are cached at edges near users: a visitor in Jaipur gets files from an Indian edge in ~20ms instead of Virginia in ~250ms, and your origin (bucket/servers) is hit once per file per edge instead of once per user. CDN egress is also cheaper than raw egress (tab 4). Mechanics to know: the cache key (URL + chosen headers) decides what counts as "the same file"; TTL / Cache-Control headers decide freshness; invalidation evicts stale files after a deploy — or better, use hashed filenames (app.9f3c2.js) so every version is a new URL and caching becomes infinite + conflict-free. CDNs can also front dynamic APIs (TLS terminated near the user + optimized backbone to origin) — modest wins, sometimes free ones.

(5) The response streams back; the browser parses HTML and fires further requests for assets, ideally served from CDN edges. Bonus flourish: mention where 502/503/504 would each arise in that chain — interviewers light up.

L4 vs L7 load balancing — difference and when each?

L4 balances at the transport layer: forwards TCP/UDP by IP+port, no idea what HTTP is — minimal latency, millions of connections, any protocol. L7 understands HTTP: it can terminate TLS, route by path/host/header, retry idempotent requests, and give per-route metrics. Web/API apps → L7 by default; L4 for raw TCP protocols, extreme throughput, or when you need to pass encrypted traffic through untouched.

Users report 502s, then later 503s, then 504s. What does each tell you?

502 bad gateway: the LB reached a backend and got a broken/refused response — app processes crashing or restarting (bad deploy, OOM kills). 503 no backend available: every copy unhealthy or at capacity, or scaled to zero — look at health checks, autoscaling limits, quota. 504 timeout: backends alive but too slow — a hung dependency (DB pool exhausted, LLM latency) exceeding a timeout in the chain. Same family, three different investigations — naming that mapping crisply is exactly what's being tested.

How does a CDN make things faster AND cheaper?

Faster: content is served from an edge ~10–50ms from the user instead of a region ~100–300ms away, and TLS handshakes terminate at the edge too. Cheaper: each file leaves your origin roughly once per edge instead of once per user, and CDN egress rates undercut raw internet egress. Add the operational detail — hashed filenames make cache invalidation a non-event — and the answer is complete.

Design a rate limiter for an AI API. What are the pieces?

Algorithm: token bucket per identity (API key/user) — refill rate = sustained allowance, bucket size = burst allowance; empty → 429 with a Retry-After header. State: counters in a fast shared store (Redis) so all app copies enforce the same limits; or push it to the API gateway and configure usage plans. AI twist: consider limiting by tokens consumed, not just request count — 1 request can cost 100× another — and tier limits by plan. Mention graceful client behavior too: exponential backoff + jitter on 429.

Why are sticky sessions usually a smell? When are they legitimate?

Stickiness pins users to one backend copy — which breaks the interchangeable-copies model: that copy's death logs users out, load skews, deploys get complicated. It usually exists to hide in-memory session state, and the real fix is externalizing state (Redis sessions / signed tokens — tab 3). Legitimate uses: legacy apps you can't change, and long-lived stateful connections like WebSockets, where "stickiness" is inherent to the socket.

The concept, in detail

What an LLM actually does (enough to reason about systems)

A large language model is a neural network trained on vast text to do one deceptively simple thing: predict the next token. A token is a chunk of text — roughly ¾ of an English word ("understanding" might be under+standing). Generation is a loop: feed in everything so far → model outputs probabilities for the next token → pick one → append → repeat. Two consequences you can now derive yourself:

  • Streaming is natural, not a feature bolted on — tokens exist one at a time anyway, so sending them as they're born (tab 7's SSE) costs nothing extra.
  • Output costs more than input. Reading the prompt (prefill) processes all input tokens in one parallel pass — GPU-friendly, fast. Generating (decode) runs the whole model once per output token, sequentially. More GPU-seconds per token → higher price per output token (typically 3–5×) and why long answers, not long prompts, dominate latency.
  • During decode the model keeps a working memory of everything processed so far — the KV cache — in GPU VRAM. Providers exploit this: if many requests share the same long prefix (your system prompt + docs), it can be computed once and reused — that's prompt caching, sold at a steep discount (often ~90% off cached input). Design prompts static-prefix-first to harvest it.

The request vocabulary

  • Context window — the maximum tokens per request (input + output), i.e., the model's working memory. Modern models: 128K–1M+ tokens. Everything must fit: instructions, retrieved docs, chat history, the answer.
  • System prompt — standing instructions setting role and rules ("You are Acme's support agent. Answer only from provided context."). Sent with every request; the model has no memory between requests — your app supplies history each time (that's why chat storage, tab 5, exists).
  • Temperature — randomness dial: 0–0.3 for extraction/classification/factual work (near-deterministic), 0.7–1.0 for creative variety.
  • Max output tokens — a hard cap on answer length: both a safety rail and a cost rail.
  • Structured output / JSON mode — instruct (or constrain) the model to emit valid JSON matching a schema, so your code can parse responses reliably. Essential for anything programmatic.
  • Tool calling (function calling) — you declare functions ("get_order_status(order_id)"); the model can respond with a request to call one; your code executes it and returns the result; the model continues with real data. An agent is exactly this in a loop: model reasons → picks a tool → observes the result → repeats until the goal is met. Demystified, "agentic AI" is a while-loop around tool calling — a great one-liner to own in interviews.
  • Embeddings API — same providers, tiny prices: text in → vector out (tabs 5 & 9 run on this).

The model landscape — how to talk about it like a practitioner

  • Proprietary API models (Claude, GPT-4o/o-series, Gemini): top quality, pay per token, weights never leave the provider.
  • Open-weights models (Llama, Mistral, Qwen, Phi…): downloadable weights you may self-host (tab 2/10 economics) — or, the best of both, rent hosted open models per-token from Bedrock/Vertex/Foundry.
  • Every provider sells a ladder: small-fast-cheap → mid → frontier. Price spreads are 10–60× between rungs. The core engineering skill of the GenAI era is routing each task to the cheapest rung that passes your quality bar — measured by evals (tab 9), not vibes.
  • Multimodal: modern flagships accept images (and increasingly audio/video) as input; separate model families generate images (Nova Canvas, Imagen, DALL·E/GPT-image) and video (Veo, Sora-class). Speech has dedicated services: transcription (Amazon Transcribe / Google Speech-to-Text / Azure AI Speech, plus Whisper-family) and synthesis (Polly / Text-to-Speech / Azure Speech).

Buying shapes: on-demand, batch, provisioned

  • On-demand — pay per token, shared capacity, per-model-per-region quotas (requests/min and tokens/min). Default.
  • Batch — submit a file of thousands of requests, results within ~hours, typically ~50% cheaper. Perfect for nightly summarization, bulk embedding, evaluations (pairs beautifully with tab 6's queues).
  • Provisioned throughput (Bedrock provisioned, Azure PTU) — reserve dedicated model capacity for a fixed hourly fee: guaranteed throughput and steadier latency for serious production scale; the "reserved instance" idea applied to AI.
  • Guardrail add-ons (Bedrock Guardrails, Azure AI Content Safety, Vertex safety filters) — managed input/output screening: topic blocks, PII masking, harm categories — cheaper than building your own moderation layer.

The cost-estimation walkthrough (interviews love this)

Support bot, 10,000 conversations/day, avg 6 turns. Per turn: system prompt+context ≈ 2,500 input tokens, answer ≈ 300 output tokens. Interview corner
What is a token, and why do providers bill by it?

The model's unit of text — subword chunks from a fixed vocabulary; ~¾ of an English word on average. Compute scales with tokens processed: the prompt is one parallel prefill pass, and each output token is a full sequential model pass — so tokens are literally the meter of GPU work. That's also why output tokens cost several times input, and why latency ≈ time-to-first-token + output_tokens × per-token time.

Big context windows are huge now. Why still bother with RAG?

Four reasons: cost — shipping 500K tokens of documents with every request dwarfs retrieving 3K relevant ones; latency — prefill time grows with input size; quality — models demonstrably attend worse to the middle of very long contexts ("lost in the middle"), while focused context sharpens answers; freshness/scale — corpora change hourly and can exceed any window. Long context and RAG compose: retrieve generously, then let a big window hold it comfortably. (Full treatment: tab 9.)

Your LLM bill must drop 10×. Name your levers, in order.

(1) Model right-sizing/routing — send the 80% of easy traffic to a model 10–30× cheaper; keep the flagship for the hard 20%. (2) Prompt caching — restructure prompts static-first; cached input is ~90% off. (3) Trim context — tighter retrieval top-k, summarized chat history, shorter system prompts. (4) Cache responses — exact and semantic (embedding-keyed) caching for repeated questions. (5) Batch API for all offline work (~50% off). (6) Cap output tokens. (7) At sustained scale: provisioned capacity pricing, or evaluate self-hosting a fine-tuned small model (tab 10). Ordered, measurable, and it shows you know caching exists at three different layers.

On-demand vs provisioned throughput (PTU) — how do you decide?

On-demand: pay per token, zero commitment, but shared capacity — quotas and occasional latency variance. Provisioned: fixed hourly fee for dedicated capacity — predictable throughput/latency, economical only above high steady utilization. Decide like reserved VMs: measure sustained tokens/min; if you'd keep provisioned units busy (rule of thumb: ~60–70%+ utilization) or you have hard latency SLOs, provision the baseline and burst on-demand.

How does tool calling work under the hood? And define "agent" without buzzwords.

You send the model a list of function declarations (name, description, JSON schema). The model, when it decides a call is needed, emits a structured "call X with these arguments" message instead of prose. Your code — not the model — executes the function, appends the result to the conversation, and re-invokes the model, which now answers with real data. An agent is that loop with autonomy: reason → choose tool → act → observe → repeat until done, with the loop, tool permissions, and stop conditions owned by your application. The model never executes anything itself — an important safety point interviewers like to hear.

How would you make an app resilient to an LLM provider outage?

Layers: timeouts + retries with backoff for blips; a circuit breaker so a hard-down provider fails fast instead of hanging threads; a fallback model — ideally a second provider or region behind your internal LLM interface — accepting a quality dip over an outage; degrade gracefully (serve cached/semantic-cached answers, or queue requests for later); and monitor provider error rates so you flip before users notice (tab 11). Multi-provider abstraction from day one makes all of this a config change.

The concept, in detail

The problem RAG solves

An LLM is a brilliant new employee who has read the public internet up to a cutoff date — and none of your company's documents. Ask about your refund policy and it will either decline or, worse, hallucinate: produce a fluent, confident, wrong answer (models are trained to continue text plausibly, not to know what they don't know). Analogy
RAG is an open-book exam with a good librarian. The librarian (retrieval) fetches the five most relevant pages; the scholar (LLM) answers only from those pages, quoting them. No librarian → the scholar improvises from memory (hallucination). Bad librarian → confident answers from the wrong pages. Most "the AI is wrong" bugs are librarian bugs.

Stage 1 — Ingestion (where products are quietly won or lost)

  • Parsing: real documents are messy — PDFs with two columns, tables, headers, scanned pages. Naive text extraction produces scrambled garbage, and everything downstream inherits it. The clouds sell managed document parsers with OCR (optical character recognition — reading text from images): Amazon Textract · Google Document AI · Azure Document Intelligence — they return structured text, tables, and layout. Budget real effort here.
  • Cleaning: strip boilerplate (headers/footers/nav), deduplicate near-identical docs, attach metadata (source, tenant, date, language, version).
  • Chunking: split documents into retrievable pieces. Why not whole docs? Too big (context budget) and too diluted (a 50-page doc's vector is an average of 50 topics — matches nothing well). Why not sentences? Too little context to answer from. Strategies:
    StrategyHowVerdict
    Fixed-sizeEvery N tokens, with overlapBaseline; fine for uniform text
    Recursive / structure-awareSplit at headings → paragraphs → sentences until size fitsThe sensible default — respects natural boundaries
    SemanticSplit where embedding similarity between sentences dropsBetter coherence, costlier to build
    Layout-awareKeep tables/sections intact from the parserEssential for forms, contracts, invoices
    Typical size 300–800 tokens with 10–15% overlap so sentences straddling a boundary survive in one piece. A power move: store small chunks for precise matching but hand the model the surrounding section for answering ("small-to-big" retrieval).
  • Embedding + storing: embed each chunk (tab 8) and store vector + raw text + metadata (tab 5). Keep the raw text forever — every embedding-model upgrade means re-embedding everything.

Stage 2 — Retrieval (the librarian's craft)

  1. Embed the query with the same model used at ingestion.
  2. Filter by metadata first — tenant (privacy wall!), doc type, date range, language.
  3. Vector search top-k (start k=5–10) — semantic matches regardless of wording.
  4. Hybrid: add keyword search (BM25 — the classic relevance algorithm) and merge rankings with RRF (reciprocal rank fusion — items ranked well by either list rise). Why: pure vectors fumble exact identifiers — "error 4012", "PB-30 plan", people's names. Hybrid is the pragmatic production default.
  5. Rerank (optional but potent): a cross-encoder reranker reads query+chunk together and scores true relevance — far more accurate than vector distance, far too slow to run on millions. So: vectors fetch 50 candidates fast → reranker orders them → keep the best 5. (Managed: Cohere Rerank on Bedrock, Vertex Ranking API, Azure AI Search semantic ranker.)
  6. Query rewriting: user queries are lazy ("what about pricing?"). An LLM pre-step rewrites them using chat history ("Acme Pro plan pricing 2026") — cheap, high-leverage. Related fancy tricks worth name-dropping honestly: HyDE (embed a hypothetical answer instead of the question), multi-query (retrieve for several phrasings), agentic RAG (the model decides when/what to search, possibly multiple rounds), GraphRAG (retrieve through a knowledge graph of entities for "connect the dots" questions).

Stage 3 — Generation (the scholar's instructions)

System: You are Acme's support assistant. Answer ONLY from the provided context.
        Cite sources as [1], [2]. If the context doesn't contain the answer,
        say "I don't know — contact support@example.com". Never invent policy.

Context:
[1] (refunds-policy.md, updated 2026-05) "Refunds are processed within 7 days..."
[2] (billing-faq.md) "Duplicate charges are auto-reversed within 48 hours..."

User: My card was charged twice — will I get my money back?

Details that matter: put the most relevant chunks first and last (models attend best to edges — "lost in the middle"); include doc dates so the model can prefer fresh policy; keep the refusal path explicit; low temperature. In the UI, render the citations as links — trust is the product.

Evaluation — the difference between a demo and a product

Build a golden set: 30–100 real questions with known-correct answers and source docs. Then measure two layers separately:

  • Retrieval metrics: hit rate (is a correct chunk in the top-k?) and MRR (mean reciprocal rank — how high does the first correct chunk appear: rank 1 → 1.0, rank 3 → 0.33, averaged). Cheap, fast, run on every change.
  • Answer metrics: groundedness/faithfulness (is every claim supported by the retrieved context?), relevance (does it answer the question?), correctness vs the golden answer. Scored by humans on samples and by LLM-as-judge — a strong model grading with a rubric — at scale (calibrate the judge against human labels before trusting it).

Debugging rule with the eval numbers in hand: low hit rate → fix retrieval (chunking, hybrid, rewriting); high hit rate but bad answers → fix generation (prompt, ordering, model). This two-layer diagnosis is the single most senior-sounding thing you can say about RAG.

Keeping it fresh

Documents change. Wire ingestion event-driven (tab 6): doc updated in storage → event → re-parse, re-chunk, re-embed that document, upsert by stable chunk IDs, delete removed docs' chunks. A nightly reconciliation sweep catches strays. Staleness is a silent quality killer — and "how do you keep the index fresh?" is a beloved follow-up question.

Interview corner
Walk me through a production RAG architecture end-to-end.

Ingestion: docs land in object storage → events (queue) trigger parse (Textract-class OCR) → clean → structure-aware chunking (~500 tokens, overlap) → embed → upsert vectors + text + metadata (tenant, source, date) into pgvector/a vector store, stable IDs for re-ingestion. Serving: rewrite the query with chat history → metadata filter (tenant) → hybrid retrieval (vector + BM25, RRF-merged) top-50 → cross-encoder rerank → top-5 into a cited, refusal-capable prompt → LLM, streamed to the user with sources. Around it: golden-set evals in CI (hit rate/MRR + judge-scored groundedness), event-driven freshness, answer→chunk lineage logs. That's a complete senior answer in five breaths.

How do you choose chunk size? What breaks at the extremes?

Too small (a sentence): matches precisely but lacks context to answer from — the model gets fragments. Too big (pages): the chunk's embedding averages many topics — matches nothing well — and stuffs the prompt with noise. Sweet spot is usually 300–800 tokens, split at natural boundaries with ~10–15% overlap, then validated empirically: sweep sizes against the golden set's hit rate. Bonus: mention small-to-big retrieval (match small, feed the model the surrounding section).

Why hybrid search? Give a concrete failure of pure vector search.

Embeddings compress meaning, not spelling — rare exact tokens lose to semantic neighbors. Query "error 4012": vector search happily returns chunks about error 4013 and generic payment failures ("semantically similar"!), while the one chunk literally containing "4012" may miss the top-k. BM25 keyword search nails exact identifiers; vectors nail paraphrases ("charged twice" → "duplicate payment"). RRF merges the two rankings so either strength wins. Production default in any domain with codes, names, or SKUs.

How do you evaluate a RAG system? Be specific.

Two layers, measured separately on a golden set of real Q&A pairs. Retrieval: hit rate@k (correct chunk present?) and MRR (how high?) — cheap, run in CI on every change. Generation: groundedness/faithfulness (every claim supported by context?), answer relevance, correctness — human-labeled samples plus a calibrated LLM-as-judge for scale. Then the diagnosis rule: low hit rate → fix chunking/hybrid/rewriting; high hit rate + bad answers → fix prompt/ordering/model. In production, add online signals: thumbs, deflection rate, "I don't know" rate, and per-answer chunk lineage for postmortems.

How do you reduce hallucinations in a RAG product?

Stack defenses: retrieve better (hybrid + rerank — most hallucination is compensation for missing context); instruct explicitly ("answer only from context; say I-don't-know otherwise") at low temperature; require citations, and optionally verify them post-hoc (a checker pass that drops unsupported sentences); refuse below a retrieval-confidence threshold rather than guessing; measure groundedness continuously so regressions surface. And the product-level honesty: show sources, so users can verify — you'll never reach zero, so design for verifiability.

Scale: 10 million documents, 50 tenants, hourly updates. What changes vs the toy version?

Ingestion becomes a real pipeline: queued, parallel workers, batch embedding APIs (half price), idempotent upserts by stable chunk ID, per-doc status tracking and reconciliation. Storage: a vector store built for scale (partitioned/sharded HNSW — dedicated engines or OpenSearch/Vertex Vector Search territory), tenant as a first-class partition/filter. Retrieval latency: tuned ANN parameters, caching of hot queries, rerank only the top candidates. Freshness: event-driven per-document re-index, not full rebuilds. Cost: embedding spend tracked per tenant; retrieval and generation metered (tab 11). The theme interviewers want: everything becomes incremental, idempotent, and measured.

  1. Prompt engineering (minutes, ~free): better instructions, a few worked examples in the prompt ("few-shot"). Solves most problems; exhaust it first.
  2. RAG (days): supplies your knowledge at request time (tab 9). Facts change? Update documents — never retrain.
  3. Fine-tuning (days–weeks, real money): continue training an existing model on your example pairs to change its behavior — tone, format discipline, domain shorthand, narrow-task skill. The killer use: making a small cheap model perform like a big one on ONE narrow task.
  4. Pre-training from scratch (months, tens of millions of dollars, thousands of GPUs): building a foundation model. Not your problem — but knowing that instruction-tuned chat models are built by pre-training on internet text, then instruction-tuning, then preference-tuning (RLHF/DPO — aligning outputs to human-preferred answers) earns credibility.

What "training" actually is (the 5-minute honest version)

A model is millions/billions of numbers (parameters/weights). Training: show it an input, let it predict, measure how wrong it was with a loss number, then nudge every weight slightly in the direction that reduces the loss — gradient descent. Repeat over the dataset many times (each full pass = an epoch) and the weights gradually encode the patterns.

Analogy
Walking downhill in fog: you can't see the valley (perfect weights), but you can feel the slope under your feet (the gradient) and keep stepping downhill (reducing loss). The learning rate is your stride — too big and you overshoot the valley, too small and you walk forever.

Overfitting — the concept interviews test most: train too long or on too little data and the model memorizes the training examples instead of learning the pattern — like a student who memorizes last year's question paper and fails a fresh exam. Detection: split data into train / validation / test sets; when training loss keeps improving but validation loss starts worsening, you're memorizing — stop (early stopping), get more/better data, or regularize. The test set is touched exactly once, at the end, for the honest final number.

The fine-tuning menu

  • Full fine-tuning: update all weights. Maximum change, maximum cost (needs training-grade GPU memory), risks "catastrophic forgetting" of general skills.
  • LoRA (low-rank adaptation) — the modern default: freeze the base model; train tiny adapter matrices (often <1% of parameters) that steer it. 10–100× cheaper, one base model can host many task-adapters, and quality is usually close to full FT. QLoRA = LoRA on a quantized (4-bit) base — fine-tune a 7B model on a single 24 GB GPU. In the hosted services (Bedrock/Vertex/Azure OpenAI fine-tuning), adapter-style tuning is what's happening behind the "create fine-tune job" button.
  • Distillation: use a big "teacher" model to label thousands of examples, then fine-tune a small "student" on them — buying the teacher's judgment at the student's price. This is the workhorse pattern behind most "we cut LLM costs 90%" stories (worked example below).

Data — where fine-tunes are won

Format: instruction pairs (input → ideal output), typically JSONL chat format. Rules that matter more than any hyperparameter: quality beats quantity (500–5,000 clean, consistent, representative examples beat 50,000 noisy ones); deduplicate; make outputs exactly the style/format you want (the model will copy everything, including your labelers' bad habits); keep validation/test sets that never touch training (and never let test data leak into training — "contamination"); check the base model's license allows commercial fine-tuning, and the teacher model's terms allow distillation.

What an ML platform actually gives you

SageMaker, Vertex AI, and Azure ML bundle the same four capabilities:

  • Hosted notebooks — Jupyter in the browser, near your data, with GPUs on tap.
  • Managed training jobs — "run this script on 4× A100 for as long as it takes, then release the machines." GPUs exist only for the job's duration; add checkpointing (save weights every N steps to object storage) and you can run on spot GPUs at 60–90% off — eviction just resumes from the last checkpoint. Multi-GPU training is usually data parallelism: each GPU holds a model copy, processes a different data slice, and they average their gradient updates each step.
  • Experiment tracking + model registry — which data + config produced which metrics, and versioned model artifacts (MLflow is the common open standard; W&B the popular SaaS). Without this you cannot reproduce your own best model — a surprisingly common real-world failure.
  • Deployment endpoints — turn a registry model into an autoscaled HTTPS API with instance choice, A/B traffic splits, and monitoring.

Serving a model you own

Self-hosting an open-weights model means: pick GPU(s) by VRAM (tab 2 math), run a serving engine — vLLM is the standard name: it batches concurrent requests continuously and manages KV-cache memory cleverly (PagedAttention) for several-fold throughput gains — usually with quantization (4/8-bit) to shrink footprint. Wrap it in a container behind a queue or endpoint. Hard truths to say out loud: GPU autoscaling is slow (minutes to boot + load weights — keep a warm floor, scale on queue depth), utilization discipline decides economics, and below serious sustained volume, per-token APIs beat self-hosting — the honest breakeven framing wins interviews.

The MLOps loop (the diagram to narrate)

Data → train → evaluate → register → deploy → monitor → drift → retrain. Production models degrade not because weights rot but because the world shifts (drift): new products, new slang, new ticket types. Monitor live quality (sampled evals, confidence distributions, business metrics); schedule periodic retrains with freshly labeled data; keep the previous model one click away (registry + endpoint versioning) for instant rollback.

Key considerations

  • Fine-tune last, not first — only after prompting + RAG plateau, and only with an eval set that proves the gap. "What did you try before fine-tuning?" is a screening question.
  • It's for behavior, not facts — knowledge goes stale the day training ends and can't be cited; that's RAG's job. (Combo is common: RAG for facts + a small fine-tune for voice/format.)

  • Prefer hosted fine-tuning first (Bedrock/Vertex/Azure OpenAI) — no GPU wrangling; drop to LoRA-on-your-own-GPUs for open models, data control, or unit economics.

  • Plan the serving story before training — a model you can't serve within latency/cost budgets is a science project; measure quantized variants.

Interview corner
Fine-tuning vs RAG — the definitive comparison.

RAG injects knowledge at request time: current, citable, per-tenant, updated by editing documents — right for facts and changing corpora. Fine-tuning changes parameters: behavior, tone, output format, narrow-task competence — right for style discipline and for making small models match big ones on one task. Fine-tuning is wrong for facts (stale, uncitable, retrain-to-update); RAG is wrong for tone/format. They compose: RAG for content + fine-tuned small model for the task. Deciding evidence: an eval set showing prompting+RAG plateaued below target.

What is LoRA and why did it change the economics of fine-tuning?

Low-rank adaptation: freeze the base model's weights and train small low-rank matrices inserted into key layers — typically <1% of parameters. Effects: training fits on modest GPUs (QLoRA: a 7B base quantized to 4-bit fine-tunes on one 24 GB card), training is 10–100× cheaper, adapters are megabytes (store many task-personalities per base model, swap at load), and quality lands near full fine-tuning for most tasks. It moved fine-tuning from "lab with a GPU cluster" to "afternoon with a credit card".

What is overfitting? How do you detect and fix it?

The model memorizes training data instead of learning the generalizable pattern — great training scores, poor real-world scores (the student who memorized last year's paper). Detect: validation loss/metrics diverge from training (train keeps improving, validation worsens). Fix: more/more-diverse data, fewer epochs (early stopping at the validation minimum), regularization, smaller model or lower LoRA rank, and rigorous train/val/test hygiene with the test set used exactly once.

Estimate the cost of fine-tuning — what drives it?

Hosted APIs: priced per training token — (dataset tokens × epochs) × rate; a few thousand short examples for 3 epochs on a small model is typically tens of dollars, not thousands. Self-managed: GPU-hours × rate — e.g., LoRA on an 8B model, 5k examples, ~2–4 hours on one A100 ($3–5/hr) ≈ $10–20 on demand, less on spot. The real costs people forget: labeling/cleaning the data, running evals, and the engineer's time. Answering with the formula + a worked number + "data prep dominates" is the complete answer.

How would you serve an open-source model in production?

Size GPUs from VRAM math (params × bytes/param + KV-cache headroom; quantize to fit smaller cards). Run vLLM (continuous batching, paged KV cache) in a container; front with a queue or endpoint; scale on queue depth/concurrency with a warm floor because GPU cold starts are minutes (boot + weight loading). Watch utilization — idle GPUs destroy the economics — and close with the breakeven honesty: below sustained high volume, per-token APIs are cheaper and simpler; self-hosting wins on volume, data control, or a fine-tuned model APIs can't serve.

What is distillation and when is it the right play?

Transferring a big teacher model's competence to a small student: the teacher labels a large task-specific dataset (cheaply, via batch APIs); the student fine-tunes on it; you serve the student at a fraction of the cost/latency, often with a teacher-fallback for low-confidence cases. Right when: one narrow, high-volume task (classification, extraction, routing) currently running on an expensive general model. Caveats: quality ceiling ≈ teacher's on that task; check the teacher provider's terms permit training on its outputs; keep an eval set to verify the student holds up on fresh data.

The concept, in detail

Environments, configuration, secrets

Professionals run at least two full copies of the system: staging (the rehearsal, on production-like everything) and production. The same container image runs in both — only configuration differs, injected as environment variables. Secrets (API keys, DB passwords) never live in code or images: they live in a secrets manager (Secrets Manager / Secret Manager / Key Vault) and are injected at deploy time, rotated without redeploying, and audited. Feature flags — config switches that turn features on per user/percentage — let you ship code dark and light it up gradually (and kill it instantly without a deploy).

Infrastructure as code (IaC)

Clicking around the console works once — then you can't reproduce, review, or roll back your own infrastructure. IaC writes infrastructure as declarative files — "one Cloud Run service, one Postgres, one queue, wired so" — that a tool applies: Terraform (the cross-cloud standard), CloudFormation/CDK (AWS-native), Bicep (Azure-native). Payoffs: staging is provably identical to prod, changes go through code review, disaster recovery = re-apply the files, and the files ARE the documentation. Interview line that lands: "if it's not in code, it doesn't exist — console clicking is for exploration only."

CI/CD — the assembly line

CI (continuous integration): every push automatically runs tests, linters, and builds the container — bugs die minutes after birth. CD (continuous delivery/deployment): the built artifact auto-deploys to staging, then production, with gates. Releases become boring, frequent, and reversible — which is the whole point. GitHub Actions is the de-facto standard on all three clouds. The deployment strategies are a favorite interview topic:

StrategyHowTrade-off
RollingReplace copies a few at a timeDefault, zero-downtime; both versions briefly coexist
Blue-greenFull new fleet (green) beside old (blue); flip 100% of traffic at onceInstant cutover AND instant rollback (flip back); costs 2× capacity during deploys
CanarySend 1% → 10% → 50% → 100% of traffic to the new version, watching metrics between stepsLimits blast radius to the canary %; needs good metrics + patience; the standard for risky changes

For AI apps, canary deploys apply to prompts and models too — route 5% of traffic to the new prompt/model, compare quality + cost + latency, then promote. Version prompts like code; a prompt change is a deploy.

Autoscaling — elasticity in practice

Pick the signal that truly measures demand: CPU% for compute-bound services, concurrency/requests-per-copy for I/O-bound API backends (most GenAI apps — tab 3), queue depth for workers (tab 6). Then set the floor and ceiling deliberately: min instances = your latency promise (warm copies, no cold starts); max instances = your blast-radius and budget cap. Two failure modes to name: flapping (scale up/down oscillation — fix with cooldowns) and scaling on the wrong signal (CPU-based scaling never triggers for an app that's just waiting on LLM APIs while requests pile up).

Reliability — the professional vocabulary

  • SLI / SLO / SLA: an SLI is a measured indicator (p95 latency, error rate, availability %). An SLO is your internal target for it ("99.9% of chats answer within 5s"). An SLA is the contractual promise to customers, with penalties, always looser than the SLO. The error budget is 100% minus the SLO — the amount of failure you're allowed; budget left → ship fast; budget burned → freeze features, fix reliability. This framing (from Google's SRE practice) is catnip in interviews.
  • Timeouts everywhere: every network call gets a timeout; without one, a hung dependency silently consumes threads until the whole service stalls.
  • Retries with exponential backoff + jitter: retry transient failures at growing, randomized delays. Without backoff+jitter, a thousand clients retrying in sync become a retry storm that re-kills the recovering service.
  • Circuit breaker: after N consecutive failures to a dependency, stop calling it for a cooldown (fail fast, serve fallbacks), then probe gently. Protects both sides.
  • Graceful degradation, AI edition: provider down? Fall back to a second model/provider (tab 8); serve semantic-cached answers; queue requests for later; or honestly say "assistant is busy" — anything but a spinner into a 504.
  • DR (disaster recovery): know RTO (how fast you must be back) and RPO (how much data you may lose). Multi-AZ (tab 1) is the default answer; multi-region — active-passive with replicated data, or active-active — is the expensive next tier justified only by strict RTO/RPO. Backups you haven't test-restored don't count.

Observability — logs, metrics, traces (+ the AI layer)

  • Logs — the diary. Emit structured JSON (machine-queryable), one event per line, each carrying a correlation/request ID so one user's journey can be stitched across services.
  • Metrics — the dials. The classic trio for any service is RED: Rate (req/s), Errors (by status code — tab 7's table), Duration (p50/p95/p99 latency — always percentiles, never averages: the average hides the pain your slowest 5% feel).
  • Traces — the journey map: one request's timeline across hops ("4.2s total: 80ms DB, 3.9s LLM, rest app") — the tool that ends "which part is slow?" debates. OpenTelemetry is the standard plumbing name.
  • LLM observability — the new layer: log per-call model, prompt version, tokens in/out (both are in every response — tab 8), cost, latency, cache hit, and quality signals (thumbs, refusals, judge scores). Purpose-built tools: Langfuse (open-source) / LangSmith; cloud-native: Bedrock/Vertex/Foundry each expose usage metrics into CloudWatch/Cloud Monitoring/Azure Monitor.
  • Alerts: page on symptoms users feel (error rate, p95, DLQ depth, budget burn), not on every twitch; every alert must be actionable or it trains you to ignore alerts.

Cost — FinOps, with the GenAI twist

Classic cloud cost tools: budgets + alerts (set day one), tags/labels on every resource (team/product/env) so the bill decomposes, rightsizing, spot, commitments (tab 2), egress hygiene (tab 4). The GenAI twist: tokens are usually the #1 line item and they scale per message, so cost is an application-level discipline: track unit economics (cost per conversation / per document / per user / per tenant) from your own token logs; cache at three layers (prompt caching, exact response cache, semantic cache — tabs 8 & 5); route to right-sized models; batch offline work; cap output tokens; rate-limit users (tab 7). A GenAI product that doesn't know its cost-per-conversation is a product that hasn't met its margins yet.

Key considerations

  • Budgets + alerts before the first deploy — every cloud horror story begins "we noticed two weeks later".
  • Bound everything: autoscaling max, output-token caps, per-user rate limits, job retry limits — un-capped systems convert bugs into invoices.

Interview corner
Blue-green vs canary deployment — differences and when each?

Blue-green: run a complete new fleet beside the old; flip all traffic at once; rollback = flip back. Simple mental model, instant reversal, but 2× capacity during the switch and the new version meets 100% of traffic simultaneously. Canary: shift a small percentage first, verify real-production metrics (errors, p95, business KPIs), then ramp. Smaller blast radius, richer validation, but needs traffic splitting + good observability and takes longer. Use blue-green for infra-level swaps and simple services; canary for risky app changes — and for AI, canary new prompts/models the same way.

Define SLI, SLO, SLA — and what's an error budget?

SLI: the measured indicator (p95 latency, success rate). SLO: your internal target for the SLI (99.9% success monthly). SLA: the external contract with customers, with remedies, set looser than the SLO. Error budget: 100% − SLO — the failure you may "spend": 99.9% allows ~43 minutes of bad time monthly; budget remaining → ship features aggressively; budget exhausted → stop launches and invest in reliability. It turns "how reliable should we be?" from philosophy into arithmetic.

Why retry with exponential backoff AND jitter? What else protects you from a flaky dependency?

Immediate uniform retries from thousands of clients hammer a struggling service in synchronized waves — a retry storm that prevents recovery. Exponential backoff spaces attempts out (1s, 2s, 4s…); jitter randomizes them so waves de-synchronize. Complete the answer with the full armor: timeouts on every call (no infinite hangs), retry budgets (don't retry forever; only retry idempotent operations), a circuit breaker that fails fast once the dependency is clearly down, and a fallback path (cache, alternate model, honest error). For LLM APIs specifically: respect Retry-After on 429s and buffer bursts behind a queue.

The monthly bill doubled. Walk me through finding out why.

(1) Cost tool first (Cost Explorer / Billing / Cost Management): break the delta down by service, then by tag/label and region — identify the line item that moved. (2) If it's model/token spend: your per-request token logs by tenant/feature/model — find whether it's traffic growth, a fat prompt (context bloat after a change), cache hit-rate collapse, or one abusive key (rate limits!). (3) If compute: autoscaling history (did max-instances save you or was it unbounded?), forgotten GPU VMs, a runaway retry loop (its signature: traffic flat, requests up). (4) If storage/egress: lifecycle rules broken, a new big consumer of downloads. Then fix the class of problem, not just the instance: caps, alerts at 50/80/100%, anomaly detection on. Structure impresses more than any single answer.

What would you monitor in an LLM application? (Name the AI-specific parts.)

Standard RED per endpoint: rate, errors by status code, duration p95/p99 — plus infra basics (instance counts, queue depth, DB health). AI layer: tokens in/out and cost per request (rolled up per feature/tenant/day), time-to-first-token and tokens/sec for streaming UX, provider error/429 rates, cache hit rates (prompt/exact/semantic), and quality signals — user feedback, refusal/"I don't know" rate, sampled LLM-as-judge groundedness scores, plus prompt/model version on every log line so regressions attribute cleanly. Alert on: error spikes, p95 breaches, DLQ depth, budget burn rate, and judge-score drops after deploys.

Explain RTO and RPO. How do they drive architecture?

RTO (recovery time objective): how quickly service must be restored after disaster. RPO (recovery point objective): how much recent data you may lose (the gap between last backup/replica and the failure). They're requirements that price the architecture: nightly backups alone → RPO up to 24h. Continuous replication → RPO near zero. Multi-AZ managed DB failover → RTO of minutes. Warm standby in a second region → RTO minutes-to-an-hour with region-level protection; active-active multi-region → RTO ~zero at maximal cost/complexity. Strong move: ask the interviewer for the RTO/RPO before proposing the design — that's exactly how real architecture works.

How cloud questions are actually asked

Four formats cover ~95% of cloud interviewing:

  4. Debugging / war stories — "the app is slow / the bill doubled / users see 504s". Tested skill: ordered diagnosis (measure → isolate → fix → prevent), which every tab's interview corner has been drilling.

The scenario framework (memorize this skeleton)

  1. Clarify requirements (2 min): users & scale ("how many users/requests/documents?"), latency needs, data sensitivity/residency, budget posture, real-time vs batch. Asking before drawing is itself scored.
  2. Name the flow: walk one request left to right — client → front door (DNS/LB/gateway/CDN) → app (serverless containers) → async split (queue/workers for slow work) → data (object storage / SQL / vectors) → AI (model API) — assigning a concrete service per box, on whichever cloud you know best.
  3. Data model & storage choices: what's a file, what's a record, what's a vector; who owns what.
  4. Scale & failure: what autoscales on what signal; what happens when the model API / a zone / a worker dies.

Chat is synchronous-but-streaming: SSE through gateway/LB with long timeouts. RAG (tab 9): help docs ingested event-driven — storage events → queue → parse/chunk/embed workers → Postgres+pgvector with tenant_id on every chunk; retrieval = tenant filter + hybrid + rerank, top-5, cited, refusal-capable prompt at low temperature. Order questions use tool calling (tab 8): the model requests get_order_status(order_id); the app executes against the orders DB and returns the result. Model routing: small model for greetings/classification, mid-tier for RAG answers; prompt caching on the static prefix; per-request token logging.

Failure & scale: provider outage → circuit breaker + fallback provider + semantic cache; multi-AZ managed DB; workers scale on queue depth; autoscaling max caps the budget. Metrics: p95 time-to-first-token, groundedness score on sampled judge evals, cost/conversation by tenant. Trade-offs to volunteer: pgvector now, dedicated vector DB past ~10M chunks; managed RAG (Bedrock KB / Vertex Search) would ship a week faster at the cost of retrieval control.

Scenario B — "Design a bulk AI image-generation pipeline" (sellers upload 1,000s of product photos → lifestyle images)

Clarify: 2M images/month, ~20 GPU-seconds each, overnight turnaround acceptable, cost is the KPI.

Architecture: pre-signed PUT uploads straight to object storage (tab 4) → batch record in SQL (total/done/status) → one queue message per image (tab 6). Workers: GPU containers (L4-class) on spot VMs/nodes — 60–90% cheaper; interruption-safe because visibility timeout replays in-flight jobs and workers are idempotent (skip if output exists). Autoscale workers 0→N on queue depth with a nightly quota-aware cap. Outputs → storage under outputs/{batch}/, thumbnails via a small function, delivered through CDN with signed URLs; lifecycle rules cool/expire originals. Status: polling endpoint (done/total) or webhook on completion. DLQ + alarm for poison images (corrupt files). The math out loud: 2M × 20 GPU-s ≈ 11,100 GPU-hours/month ≈ 15 spot L4s running continuously ≈ order-of-$3–5k/month — versus 3–4× that on-demand: the spot decision IS the design. Metrics: queue depth/age, GPU utilization, cost per 1k images, DLQ count.

Scenario C — "Our GenAI feature is slow and expensive. Diagnose and fix it."

Measure first (say this first): pull the per-request logs — tokens in/out, model, latency breakdown (trace: app vs LLM time), cache hits, by endpoint. No fixes before data.

Latency, likely culprits in order: (1) no streaming — users wait for full completions: add SSE, perceived latency collapses; (2) giant prompts — 20k-token contexts inflate prefill: trim retrieval top-k, summarize history; (3) oversized model for the task — route easy intents to the small rung; (4) cold starts — set min-instances; (5) sequential tool/RAG steps that could parallelize; (6) missing DB index on the chat-history query (it's always an index, tab 5).

Cost, likely culprits in order: flagship-for-everything (routing = 10–30× on the easy 80%), no prompt caching (static-prefix restructure ≈ 4× on input), context bloat, no response/semantic cache for repeated questions, retries without caps silently multiplying calls, one abusive free-tier key (rate limits), offline jobs not on batch API (2×). Prevent: per-feature token dashboards, budget alerts, output caps, canary any prompt/model change with cost+quality gates (tab 11).

Scenario D — "Migrate an on-prem nightly ML batch job (10 TB data, 6-hour GPU run) to the cloud."

Clarify: deadline pressure? data growth? team skills? Then present the classic ladder: lift-and-shift (same scripts on GPU VMs + object storage; fastest, least cloud-native benefit) → re-platform (data to object storage; job as a container on managed training jobs / batch services with spot + checkpointing; scheduler-triggered — the usual sweet spot) → re-architect (event-driven, incremental processing instead of nightly monolith — only if the business needs fresher outputs). Data migration: first bulk load (offline transfer appliances exist for 10 TB+ — Snowball/Transfer Appliance/Data Box — name-drop then move on), then incremental sync; validate with checksums; run parallel on-prem + cloud for a cycle before cutover. Cost note: spot + rightsizing typically beats on-prem TCO for spiky GPU use; steady 24/7 use is where on-prem competes — showing you know that nuance reads senior.

Rapid-fire question bank

Answer aloud in 30–60 seconds each, then check. Tab references point to the full treatment.

Fundamentals
Vertical vs horizontal scaling — and which does the cloud favor?

Vertical = bigger machine: simple, has a ceiling, usually a restart. Horizontal = more copies behind a load balancer: near-limitless, zero-downtime, but requires stateless design. The cloud favors horizontal — elasticity, per-second billing, and managed LBs make "more small copies" cheap — with vertical as the quick first move for databases. (Tabs 1, 3, 5.)

What does "stateless" mean and why does everyone insist on it?

No request depends on data trapped in one copy's memory/disk; state lives in databases, caches, object storage. Payoff: copies are interchangeable → autoscaling, rolling deploys, and failures become non-events. (Tab 3.)

What's an AZ-level failure story you'd design for?

A building loses power: app copies spread across 2–3 AZs keep serving behind the LB; the managed database fails over to its standby in another AZ in ~a minute; object storage doesn't notice (multi-AZ by design). Cost of this posture: modest (standby DB + spread copies) — it's the production default, not an upgrade. (Tabs 1, 5, 11.)

Capex vs opex — why do CFOs care about cloud?

Cloud converts big upfront hardware purchases (capex, risky, depreciating) into pay-per-use operating spend (opex) that tracks revenue — plus elasticity means you stop paying when demand drops. Counterpoint worth adding: at very steady scale, owned hardware can be cheaper — hence hybrid strategies. (Tab 1.)

Compute, containers, async
Why did containers beat VMs as the unit of deployment?

Same environment everywhere (kills "works on my machine"), megabytes not gigabytes, sub-second starts, hundreds per host, and immutable versioned images that make deploys/rollbacks mechanical. VMs remain the substrate underneath; containers are the packaging. (Tab 3.)

When do you pick Kubernetes over serverless containers?

Many services with complex topology, a platform team to own it, or needs serverless can't express — custom GPU scheduling/bin-packing, sidecars, special networking, multi-tenancy controls. Otherwise Cloud Run/Fargate/Container Apps deliver the same outcomes with ~zero ops. Default serverless; earn your way into K8s. (Tab 3.)

Design rule: when does work go behind a queue?

When it's slower than ~2–3s, bursty beyond capacity, calls throttled dependencies, or must survive worker crashes: enqueue, return 202 + job ID, workers process with retries/backoff, DLQ for poison messages, autoscale on queue depth, idempotent because delivery is at-least-once. (Tab 6.)

What's an idempotency key and when do you need one?

A unique ID for an operation such that repeating it has no extra effect — check "already done?" before executing, or upsert keyed by it. Needed wherever retries/redelivery exist (queues, payment APIs, webhooks) — i.e., everywhere distributed. (Tab 6.)

Data
Where do a user's uploaded PDF, its metadata, and its embeddings each live?

PDF → object storage (bucket/key, pre-signed upload). Metadata (owner, status, size) → relational DB row pointing at the key. Chunk embeddings + text + tenant metadata → vector store (pgvector first). Three stores, three access patterns — one sentence each shows you know why. (Tabs 4, 5, 9.)

Strong vs eventual consistency — give a product example of each.

Strong: account balance after payment — every read must see the write (SQL primary). Eventual: like-counts, follower numbers, analytics — replicas converge in seconds and nobody is harmed by staleness. Design skill = matching the guarantee to the harm of being stale. (Tab 5.)

Why is "just add an index" the most common database fix?

Without an index, filters scan every row — fine at 1k rows, catastrophic at 10M (O(n) growth hidden during development). An index on the filtered/joined column turns scans into lookups. EXPLAIN reveals it; the fix is one DDL statement. (Tab 5.)

What breaks when 500 serverless containers each open DB connections?

Postgres connection limits (each connection = real memory): the pool exhausts, new requests error or hang. Fix: a shared pooler between app and DB — RDS Proxy / pgbouncer / built-in poolers — plus per-container pool caps. A classic serverless+SQL gotcha interviewers fish for. (Tab 5.)

GenAI
Explain RAG in three sentences to a CEO.

The AI model is brilliant but has never read our documents, so left alone it guesses. RAG looks up the most relevant passages from our own knowledge base for every question and makes the model answer only from them, with citations. Answers become current, checkable, and updatable by editing documents — no retraining. (Tab 9.)

Prompt engineering vs RAG vs fine-tuning — the 30-second version.

Prompting: instructions and examples in the request — free, first resort. RAG: retrieve your knowledge at request time — for facts, freshness, citations. Fine-tuning: train behavior/format/narrow skill into (usually) a smaller model — for style and cost, not facts. Climb in that order; combine freely. (Tabs 8–10.)

Your PM asks "why is our AI feature's latency 8 seconds?" — top suspects?

(1) Not streaming — full completion before first byte. (2) Fat prompts inflating prefill. (3) Flagship model where a small one passes evals. (4) Cold starts on scaled-to-zero services. (5) Sequential retrieval/tool steps. Then: trace one request and let the timeline convict the guilty stage. (Tabs 7, 8, 11.)

How do you A/B test a new prompt safely?

Prompts are versioned artifacts: canary the new version on 5–10% of traffic, compare quality (judge scores/feedback), cost (tokens), latency, and error/refusal rates against the incumbent, then promote or roll back — identical to a code deploy, because it is one. (Tab 11.)

When would you self-host a model instead of using an API?

Sustained high volume where per-token spend crosses the GPU+ops breakeven; strict data control/residency; a fine-tuned model APIs can't serve; latency needs colocated inference. Otherwise APIs win on quality-per-effort. Show the math instinct: estimate monthly tokens × price vs GPUs × hours × rate + engineers. (Tabs 2, 8, 10.)

Ops & cost
You deploy and errors spike. What happens next in a healthy setup?

The canary/rollout gate catches the error-rate breach on the 10% slice, halts promotion, and auto-rolls traffic back to the previous revision; the alert links the deploy; logs carry the new version tag for instant attribution. Total user exposure: minutes × 10%. If the answer is "we SSH in and debug live", the setup — not the engineer — failed. (Tab 11.)

Name the three observability signals and one thing each answers.

Logs — "what exactly happened in request X?" (structured, correlation IDs). Metrics — "how is the system trending?" (RED: rate, errors, duration percentiles). Traces — "where did the time go across services?" For AI add the fourth: token/cost/quality telemetry per request. (Tab 11.)

Your interviewer asks for one number that proves you run AI apps professionally.

Cost per conversation (or per document/user) by tier, from per-request token logs — because it connects engineering choices (model routing, caching, context size) directly to margins. Knowing yours, and its trend, ends the "do they really operate this stuff?" question. (Tab 11.)

Topics we skipped as build-topics — but interviews still ask

This guide deliberately skipped identity and security administration. Carry these four compact answers so the gap never shows:

  • Shared responsibility model: the cloud secures the infrastructure (physical data centers, hardware, hypervisor); you secure what you build on it (your data, access configuration, application code, secrets). The cloud will not stop you from making a bucket public — that's your side of the line. One-line answer, universally asked.
  • IAM (identity and access management) in one paragraph: every actor — human or service — gets an identity; policies grant specific actions on specific resources; the golden rule is least privilege (grant the minimum needed). Applications authenticate via short-lived roles/service accounts attached to their compute — never via long-lived keys pasted into code. That single paragraph satisfies most interview probes.
  • Encryption: in transit = TLS everywhere (tab 7); at rest = storage/databases encrypt by default with cloud-managed keys (KMS/Key Vault manage them; customer-managed keys exist for stricter compliance). Usually one sentence suffices.
  • VPC (virtual private cloud): your logically isolated private network within a region — subnets (public = internet-reachable via a gateway; private = not), route tables, and firewall rules (security groups) controlling who talks to whom. Standard posture: only the load balancer is public; app and database live in private subnets. Knowing that shape answers 90% of networking-security questions.
