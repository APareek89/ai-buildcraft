Start here

You already ran a fine-tune. This explains what actually happened — in the order the concepts build on each other.

This archived teaching example uses Qwen3-4B-Instruct, 4-bit, 36 layers with mlx-lm. Model shapes and numeric examples are retained from the original lesson. Its checkpoint, dataset and training run are not bundled or freshly reproduced here; memory estimates depend on hardware, optimizer and implementation.

The one-sentence version

Fine-tuning shows a model examples of the behavior you want, measures how wrong its guesses are, and nudges its internal numbers to be slightly less wrong — a few hundred times. Full fine-tuning nudges all of them; LoRA nudges a tiny set of add-on numbers instead, which is the only reason this fits on a laptop.

The five ideas, in dependency order

  1. A model is numbers in a shape. Weights, layers, tensors — nothing more exotic.
  2. A forward pass makes a guess; loss scores it. One number saying "how surprised were you by the right answer".
  3. A gradient says which way to nudge each number to lower that score. An optimizer takes the step.
  4. Doing that to every weight is full fine-tuning. It works, and it needs ~50GB of RAM for your model.
  5. LoRA freezes the model and trains a small add-on instead. 3.7 million numbers rather than 4 billion.

Read straight through — each section assumes the one before it. Budget ~45 minutes.

1 · What a model actually is

Before "fine-tuning" means anything, you need a concrete picture of the thing being tuned.

It's a stack of matrices

A language model is a large collection of numbers arranged in rectangles (matrices), organised into repeated blocks. That's genuinely it. Your model:

PieceYour modelIn English
hidden size2,560Each token is represented by a list of 2,560 numbers as it moves through.
layers (blocks)36The same block structure, repeated 36 times. Depth = repetition.
vocabulary151,936The token options it can predict. Every guess is a score over all of them.
parameters~4 billionThe individual numbers. These are what training changes.

What's inside one block

Every one of the 36 blocks has the same seven weight matrices, in two groups:

  • Attention — q_proj, k_proj, v_proj, o_proj. This is where tokens look at other tokens. It's how "it" knows what it refers to.
  • MLP — gate_proj, up_proj, down_proj. Per-token processing, no looking around. Most of the parameters — and most of what we loosely call "knowledge" — sit here.

Between them sit layer norms (keep numbers in a sane range) and RoPE (tells the model token order — pure maths, no weights).

Why "projection"

Every *_proj is a matrix multiply that reshapes a vector: q_proj takes 2,560 numbers in and gives 4,096 out. "Projection" is just linear-algebra vocabulary for that. When you read nn.Linear(2560, 4096), picture a 2560×4096 grid of trainable numbers.

Verify it yourself

model-explorer.ipynb · cell 3 
for name, child in model.model.layers[0].children().items():
    print(name, type(child).__name__)

Modules nest like folders, and .children() lists one level. Nothing is hidden — you can walk the entire 4-billion-parameter model with a for loop.

The 4-bit wrinkle

Your model is quantized: each weight is squeezed from 16 bits to 4, and eight of them are packed into one 32-bit integer. That's why the file is 2.3GB instead of ~8GB, and why q_proj.weight prints a shape of (4096, 320) instead of (4096, 2560) — 320 × 8 = 2,560. To read the real values you dequantize, which cell 5 of the explorer does.

1b · A worked example: one token, one matrix, one number

This section retains the original lesson’s Qwen3-4B arithmetic as a worked example. Recompute it against your own checkpoint before using the numbers as experiment evidence.

We'll push the phrase "The cat sat" through the very first attention block and watch the arithmetic, then zoom all the way in on a single parameter.

Step 1 — text becomes token ids

tok.encode("The cat sat")   →   [785, 8251, 7578]
                              'The'   ' cat'   ' sat'

Three words, three tokens. Note the leading spaces belong to the tokens.

Step 2 — each id becomes a vector of 2,560 numbers

The embedding table is a lookup: row 7578 is the starting representation of " sat".

x = embed_tokens(7578)          # shape (2560,)

first 8 of 2560:
[ 0.00000, -0.03711, -0.01489, +0.02234,
  +0.05957, +0.02234, +0.00745, +0.02234 ]
What these 2,560 numbers are

Not "features" you could name. They're a learned coordinate system — the model's private encoding of everything it knows about the token " sat". Nobody, including the people who trained it, can tell you what dimension 1,847 means. It only has meaning in combination.

Step 3 — the matrix multiply

q_proj turns that 2,560-number vector into a 4,096-number query. Its weight matrix is 4096 × 2560:

q = x · WqT     (2560) × (2560 → 4096) = (4096)
q_proj stored : (4096, 320)     # 4-bit packed, 8 values per uint32
q_proj real   : (4096, 2560)    # after dequantizing
entries       : 10,485,760      # one matrix, one layer

q = x @ Wq.T   →  first 6 of 4096:
[ +0.01201, -0.00045, -0.00525, -0.01657, +0.00676, +0.02390 ]

Step 4 — where one of those output numbers came from

q[0] is a single dot product: multiply all 2,560 input numbers by 2,560 weights and add them up.

q[0] = Σk=0..2559  x[k] × W[0, k]

  x[0]=+0.00000 × W[0,0]=-0.00237  =  -0.0000000
  x[1]=-0.03711 × W[0,1]=-0.01184  =  +0.0004394
  x[2]=-0.01489 × W[0,2]=+0.00946  =  -0.0001409
  x[3]=+0.02234 × W[0,3]=+0.00473  =  +0.0001057
  x[4]=+0.05957 × W[0,4]=+0.00237  =  +0.0001409
  ... 2,555 more terms ...
  ─────────────────────────────────────────────
  total                            =  +0.01201  ✓

That's the entire operation. A transformer is billions of these, arranged.

Step 5 — one parameter, out of four billion

The single number you asked about

Wq[0, 0] = −0.002365

Read the two indices as [output, input]:

  • Column 0 — it reads input feature #0, one of the 2,560 numbers describing the token right now.
  • Row 0 — it contributes to output feature #0, one of the 4,096 numbers of the query vector.
  • The value −0.002365 — "when building query-feature 0, count input-feature 0 with weight −0.0024." Negative means it pushes down. Small magnitude means it barely matters, relative to the other 2,559 votes.

This one number is 1 of 10,485,760 in this matrix, which is 1 of 7 matrices in this block, which is 1 of 36 blocks — 1 of ~4 billion in the model. Training changes numbers like this one. Full fine-tuning would adjust all four billion; your LoRA run adjusted 3.67 million add-on numbers instead and left this one frozen at exactly −0.002365.

The honest part: this parameter means nothing on its own. It is one vote, among 2,560 votes, producing one number, among 4,096, at one layer, of 36. Meaning lives in the pattern, never in the parameter. That's why you can't "look up" a fact in a model — and why fine-tuning is nudging millions of numbers slightly rather than editing any of them deliberately.

Step 6 — now Q, K, V and O

The same multiply happens four times per block, with four different weight matrices. In the archived example model:

MatrixShapeProducesThe question it answers
q_proj Q2560 → 4096Query"What am I looking for?"
k_proj K2560 → 1024Key"What do I offer to others?"
v_proj V2560 → 1024Value"What content do I pass on if chosen?"
o_proj O4096 → 2560Output"Fold the result back into the token."

The library-catalogue analogy: Q is your search request, K is each book's spine label, V is the book's actual contents. You compare your request against every spine, and take a weighted blend of the contents of whichever match.

Visual: one token through 32 heads

The two views are the same thing

Implementation view: one big matmul x @ Wq.T gives 4,096 numbers, which you then reshape to (32, 128).

Conceptual view: Wq's 4,096 columns are really 32 blocks of 128 columns — columns 0–127 build head 0's query, columns 128–255 build head 1's, and so on. Each head effectively has its own private 2560×128 matrix.

They're mathematically identical. The library does one matmul because it's faster; you should think in the second view because it explains what heads are.

So what does one head actually do?

Take head 7. Every token in your sentence produced a 128-number query and (via its group) a 128-number key. Head 7 does this, using only its own 128 numbers — never the other 3,968:

# head 7, for the token " sat", over the sentence "The cat sat"
q₇(sat) · k₇(The)  /  √128   →  score
q₇(sat) · k₇(cat)  /  √128   →  score
q₇(sat) · k₇(sat)  /  √128   →  score
                    softmax  →  [0.2, 0.5, 0.3]      # weights, sum to 1
     0.2·v₇(The) + 0.5·v₇(cat) + 0.3·v₇(sat)  →  head 7's 128-number answer

All 32 heads do this simultaneously and independently, each with different weights, so each learns to track something different — one might follow grammatical subjects, another long-range topic, another punctuation. Then:

32 answers × 128 = 4,096 concatenated → o_proj → 2,560 → added back to the token

And the token is back to 2,560 numbers, slightly better informed than before, ready for the next of the 36 blocks.

Where does 4,096 come from?

Not from "expanding" anything. The output is immediately sliced into 32 attention heads of 128 numbers each:

32 heads × 128 per head = 4,096

So q_proj doesn't produce one 4,096-long query — it produces 32 separate 128-long queries, one per head, computed in a single matmul for efficiency. Each head then runs its own independent attention over the sentence, asking a different question about it. Their 32 answers are concatenated back to 4,096, and o_proj folds that down to 2,560 so it can be added back into the token's running representation.

2560 → q:4096 / k:1024 / v:1024 → attention → 4096 → o_proj → 2560 ↺
The surprise in Qwen3's config

In the classic transformer, head_dim = hidden_size ÷ num_heads, which would make each head 2560 ÷ 32 = 80 numbers wide and q_proj a square 2560→2560. Qwen3 doesn't do that — it declares head_dim: 128 independently in config.json. That decoupling is exactly why the output is wider than the input:

hidden_size          2560
num_attention_heads    32
head_dim              128   # declared, NOT 2560/32 = 80

q_proj out = 32 × 128 = 4096   # wider than hidden_size
k/v_proj  =  8 × 128 = 1024

The model deliberately spends extra parameters to give each head 128 dimensions of room instead of a cramped 80. Better attention quality, slightly more compute. When you see a projection whose output doesn't match the hidden size, this is nearly always why — check head_dim before assuming it's a typo.

Why K and V are narrower (1024, not 4096)

Grouped-query attention. 32 query heads × 128 = 4096, but only 8 key/value heads × 128 = 1024 — four query heads share each key/value head. It cuts memory during generation substantially, at almost no quality cost. That asymmetry in the shapes is GQA, visible right there in the numbers.

Step 7 — the tokens actually compare themselves

Attention compares every query against every key, scaled, then softmaxed into weights that sum to 1:

attention = softmax( Q · KT / √128 ) · V

Computed on our three tokens, head 0:

scores (3×3):
            The     cat     sat
   The    [ 0.009,  0.001, -0.001 ]
   cat    [ 0.004,  0.000, -0.002 ]
   sat    [ 0.004,  0.000, -0.001 ]

softmax for " sat" over [The, cat, sat]:
   [ 0.334, 0.333, 0.333 ]

Each row asks "how much should this token attend to each other token?" The result is a weighted average of the V vectors, which o_proj then maps back to 2,560 numbers and adds into the token's running representation.

Read those numbers honestly

The near-uniform 0.334/0.333/0.333 is not what the real model computes. To keep the arithmetic legible this demo skipped four things the real forward pass does: input_layernorm before the projections, Qwen3's per-head q_norm/k_norm, RoPE positional encoding, and the causal mask that stops tokens seeing the future. With those applied the scores become sharply differentiated. The mechanics above are exact; the specific attention weights are a simplification.

Where LoRA attaches

The example adapter wraps all four of these matrices (plus the three MLP ones) in blocks 28–35. For q_proj it never touches the 10,485,760 numbers above. Instead it computes a correction alongside them:

q = x·WqT + scale · ((x · A) · B)

where A is 2560×8 and B is 8×4096 — 53,248 trainable numbers standing in for 10.5 million. That single frozen −0.002365 stays exactly where it is; the adapter learns to add a small correction to the result instead.

2 · The forward pass and the loss

How a guess is made, and how we turn "that guess was bad" into a single number.

The forward pass

Text goes in as token ids. Each token becomes a 2,560-number vector, then flows through all 36 blocks, each one adding information. At the end you get logits: for every position, a raw score for each of the 151,936 possible next tokens. softmax turns those scores into probabilities that sum to 1.

tokens → [36 blocks] → logits → softmax → probabilities

Everything is next-token prediction

Here's the trick that makes training work, and it's the line you saw in the code:

tuner/trainer.py · default_loss, lines 87–88 
inputs  = batch[:, :-1]   # everything except the last token
targets = batch[:, 1:]    # everything except the first

Shifting by one means: at every position, the "right answer" is simply the next token. One forward pass over a 400-token email produces 400 graded predictions at once. Your training data needs no labels — the text is the label.

Cross-entropy, in plain terms

Cross-entropy loss for one position is:

loss = −log( probability the model gave the correct token )

That's the whole formula. It has one behaviour worth feeling: it punishes confident wrongness brutally and rewards confident correctness. Drag the slider:

◆ Loss calculator
60%
loss = −log(0.60) = 0.51

The number in your training log is this, averaged over every token in the batch.

Perplexity = eloss

The archived example reports Test loss 2.340, Test ppl 10.382. Perplexity is just the loss exponentiated, and it reads in English: "on average the model was wavering between ~10 candidate tokens." Perfect certainty is 1.0. Same information, friendlier scale — that's why lora.py line ~313 computes math.exp(test_loss).

The mask (the part the lab skipped)

tuner/trainer.py · lines 92–96 
steps = mx.arange(1, targets.shape[1] + 1)
mask  = mx.logical_and(steps >= lengths[:, 0:1], steps <= lengths[:, 1:])
ce    = nn.losses.cross_entropy(logits, targets) * mask

Multiplying by a 0/1 mask zeroes out positions that shouldn't count: padding at the end of short rows, and — if you pass --mask-prompt — the customer's email text, so the model is graded only on writing the reply. Dividing by mask.sum() rather than the array size keeps the loss comparable across batches of different lengths.

3 · Gradients and how learning happens

The only real "maths" in the whole process, and it's one idea: slope.

A gradient is a slope

You have a loss (how wrong we are) and 4 billion knobs. For each knob, we want to know: "if I turn this one slightly up, does the loss go up or down, and how sharply?" That answer — the derivative — is the gradient for that knob.

The classic picture: you're on a foggy hillside and want to reach the valley. You can't see the landscape, but you can feel the slope under your feet. Take a small step downhill. Repeat. The gradient is the slope; the learning rate is your step size.

Why learning rate is delicate

Steps too big and you leap across the valley and up the far side — that's loss going nan or exploding. Too small and you crawl, needing far more iterations. 1e-5 is the default in the example run; the troubleshooting table suggests 2e-5 if loss barely moves and 5e-6 if it's jumpy.

Backpropagation, and why you never write it

Computing that slope for 4 billion knobs sounds impossible. It isn't, because of the chain rule from calculus: if you know how the loss changes with respect to a layer's output, you can work out how it changes with respect to that layer's input — and so on backwards through the network. That's backpropagation.

Frameworks do it automatically. This is that moment in your code:

tuner/trainer.py · line 240 and 250 
loss_value_and_grad = nn.value_and_grad(model, loss)
...
(lvalue, toks), grad = loss_value_and_grad(model, *batch)

MLX traced every operation in the forward pass, so it can walk it backwards and hand you grad — a structure mirroring your model, holding one gradient per trainable parameter. Note the phrase "trainable": frozen parameters aren't in there at all, which is exactly why LoRA is cheap.

The optimizer takes the step

tuner/trainer.py · line 259 
optimizer.update(model, grad)

The simplest optimizer would be weight = weight − learning_rate × gradient. The example run uses Adam, which adds two refinements:

  • Momentum — keeps a running average of recent gradients, so consistent directions build speed and noisy ones cancel out.
  • Per-parameter step sizes — parameters with consistently large gradients get smaller steps, and vice versa. Everyone moves at a sensible pace.

The cost: Adam stores two extra numbers per trainable parameter (the two running averages). Remember that — it's the punchline of the next section.

You've seen this work

In training-loop-lab.ipynb, one call to value_and_grad plus one optimizer.update dropped the loss on a single email from 4.53 to 3.70. That's one step downhill. Training is 600 of them.

4 · Full fine-tuning FFT

The straightforward method: update every weight. Understand it first, because LoRA is defined by what it changes about it.

What it means

All 4 billion parameters are trainable. Every gradient step adjusts the entire model. Conceptually it's the purest form of fine-tuning and has the highest quality ceiling: nothing about the model is off-limits, so it can learn new domains, new formats, even new languages.

In your toolchain it's one flag — --fine-tune-type full — and the code is refreshingly blunt:

mlx_lm/lora.py · lines 232–235 
if args.fine_tune_type == "full":
    for l in model.layers[-max(args.num_layers, 0):]:
        l.unfreeze()

No adapters, no cleverness: just mark the last N layers trainable again.

Why full training can exceed a 16 GB machine

Training needs far more memory than the weights alone. For every trainable parameter you must hold:

  • the weight itself
  • its gradient (same size)
  • Adam's two running averages (usually in higher precision)

Play with it — the defaults are a 4B model on a 16 GB machine:

◆ Training memory calculator
4B
16 GB

For a 4B model, full fine-tuning needs roughly 48GB before activations even enter the picture. A 16 GB machine shares that memory with the OS. It isn't close, and no amount of patience fixes it — the run simply cannot start.

When FFT is still the right answer

On rented A100/H100 GPUs, with a genuinely large dataset (tens of thousands of examples), or when you need the model to absorb a whole domain rather than adopt a style. Also for small models — full fine-tuning a 0.5B model on a laptop is entirely reasonable, which is why the DeepLearning.AI lesson uses a 135M model for its live demo.

The other cost: one full copy per task

A fully fine-tuned 4B model is a new ~8GB file. Ten tasks, ten copies. Adapters are ~15MB each and share one base — that difference matters more in production than the training cost does.

5 · Freezing — the mechanism underneath everything

"Frozen" sounds abstract. In code it's a boolean flag, and it has one precise consequence.

What freezing does

Every parameter carries a "trainable" flag. Freezing sets it to false. The single consequence: the autograd system doesn't compute a gradient for it, and the optimizer never touches it. The weight still participates fully in the forward pass — it just never changes.

mlx_lm/lora.py · line 224 
model.freeze()

One line freezes all 4 billion. That's step one of every LoRA run — the model is fully frozen first, then a small number of things are made trainable again.

The three consequences

EffectWhy it matters
No gradients storedThe biggest memory saving. Gradients are the same size as weights.
No optimizer stateAdam's two averages per parameter simply don't exist for frozen weights.
Can't be damagedThe base model's general ability is preserved exactly — no "catastrophic forgetting".

Inspect the relevant training code

MLX training loop · illustrative excerpt 
total     = sum(p.size for _, p in tree_flatten(model.parameters()))
trainable = sum(p.size for _, p in tree_flatten(model.trainable_parameters()))

Two different methods: parameters() returns everything, trainable_parameters() returns only the unfrozen. In the example lab that printed 0.29% trainable. And it's why the saved adapter file contains only the LoRA matrices — look at the save line:

tuner/trainer.py · line 372 
adapter_weights = dict(tree_flatten(model.trainable_parameters()))

That one word, trainable_, is why your checkpoint is 14MB and not 2.3GB.

Battery-interruption bonus

Because the file holds only adapter weights, resuming loads it with strict=False — "don't complain that most of the model is missing from this file." That's lora.py line ~248, and it's what makes your 0000400_adapters.safetensors resumable.

6 · LoRA Low-Rank Adaptation

Freeze everything, then add a small, trainable detour beside each layer you care about.

The core insight

Full fine-tuning learns an update ΔW — a change for every entry of a weight matrix. For q_proj that's a 2,560 × 4,096 grid: 10.5 million numbers, for one matrix in one layer.

LoRA's bet: the useful update isn't random noise, it has structure — a few coherent patterns rather than 10 million independent choices. So instead of learning ΔW directly, learn two skinny matrices whose product is ΔW:

ΔW ≈ A · B where A is 2560×r and B is r×4096

with r (the rank) small — 8 in the example run. You've forced the update through an 8-dimensional waist. That's the entire idea; everything else is bookkeeping.

◆ Rank explorer — q_proj (2560 → 4096)
8

The layer, in code

Three lines do the work, and you can read every one:

▸def __call__(self, x):
The forward pass of a LoRA-wrapped layer. x is the incoming activation. Python calls this whenever you use the layer like a function — layer(x).
▸    y = self.linear(x)
The original frozen layer, untouched. self.linear is the real Qwen weight matrix. Its output y is exactly what the base model would produce — LoRA never interferes with this path.
▸    z = (self.dropout(x) @ self.lora_a) @ self.lora_b
The trainable detour. @ is matrix multiply in Python. Read it right to left: x (2560 wide) is squeezed by lora_a down to just 8 numbers, then expanded by lora_b back out to 4096. The squeeze is where the parameter saving comes from. dropout randomly zeroes some inputs during training to reduce overfitting (off in the example run).
▸    return y + (self.scale * z).astype(x.dtype)
Original plus correction. scale (20.0 in the example run) controls how loudly the adapter speaks. .astype(x.dtype) converts back to the model's precision — the adapter computes in float32 for stability but the model runs in bfloat16.

The zero-initialization trick

tuner/lora.py · lines 88–93 
self.lora_a = mx.random.uniform(low=-scale, high=scale, shape=(input_dims, r))
self.lora_b = mx.zeros(shape=(r, output_dims))

A starts random, B starts as all zeros. So on iteration 1, z = (x·A)·B = 0, and the wrapped model behaves identically to the original. Training begins from "change nothing" rather than from noise — you can never make the model worse by attaching an untrained adapter.

The consequence you observed

The example lab printed lora_a change = 0.00e+00 after the first step, while lora_b moved. That's not a bug: the gradient of A is proportional to B, and B is zero, so A mathematically cannot move until B does. From step 2 onward both train.

What the example run actually trained

In the archived example adapters.safetensors:

FactValue

Why the last layers? Early layers handle general structure — grammar, syntax, basic semantics — that your emails don't need to change. Later layers shape higher-level style and output format, which is exactly what you're teaching. Adapting the end is cheaper and usually enough.

Fusing

At inference you can keep base + adapter separate (swap adapters per task) or merge them permanently:

tuner/lora.py · line 52 
delta = ((self.scale * self.lora_b.T) @ self.lora_a.T).astype(weight.dtype)
fused_linear.weight = weight + delta

Multiply the two skinny matrices back into a full-size ΔW, add it to the base weight, and the adapter disappears into an ordinary layer. This is often called adapter merging. Note it costs a full model copy — which is why you only do it when you're happy.

7 · Choosing between them

Same goal, different trade-offs. Here's how to decide without hand-waving.

Full fine-tuningLoRA
What trainsEvery weight (or every weight in the last N layers)Small A·B matrices beside chosen layers
Your model~4B parameters3.67M parameters
Memory (4B)~48GB+~2.5GB
Fits the example memory budgetNoYes
Output artifactFull model, ~8GBAdapter, ~15MB
Multiple tasksOne full copy eachMany adapters, one shared base
Quality ceilingHighestVery close for style/format tasks
Forgetting riskReal — can degrade general abilityNear zero — base is frozen
SpeedSlower per stepFaster (fewer gradients)

The honest decision rule

  • Teaching style, tone, or output format? LoRA. A short-form response task is a reasonable LoRA baseline; evaluate it against the untuned model.
  • Teaching a genuinely new domain (a new language, a specialised technical field) with tens of thousands of examples? Full fine-tuning, on rented GPUs.
  • Model under ~1B parameters? Full fine-tuning is affordable even locally; the LoRA machinery buys you less.
  • Need several behaviours from one deployment? LoRA, decisively — hot-swappable adapters over a single base.
The family tree, so the jargon stops being scary

PEFT (Parameter-Efficient Fine-Tuning) is the umbrella for "don't train everything". LoRA is its most popular member. QLoRA = LoRA where the frozen base is also quantized — which, since your base is 4-bit, is what you're actually running. DoRA splits each update into direction and magnitude and trains them separately; one flag away (--fine-tune-type dora). Prompt/prefix tuning trains virtual tokens instead of weights — cheaper, weaker, mostly superseded.

A different axis: what you train on

LoRA vs FFT is about which weights. Separately there's what signal:

  • SFT (supervised fine-tuning) — input → correct output pairs. What you're doing.
  • DPO / RLHF — pairs of answers labelled "this one is better". How chat models learn tone and refusals. Usually applied after SFT.
  • Continued pre-training — raw domain text, no Q→A structure. Absorbs vocabulary before any SFT.

These combine freely with either method: "LoRA + DPO" is a perfectly normal sentence.

Two files named lora.py

mlx_lm/lora.py is the CLI script (377 lines) — argument parsing and setup. mlx_lm/tuner/lora.py is the layer definition (285 lines) — the actual LoRA maths. VS Code's file search shows the first one; the concepts in this page live in the second.

One iteration, end to end

  1. iterate_batches pulls rows, sorted by length to minimise padding, and pads to a multiple of 32.
  2. default_loss shifts tokens, runs the forward pass, applies cross-entropy, masks padding, averages per real token.
  3. nn.value_and_grad back-propagates to get a gradient for every trainable parameter — i.e. only the LoRA matrices.
  4. optimizer.update nudges those matrices with Adam.
  5. Every 10 iters: print the loss. Every 100: mx.save_safetensors writes a checkpoint.

9 · Syntax decoder

The Python and MLX constructs that make this code look harder than it is. Click any line.

Python you'll trip on

▸inputs = batch[:, :-1]
Two-dimensional slicing. The comma separates dimensions: [rows, columns]. : alone means "all of this dimension", :-1 means "everything except the last". So: all rows, all columns except the final one. [:, 1:] is all rows, columns from index 1 onward.
▸z = x @ a
Matrix multiplication. @ is Python's dedicated matmul operator (* would multiply element-by-element instead). Shapes must line up: (n×2560) @ (2560×8) gives (n×8).
▸def __call__(self, x):
Makes an object callable. Defining __call__ means you can write layer(x) instead of layer.forward(x). The double underscores mark Python's built-in hooks ("dunder" methods). __init__ is the constructor — it runs once when the layer is created.
▸yield batch, mx.array(lengths)
A generator. yield hands back a value and pauses, resuming where it left off next time. That's how iterate_batches feeds an endless stream of batches without ever building them all in memory — critical when the dataset is large.
▸@dataclass
class TrainingArgs:
A decorator. The @ prefix wraps the thing below it. @dataclass auto-generates boilerplate (constructor, printing) for a class that's just a bag of settings. @partial(mx.compile, ...) on step() is the same mechanism, wrapping the function so MLX compiles it into one optimised GPU graph.
▸len_fn = lambda idx: len(dataset[idx][0])
An anonymous function. lambda args: expression is a one-line function without a name. Here it's handed to sorted() as the "how to measure each item" rule.
▸train(model=model, args=training_args, **kwargs)
Keyword arguments and unpacking. name=value passes by name rather than position. *batch unpacks a tuple into separate arguments; **kwargs does the same for a dictionary into named ones.
▸sum(p.size for _, p in tree_flatten(...))
A generator expression. Builds values on the fly and feeds them to sum() without making a list. The _ is a conventional name for "a value I'm required to unpack but don't care about" — here, the parameter's name.

MLX-specific

▸mx.eval(loss, model.parameters())
Force computation. MLX is lazy: operations build a graph and don't run until a result is needed. mx.eval() says "actually compute this now". You'll see it before printing or timing anything. Forgetting it makes timings meaningless — you'd be measuring graph-building, not maths.
▸nn.value_and_grad(model, loss_fn)
Returns a new function. Call the result and you get back both the loss value and all gradients in one pass. Higher-order functions like this are the standard functional-style API in MLX and JAX.
▸tree_flatten(model.parameters())
Flattens a nested structure. Model parameters come as dicts inside dicts (mirroring the module tree). tree_flatten turns that into a flat list of (name, array) pairs — e.g. ("model.layers.28.mlp.up_proj.lora_a", array) — which is how they get counted and saved.
▸W.astype(mx.float32)
Change numeric precision. The model runs in bfloat16 (16 bits, fast, less precise); losses accumulate in float32 to avoid rounding drift. Also required before handing arrays to numpy, which has no bfloat16 type.
▸mx.dequantize(q.weight, q.scales, q.biases, ...)
Unpack 4-bit weights. Quantized weights are stored as packed integers plus per-group scales and biases. Dequantizing reverses the compression to give readable floats. Needed any time you want to inspect or fuse.

11 · Glossary & where to go next

Glossary

TermPlain English
Parameter / weightOne trainable number inside the model.
TensorAn array of numbers, possibly multi-dimensional. A matrix is a 2D tensor.
TokenA chunk of text (~4 characters). Models read and predict these, not words.
LogitsRaw, unnormalised scores for every possible next token.
SoftmaxTurns logits into probabilities summing to 1.
LossOne number: how wrong the model was. Lower is better.
Cross-entropyThe specific loss used: −log(probability of the correct token).
Perplexityeloss. "How many tokens is it wavering between."
GradientThe slope: which way to nudge a weight to reduce loss.
BackpropagationThe chain-rule algorithm that computes all gradients efficiently.
Optimizer / AdamDecides the actual step from the gradient; Adam adds momentum and per-parameter step sizes.
Learning rateStep size. Too big explodes, too small crawls.
IterationOne weight update = one batch processed.
EpochOne full pass over the dataset. iters × batch ÷ rows.
OverfittingMemorising training data; train loss falls, validation loss doesn't.
FrozenMarked untrainable: no gradient, no optimizer state, never changes.
Rank (r)The width of LoRA's bottleneck. Higher = more capacity and more parameters.
AdapterThe small trained LoRA matrices, saved as a separate file.
QuantizationStoring weights in fewer bits (4 instead of 16) to save memory.
PEFTParameter-Efficient Fine-Tuning — the family LoRA belongs to.
SFTSupervised Fine-Tuning: learning from input→output pairs. What you're doing.
Gradient checkpointingDiscard intermediate values and recompute them; trades speed for memory.

Courses — only if you want the maths properly

  • Andrej Karpathy — "Neural Networks: Zero to Hero" (free, YouTube). The single best fit for you: he builds autograd from scratch in Python, so value_and_grad stops being magic. Watch "The spelled-out intro to backpropagation" (2.5h) — that one video covers the gap you named.

Reading the source of mlx-lm, is worth more than a fourth course. It's under 1,300 lines and it's the real thing.
