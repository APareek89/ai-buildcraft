RAG, Visually
Retrieval-Augmented Generation · for beginners

From a raw document to a grounded answer

An LLMi only knows what it learned during training. RAG lets it look things up in your documents first — so answers can use current, specific, citable evidence. This page walks the pipeline with interactive simulations and an archived Agentic Learning Studio worked example. The chunk counts, database version and retrieval score below illustrate that example; this page does not connect to a live knowledge base.

bge-small · 384-dim Supabase + pgvector HNSW + tsvector Hybrid + RRF 260-chunk worked example
Without RAG

Closed-book exam

You ask the model a question and it answers purely from memory. If the topic is new, niche, or changed after training, it guesses — and can sound confident while being wrong (hallucinationi).

With RAG

Open-book exam

Before answering, the system retrieves the most relevant pages from your notes and hands them to the model with the question. The model answers grounded in those pages and can cite them.

1

Documents — the raw material

RAG starts with your source material: PDFs, Word docs, Markdown, web pages, or structured data (JSON/CSV). The first job is to normalize everything into plain text plus useful metadata.

concept Two shapes of input

Prose — long free text (a guide, a research plan). Will be sliced into windows.
Records — a catalog where each row is already one self-contained item (e.g. a list of tools). Each row becomes one chunk, no slicing.

example A 260-chunk knowledge base

The worked example has 4 documents → 260 chunks: a 247-row tool catalog (247 record chunks), a research-plan .docx (11 prose chunks), and two small JSON files (one chunk each). That is 247 + 11 + 1 + 1 = 260.

2

Chunks — why we slice documents

You can't embed a whole 50-page document as one vector — meaning gets blurred and retrieval returns way too much. So prose is cut into small overlapping chunksi (~a few paragraphs each). Records are already chunk-sized, so they're left whole.

concept Why overlap?

If a sentence is split across two chunks, neither chunk fully contains the idea. A small overlap (the tail of one chunk repeats at the head of the next) means the idea survives in at least one chunk.

technical Worked-example settings

~320 words per chunk, 60-word overlap, split on paragraph boundaries. (~450 / ~80 tokens.)

src/rag/chunkers.ts
const TARGET_WORDS = 320;
const OVERLAP_WORDS = 60;

3

Embeddings — turning text into numbers

An embeddingi is a list of numbers (a vectori) that captures the meaning of a piece of text. Texts about similar things get vectors that point in similar directions. The worked example uses bge-small-en-v1.5, which outputs 384 numbers per text and can run locally without an embedding API. The diagrams here simulate the mechanism; they do not load that model.

concept Meaning becomes geometry

Think of every text as an arrow in a 384-dimensional space. "LangGraph" and "CrewAI" land close together (both agent frameworks); "banana bread recipe" lands far away. Closeness = similar meaning.

technical One subtle gotcha: queries ≠ passages

BGE is asymmetric — a search query must be prefixed with a special instruction; stored passages are not. Mixing this up quietly hurts results, so the code has two separate functions.

src/rag/embed.ts
embedQuery(t)   // "Represent this sentence…: " + t
embedPassages(t) // t, raw (no prefix)
A real embedding is 384 numbers. Here's the first few of what "langflow …" becomes — just to make it concrete:

    Store + Index — making 260 vectors searchable fast

    All chunk vectors (plus their text + metadata) are saved in Postgres via the pgvectori extension. To search them quickly without comparing against every row, we build two indexes: one for vector search, one for keyword search.

    technical The chunks table (key columns)

    columnholds
    contentthe chunk text
    embeddingvector(384) — the meaning
    content_tsvauto keyword index of content
    title, category, verdict, as_of_datefilterable metadata
    content_hashUNIQUE → idempotent re-ingest

    concept Two indexes, two skills

    HNSWi (vector) → "find me things that mean the same." Approximate but fast.
    GIN / tsvectori (keyword) → "find me things that contain this exact word" (rescues names like LangGraph).

    supabase/migrations/0001_rag.sql — the indexes
    -- vector nearest-neighbour (cosine). Grows incrementally, no retraining.
create index chunks_embedding_hnsw on chunks
  using hnsw (embedding vector_cosine_ops) with (m=16, ef_construction=64);

-- keyword search; content_tsv is a GENERATED column kept in sync automatically
create index chunks_tsv_gin on chunks using gin (content_tsv);

    Query — the question becomes a vector too

    When you ask something, the system builds a search string and embeds it with embedQuery() (the prefixed one). Now the question lives in the same 384-D space as the chunks, so "nearest" is meaningful.

    example The worked example's query string

    The retriever blends the topic, the learner's goal, the must-cover items, and the raw prompt into one search string:

    Retrieve — two searches, fused

    The query runs two searches in parallel, then merges them. Vector search finds meaning; keyword search guarantees exact names. Merging them (RRFi) gives results better than either alone.

    technical Search A — vector (semantic)

    select id, content,
  1 - (embedding <=> $1::vector) as sim
from chunks
order by embedding <=> $1::vector
limit 20;

    <=> = cosinei distance. sim = 1 − distance (1 = identical meaning).

    technical Search B — keyword (exact)

    select id, content
from chunks
where content_tsv @@
   plainto_tsquery('english', $1)
order by ts_rank(...) desc
limit 20;

    Catches "LangGraph" even if the embedding blurs it with "LangChain".

    DEMO RRF — fusing the two ranked lists

    Each list ranks chunks differently. RRF scores every chunk by Σ 1/(60 + rank). A chunk that appears in both lists climbs to the top. Watch "LangGraph guide" and "langflow record" win — they're in both.

    concept Coverage — "did we actually find good stuff?"

    After fusing, a single coverage score (0–1, no LLM) estimates how well the KB covered the question — half from the best match, half from how many strong matches there were. Low coverage is the signal to fall back to the model's own knowledge (or, later, a web search).

    src/rag/retrieve.ts
    const topSim = Math.max(...sims);              // best single match
const strong = sims.filter(s => s >= 0.45).length; // how many are strong
const coverage = 0.5*topSim + 0.5*Math.min(1, strong/(k*0.4));
    Worked-example result for the LangChain/LangGraph query: 8 chunks retrieved, coverage 0.872 (87.2%). This is the example's retrieval heuristic, not a measured probability that the answer is correct.
    7

    Augment + Generate — the grounded answer

    The retrieved chunks are tagged S1…S8 and pasted into the model's prompt with an instruction to prefer them and cite them. The model writes the lesson; every [S#] it cites resolves to a real source in the footer.

    technical What the model actually receives

    src/agent/prompts.ts · architectUserPrompt()
    SOURCES from the knowledge base (cite via sources:["S#"];
trust their recency over your training data):
[S1] langflow (as of 2026-06-17): Visual framework for agentic…
[S2] dify (as of 2026-06-17): Open-source LLM app platform…
… (8 sources)
    Result: instead of a generic answer from memory, the model writes a lesson grounded in your 8 retrieved notes — current, specific, and with a Sources footer. That's the whole point of RAG.

    concept Graceful fallback

    If there's no database, the query is empty, or nothing matches, retrieve() returns {chunks:[], coverage:0} and the system simply tells the model "use your own knowledge." The app never crashes for lack of RAG — retrieval only ever improves the answer.

    The whole loop, in one breath

    1. Documents → Chunks: normalize files; slice prose into ~320-word overlapping windows; keep records whole.
    2. Chunks → Embeddings: each chunk becomes 384 numbers capturing meaning (bge-small, local, free).
    3. Store + Index: save vectors + text + metadata in Postgres/pgvector; build HNSW (vector) and GIN (keyword) indexes.
    4. Query: embed the question into the same space (with the BGE query prefix).
    5. Retrieve: vector search + keyword search → fuse with RRF → top-8 → coverage score.
    6. Augment + Generate: inject the chunks as S1…S8, the model answers grounded and cites them.
