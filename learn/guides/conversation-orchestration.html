Thread Orchestration — Conducting One Whole Conversation

This scripted teaching demonstration shows the layer above a single-request orchestrator: how a thread is conducted across many messages. Free text becomes a card, follow-up questions appear as a small form above the prompt box, and every later message is routed against what the thread already knows.

The idea, in plain English

The one-paragraph version

A conversation is not a sequence of independent questions — it’s a matter unfolding. So the thread carries a matter context object: the facts collected so far (each one typed to a schema field), which situation-card is active, and what has already been answered. Every new message — including the very first — goes through the same door: a classifier that reads the message together with that context and decides one of four routes: same card new purpose, same matter new card, brand-new matter, or unclear. Intake is deterministic and form-shaped; execution behind it is fully agentic. The chat box never disappears — it’s the doorway, not the product.

Your interface assumption — confirmed, and it has a name. Free text first → the agent repackages it into a card → the missing facts appear as a small form attached above the composer (the prompt box). That’s the “composer-attached form” pattern: the user never leaves the conversation, but the facts arrive typed, not as twenty chat turns. Tab B is a working demo of exactly this.

Why the carry-over works at all: facts live as typed schema fields, never as loose chat memory. “Cheque amount Rs 8,40,000” maps onto the recovery-suit schema’s claim_amount because both are declared fields — so switching cards mid-thread is re-classification plus gap-fill, not a restart. This is the payoff of “the schema is the product”.

2 · Classification — always with the context

function routeMessage(text, ctx) {
  const scores = scoreAgainstCards(text);                  // deterministic fingerprints first
  const overlap = factOverlap(text, ctx.facts);            // does it reference held facts / parties?

  if (scores.top === ctx.active_card)                return { route: "SAME_CARD",  purpose: detectPurpose(text) };
  if (scores.top !== ctx.active_card && overlap.high) return { route: "NEW_CARD",   card: scores.top };
  if (overlap.low && scores.top)                     return { route: "NEW_MATTER?", card: scores.top }; // confirm first
  return { route: "CLARIFY" };                             // one question - never guess
}

3 · Carry-over — why a card switch is not a restart

// declared once per card pair; typed fields map to typed fields - nothing is smuggled as prose
const CARRY = { "cheque_bounced -> recovery_suit": {
  cheque_amount: "claim_amount", drawer: "defendant", memo_date: "default_date_evidence" } };

function switchCard(ctx, toCard) {
  const mapped = applyCarry(CARRY, ctx.facts, toCard);
  const gaps   = gapsFor(toCard, mapped);                  // sufficiency recomputes on the NEW schema
  return { mapped, ask: gaps,                              // the form asks ONLY the delta
           note: "carried: " + Object.keys(mapped).join(", ") };   // said out loud in the thread
}
// assumptions do NOT carry - anything with status "unconfirmed" is re-asked if the new card needs it

4 · The composer-attached form — the interface contract

// the form is DERIVED, never designed per-conversation: it renders whatever gaps() returns
function renderForm(gaps, prefills) {
  return { position: "above_composer",                     // user never leaves the chat
           fields: gaps.map(g => ({ id: g.field, label: g.label, why: g.why_it_matters })),
           prefilled: prefills,                            // extracted facts shown, editable - trust
           rounds_cap: 2 };                                // then: labelled assumptions or a human
}
Where Exhibit G’s orchestrator fits: everything on this page happens before and after it. Once a route lands with sufficient facts, the request orchestrator takes over unchanged — planner, lanes, merge, verifier. Thread orchestration decides what to run and with which facts; request orchestration decides how to run it.

Design rules — and the honest answer to “is this agentic enough?”

The answer

“Agentic” describes the backend, not the input surface. Determinism at intake, agency in execution: the orchestrator, the treatment walks, the verifier are exactly as agentic behind a form as behind a chat box. Forms at intake are accuracy engineering — legal answers are context-gated, so collecting the answer-changing facts up front is how you earn the right to be agentic afterwards. Law firms buy reliability, not vibes.

RuleThree doors, one pipeline

Pick a card, type freely, or upload a document — all three converge on the same schema. Taxonomy navigation is never mandatory; the classifier is the concierge.

RuleForms stay surgical

Only fields the schema marks answer-changing, each with a why-we-ask line. Three sharp fields beat chat; ten bureaucratic ones lose to it.

RuleContext is visible, and editable

The matter chip and its facts ledger are on screen — tap to inspect, correct any fact. Trust comes from seeing what the system thinks it knows.

RuleFacts carry; assumptions don’t

Typed, user-confirmed facts cross card boundaries and are named out loud when they do. Unconfirmed assumptions are re-asked. Nothing stakes-bearing travels silently.

RuleNever guess the route

Low fact-overlap means one confirming question — “new matter, or the same cheque?” — not a silent new context. One question is cheap; a polluted matter file is not.

RuleChat never disappears

The free-text box survives every state — it’s how purposes arrive, how corrections arrive, and the escape hatch when no card fits. Doorway, not product.

Say this line
"The thread carries a typed matter context; every message - first or fifteenth - is classified against it into one of four routes; missing facts arrive through a small form docked above the prompt box; typed facts carry across cards and are announced when they do; and behind all that determinism, the request orchestrator stays fully agentic. Forms at intake are how the agent earns its autonomy."
