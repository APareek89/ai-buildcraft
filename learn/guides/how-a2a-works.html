Two Roles: Client Agent and Remote Agent

In plain wordsThink of a manager (client agent) who assigns a task to a specialist contractor (remote agent) — the manager doesn't do the work, but they own the goal and collect the result.

Every A2A interaction has exactly two roles. The is the one that has a goal and wants help. It initiates the conversation and sends work.

The is the specialist that receives the work, executes it, and returns results. It publishes an — a structured description of what it can do — so the client agent can find and understand it.

  • Client agent: owns the goal, discovers remote agents, sends tasks, collects results.
  • Remote agent: receives tasks, does the work, streams progress or returns a final artifact.

One agent can play both roles at once. A travel-planning agent might be a remote agent to the user's assistant, while acting as a client agent to a flights-search agent.

Imagine a user asks their AI travel assistant: "Book me the cheapest flight to Tokyo next Friday."

The assistant is built on Framework A; the flights-search agent is built on Framework B by a different company.

Without A2A, the travel assistant cannot find the flights agent.

It cannot understand what the flights agent accepts or send a task in a readable format.

The teams would need to write a custom integration.

With A2A — step by step

  1. Discovery: The travel assistant fetches the flights agent's Agent Card from a well-known URL.
  2. The card lists skills, input formats, and authentication requirements.
  3. Task creation: The client agent sends a Task — a structured message containing the goal.
  4. The goal: "find cheapest flight, Tokyo, next Friday."
  5. Execution: The remote agent searches, reasons, and streams progress updates back.
  6. Result: The remote agent returns an Artifact — a structured flight option.
  7. The travel assistant presents the option to the user.

Neither team wrote custom glue code.

The shared protocol handled discovery, task format, and result delivery.

What Is an Agent Card?

In plain wordsAn Agent Card is like a business card stapled to a résumé — it tells you who this agent is, what it's good at, and how to reach it, all in one place.

When a wants to delegate work, it first needs to know: can this other agent actually do what I need? The solves this with a structured JSON document called an .

JSON (JavaScript Object Notation) is just a text format for structured data — think of it as a tidy list of labelled fields. The Agent Card is published by the so any caller can read it.

The four core fields

  • name — a human-readable label for the agent (e.g. "ResearchBot").
  • description — a short plain-English summary of what the agent does.
  • url — the endpoint the client agent calls to send tasks. This is the agent's "address".
  • skills — a list of capability objects, each with an id, name, and description of one thing the agent can do.

Each field has a job. The url tells the client where to send work. The skills list tells it whether to bother. Without both, the client agent is guessing.

Before reading on, predict: if a client agent reads an Agent Card and finds no skill that matches its task, what should it do? (Answer: skip this remote agent and look for another one — the card just saved a wasted round-trip.)

Three Ways an Agent Card Gets Distributed

In plain wordsThink of the three distribution methods like finding a plumber: checking a standard directory listing (well-known URL), searching a trade registry (agent directory), or getting their card directly from a friend (direct config).

Publishing the card is only half the story — the client agent also needs to find it. The supports three distribution patterns.

  1. Well-known URL — the remote agent hosts its card at a predictable path, typically /.well-known/agent.json. Any client that knows the agent's domain can fetch it automatically, no prior arrangement needed.
  2. Agent directory — a central registry lists many Agent Cards. The client queries the directory to discover agents by capability. This is useful in large systems with many agents.
  3. Direct config — an operator hardcodes the card's location or content into the client agent's configuration. Simple and reliable for private or internal agents.

The well-known URL pattern is the most open — anyone can discover the agent. Direct config is the most controlled — only agents you configure can find it. The directory sits in between.

Security Risk: What a Public Card Can Leak

A public Agent Card is readable by anyone — including attackers. If the card lists sensitive internal skills (e.g. "delete customer records" or "access payroll data"), it becomes a map of what to target.

How this breaks in practice

  • Over-disclosure — a card lists every skill, including internal admin operations. An attacker reads the card and crafts a request aimed at those operations.
  • Endpoint harvesting — the url field exposes the live endpoint. Combined with a skill list, this is enough to probe the agent directly.
  • Stale cards — a card cached in a directory may list skills the agent no longer supports, causing the client to send tasks that will fail.
Key mitigation: keep public cards sparse. List only the skills you intend to expose publicly. Richer capability details can live behind authentication, served only to trusted callers.

A second mitigation is authentication on the card endpoint itself — require a token before returning the full card. This turns discovery into a gated step, not an open broadcast.

import urllib.request
import json

def fetch_agent_card(agent_domain: str) -> dict:
    """Fetch the Agent Card from the well-known URL."""
    url = f"https://{agent_domain}/.well-known/agent.json"
    with urllib.request.urlopen(url) as response:
        return json.loads(response.read())

def find_skill(card: dict, skill_id: str) -> dict | None:
    """Return the matching skill object, or None if not found."""
    for skill in card.get("skills", []):
        if skill.get("id") == skill_id:
            return skill
    return None

The Task Lifecycle: States and Transitions

In plain wordsA Task's status is like a package-tracking label — it moves through defined stops (submitted → in transit → delivered), and each stop tells you exactly what's happening right now.

has a status. Knowing the states lets you write code that reacts correctly at each stage.

  1. submitted — the client has sent the task; the remote agent has not yet started.
  2. working — the remote agent is actively processing. Intermediate Messages may arrive during this state.
  3. input-required — the agent is blocked and needs more information from the client before it can continue.
  4. completed — the task finished successfully. Artifacts are now available.
  5. failed — the task ended with an error. Check the Message history for the reason.
  6. canceled — the client or agent stopped the task before it finished.

The normal happy path is: submitted → working → completed. The input-required state is a pause, not a failure — the client sends another Message and the task resumes.

How This Breaks in Practice

Common failure modes to watch for

  • Treating a task as fire-and-forget. If you never poll or listen for status updates, you'll miss the input-required state and the task will stall silently.
  • Confusing Messages with Artifacts. Messages are the conversation; Artifacts are the deliverables. Reading only Messages means you'll miss the actual output.
  • Sending the wrong Part kind. Putting a JSON object inside a text Part (as a string) instead of a data Part breaks any agent that tries to parse the schema.
  • Ignoring the failed state. A task can move to failed without throwing an exception on the client side. Always check status before reading Artifacts.
  • Assuming completed means Artifacts exist. A task can complete with zero Artifacts if the agent's output was delivered only through Messages. Check artifacts length before accessing index 0.

Verifying AI-generated A2A task code — check these specifics before trusting it:

  • Does every Message have a role field set to exactly "user" or "agent"? AI often omits it.
  • Does every Part have a kind field ("text", "data", or "file")? A missing kind makes the Part unreadable.
  • Is the code checking task status before reading Artifacts? AI-generated code often skips the status guard.
  • Does the code handle the input-required state, or does it only branch on completed and failed? A missing branch stalls the task.
  • Are Artifacts stored separately from Messages in the payload? AI sometimes nests Artifacts inside a Message by mistake.

HTTP is the same protocol your browser uses to load a web page. JSON is just structured text — key-value pairs the agent can read. No special transport is needed beyond those two basics.

The remote agent reads the request, starts the work, and immediately returns a Task object with a status field. That status tells the client whether the work is done, still running, or failed.

The three pieces every Task request carries

  • A — the instruction or input, with one or more (text, data, or a file reference).
  • Optional metadata — such as a session ID for multi-turn conversations.

When the work is short, the remote agent can return the finished right inside the same response. When it takes longer, the response status will be working — and that's where streaming comes in.

Streaming Updates with SSE

In plain wordsSSE is like a live sports ticker — the server keeps the connection open and pushes each score update the moment it happens, instead of making you refresh the page.

SSE stands for Server-Sent Events. It is a standard web technology that lets a server push a stream of small messages down a single open HTTP connection.

Without , the client would have to keep asking "are you done yet?" — a pattern called polling. Polling wastes requests and adds delay. SSE removes both problems.

. The client reads each event as it arrives and updates its view of the Task.

The stream ends when the remote agent emits a final event whose status is completed (or failed). At that point the client closes the connection and processes the final Artifact.

Answer: no — a fast task can return its result directly in the HTTP response body, status completed. SSE is only needed when the work takes long enough that the client would otherwise have to wait or poll.

How This Breaks in Practice

Common failure modes

  • Stream drops mid-task. A network hiccup closes the SSE connection before the completed event arrives. The client must detect the disconnect and decide whether to re-open the stream or treat the task as failed.
  • Task ID collision. If two requests accidentally share the same task ID, the remote agent may overwrite or confuse the two jobs. Always generate IDs that are globally unique (e.g. a UUID).
  • Status stuck on working forever. The remote agent may crash silently without emitting a failed event. Add a client-side timeout: if no event arrives within N seconds, treat the task as failed.
  • Ignoring the failed status. A common beginner mistake is only checking for completed. Always handle failed explicitly — otherwise errors pass silently.
  • Large Artifacts in the stream. Streaming a very large file as inline content can exhaust memory. Check whether the remote agent supports file references (a URL) instead of inline bytes.
Non-obvious: SSE connections are one-way — the server pushes, the client only listens. If you need to send more input mid-task (a multi-turn conversation), you send a new HTTP POST with the same task ID, not a message back through the SSE stream.

When an AI tool writes your Task-sending code, run through this checklist before using it:

  1. Does it handle both completed and failed statuses? If only one is checked, errors will be swallowed silently.
  2. Does it skip blank SSE lines? Blank lines are keep-alive signals, not data. Processing them as JSON will crash the parser.
  3. Is the task ID unique per request? A hardcoded or sequential ID will cause collisions under concurrent use.
  4. Is there a timeout or disconnect handler? Without one, a silent remote crash will hang the client forever.
  5. Does it use the task ID in the stream URL? A generated URL that points to a generic endpoint instead of /tasks/{id} will receive the wrong events.

Three Protocols, Three Problems

In plain wordsThink of it like a company: A2A is two managers delegating projects to each other, MCP is a manager plugging into a shared filing cabinet and toolbox, and a REST API is a vending machine — you press a button and get a fixed result.

You've now seen how A2A handles the full lifecycle of a — from discovery to streaming results. But A2A isn't the only protocol in the room, and using the wrong one creates real problems.

Each protocol was built to solve a different integration problem. Mixing them up leads to over-engineering (using A2A for a simple database lookup) or under-engineering (using a plain REST call for work that needs autonomous decision-making).

  • — one autonomous agent delegates a goal to another autonomous agent. The receiving agent decides how to accomplish it.
  • — an AI host connects to tools, data sources, and context at runtime. The host calls the tool; the tool doesn't think for itself.
  • REST API — ordinary application code calls a service with a fixed request and gets a fixed response. No autonomy, no lifecycle, no discovery.

The key question to ask is: who is doing the thinking? If an agent is thinking on the other end, reach for A2A. If a tool is just executing, reach for MCP. If it's plain app code calling a service, use REST.

Comparing the Three Across Four Dimensions

In plain wordsAutonomy is like the difference between hiring a contractor (A2A), renting a power tool (MCP), and pressing a button on a photocopier (REST).

Four dimensions help you compare the protocols clearly: autonomy, discovery, task lifecycle, and typical use case.

1. Autonomy

  • A2A: the remote agent decides how to complete the goal. The client agent only sets the objective.
  • MCP: the AI host decides what to call; the tool just executes the instruction.
  • REST: no autonomy on either side — the caller sends a fixed request and gets a fixed response.

2. Discovery

  • A2A: agents publish an that describes their skills. A reads it at runtime.
  • MCP:tools/list at connection time to discover available tools dynamically.
  • REST: no runtime discovery. The caller knows the endpoint in advance from documentation or an OpenAPI spec.

3. Task Lifecycle

  • A2A: full — submitted, working, input-required, completed, failed. Supports and push notifications.
  • MCP: request/response per tool call. No persistent task state across calls.
  • REST: stateless request/response. Any state must be managed by the caller.

4. Typical Use Case

  • A2A: a planning agent delegates a research sub-task to a specialist research agent.
  • MCP: an agent calls a web-search tool or reads a document from a knowledge base.
  • REST: an app fetches a user's account balance from a banking service.

How This Breaks in Practice

Protocol mismatches are one of the most common sources of wasted effort in agent systems. Here are the failure modes to watch for.

Using A2A where REST would do

Wrapping a simple, deterministic service in A2A adds a full and discovery overhead for no benefit. The result is slower, harder to debug, and harder to maintain.

Using REST where A2A is needed

Calling an autonomous agent with a plain REST request means you lose task state, streaming, and the ability to handle input-required pauses. The caller has no way to know if the agent is still working or has failed silently.

Confusing MCP tools with A2A agents

An MCP tool executes a single instruction — it doesn't plan or decide. If you treat a tool as an agent (expecting it to break down a goal), it will return a raw result with no reasoning applied.

Agent Cards leaking sensitive capabilities

Public should be sparse. Listing internal tools or data sources in a public card exposes your system's attack surface to anyone who can read the card.

Non-obvious: MCP has no built-in permission model. A tidy tool schema doesn't mean the tool is safe to call — the host must still enforce scoping, approval, and revocation.

When an AI tool generates the integration code for you, check these things before trusting it:

  • Is the right protocol used for each call? Confirm that agent-to-agent delegation uses A2A, tool calls use MCP, and deterministic service calls use REST — not a single pattern applied everywhere.
  • Does the A2A call handle task lifecycle states? Check that the code handles working, input-required, and failed — not just completed.
  • Does the MCP tool call validate its inputs? A schema validates shape, not intent. Check that the host enforces what the tool is allowed to access.
  • Is the Agent Card URL correct and scoped? Verify the URL points to the right agent and that the card doesn't expose internal capabilities it shouldn't.
  • Are REST calls truly stateless? If the generated code stores state between REST calls on the server side, it's hiding a lifecycle that should be explicit.

Decision checklist

  • Identify whether your integration involves two autonomous agents delegating work to each other (→ A2A is the right fit).
  • Check whether an agent needs to reach out to a tool, database, or external data source for context (→ MCP is the right fit).
