🧭 The whole landscape in one picture

There is no "best database." There is only "best fit for this access pattern." The trick is knowing what shape your data and your reads/writes are.

The one-sentence mental model

A database is optimized software for storing data and getting it back fast in a particular shape. Different databases make different bets about that shape — rows & joins, huge key lookups, nested JSON, similarity of meaning, relationships, full-text, or points-in-time. Pick the bet that matches how you'll read the data, not just how you'll write it.

Two words you'll hear constantly: SQL vs NoSQL, and ACID vs BASE

SQL vs NoSQL
  • SQL / Relational — rigid table schema, related via joins, one query language (SQL). Great when data is structured and correctness matters.
  • NoSQL — an umbrella for "not-relational": key-value, document, wide-column, graph, vector. Traded strict schema/joins for scale, flexibility, or special access patterns.
ACID vs BASE (consistency models)
  • ACID — a transaction fully succeeds or fully fails; data is always consistent. Banks, billing. (Postgres, MySQL, DynamoDB txns.)
  • BASE / eventual consistency — writes propagate slowly; you might read slightly stale data for a moment, in exchange for huge scale & uptime. (Cassandra, DynamoDB default.)
💬 Why did Claude recommend DynamoDB on AWS? Short version: you likely needed fast lookups by a known key (user id, session id) at any scale, with zero server management, that plugs straight into other AWS services. The Key-Value & DynamoDB tab explains exactly when that's the right call — and when it quietly becomes the wrong one.

🏛️ Relational Databases (SQL)

The default, boring, correct choice for structured data. If you're not sure, start here.

Definition

Data lives in tables — rows (records) and columns (fields) with a fixed schema. Tables link to each other through keys (e.g. an orders.user_id points at users.id). You query with SQL, a declarative language shared across all of them.

Key features

ACID transactions Joins across tables Strong schema & constraints Uniqueness (no dup emails) Powerful ad-hoc queries Mature, battle-tested

Providers

Engines
PostgreSQL — the modern defaultMySQL / MariaDBSQLite (embedded)SQL Server, Oracle
Managed cloud
AWS RDS / AuroraGoogle Cloud SQL / AlloyDBAzure DatabaseSupabase (Postgres+auth)Neon (serverless PG)PlanetScale (MySQL)
Postgres is so extensible it doubles as a vector DB (pgvector), JSON store, time-series (TimescaleDB), and geo DB. For many startups, "just use Postgres" is the correct answer for a surprisingly long time.

When to use / when not to

✅ Use when
  • Data is structured & the shape is stable (users, orders, invoices)
  • Records relate to each other and you'll join them
  • Correctness matters — money, inventory, "no two users with same email"
  • You want flexible reporting queries later (analytics, admin panels)
🚫 Avoid / rethink when
  • Every record has wildly different fields (→ document)
  • You need >100k writes/sec globally with simple key access (→ wide-column / DynamoDB)
  • The core query is "similar meaning" or "graph traversal" (→ vector / graph)
  • You just need a fast expiring cache (→ Redis)

Sample queries (SQL)

-- Create the user right after signup
INSERT INTO users (email, full_name, password_hash, plan)
VALUES ('alex@example.com', 'Alex Doe', '$2b$12$Kx…9f', 'pro')
RETURNING id;

-- Fetch a user by email at login
SELECT id, full_name, password_hash, plan
FROM users WHERE email = 'alex@example.com';

-- The "relation": join users with their subscription
SELECT u.full_name, u.plan, s.status, s.renews_at
FROM users u
JOIN subscriptions s ON s.user_id = u.id
WHERE s.status = 'active';

-- Transaction: upgrade plan + record payment, all-or-nothing (ACID)
BEGIN;
  UPDATE users SET plan = 'enterprise' WHERE id = 2;
  INSERT INTO subscriptions (user_id, status, amount_usd)
    VALUES (2, 'active', 499.00);
COMMIT;

🔑 Key-Value Stores & DynamoDB

The world's biggest, fastest hash map. You hand it a key, it hands back a value — at any scale. This is the family Claude likely recommended.

Definition

A giant dictionary: every item is found by its primary key. There are no joins and (mostly) no "search by other fields" — you look things up by the key you already know. In exchange you get predictable single-digit-millisecond speed no matter how much data you have, and effortless horizontal scaling.

Key features

O(1) lookup by key Massive horizontal scale Serverless / auto-scaling TTL auto-expiry Flexible per-item fields

Providers

AWS DynamoDB (managed, serverless) Redis (in-memory, also cache) Azure Cosmos DB Google Firestore / Bigtable Cloudflare KV / Workers Riak, etcd (config)
DynamoDB is AWS's fully-managed key-value + document store. "Fully managed" = no servers, no patching, no sharding by hand. It auto-scales and you pay per request or per provisioned capacity.

How it stores it — sessions & agent state keyed by id

Each row is found instantly by its key. The value can be a simple string or a rich JSON item (DynamoDB-style).

When to use / when not to — the DynamoDB decision

✅ Use when
  • Your #1 access pattern is "get item by known id" (session, user profile, cart, agent thread)
  • You want zero ops & automatic scaling (serverless on AWS)
  • Traffic is spiky or huge; you need consistent latency
  • You're already deep in AWS (Lambda, API Gateway, IAM integration is seamless)
  • You need per-item TTL (auto-delete expired sessions)
🚫 Avoid / painful when
  • You need flexible ad-hoc queries & joins ("all pro users in Pune who paid last month")
  • Access patterns are still changing — DynamoDB rewards designing keys up front
  • You want SQL & a rich reporting layer (→ Postgres)
  • Complex analytics / aggregations (it's not built for that)
⚠️ The classic DynamoDB trap: it's fantastic if you know your queries in advance and design your keys around them. It's miserable if you later need to slice data a new way — you may need to add "secondary indexes" or duplicate data. Relational DBs let you query any which way after the fact; DynamoDB trades that flexibility for scale & speed. That trade-off is the whole decision.

Sample queries

// DynamoDB via AWS SDK (JavaScript) — write & read by key
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, PutCommand, GetCommand, QueryCommand }
  from "@aws-sdk/lib-dynamodb";

const db = DynamoDBDocumentClient.from(new DynamoDBClient({}));

// Save one chat message
await db.send(new PutCommand({
  TableName: "ChatMessages",
  Item: { pk: "THREAD#abc123", sk: "MSG#2026-08-12T09:00:01",
          role: "user", content: "Summarize my invoices" }
}));

// Get a single item by its full key
const { Item } = await db.send(new GetCommand({
  TableName: "Sessions", Key: { pk: "session:8f2a-77c1" }
}));

// Query ALL messages in one thread, in time order (partition + sort key)
const { Items } = await db.send(new QueryCommand({
  TableName: "ChatMessages",
  KeyConditionExpression: "pk = :t AND begins_with(sk, :m)",
  ExpressionAttributeValues: { ":t": "THREAD#abc123", ":m": "MSG#" }
}));
# Redis (key-value + cache) — Python
import redis
r = redis.Redis()

r.set("session:8f2a-77c1", user_json, ex=3600)   # auto-expire in 1h
r.get("session:8f2a-77c1")
r.incr("ratelimit:user:1")                          # atomic counter
r.expire("ratelimit:user:1", 86400)

📄 Document Databases

Store JSON directly. Each record ("document") can have its own shape. Feels natural to app developers.

Definition

Instead of rigid tables, you store documents — nested JSON-like objects — grouped in collections. There's no fixed schema, so two documents in the same collection can have different fields. You can query on any field, including nested ones and arrays.

Key features

Flexible / no rigid schema Nested objects & arrays Query on any field Maps to app objects 1:1 Horizontal scaling (sharding)

Providers

MongoDB (self-host or Atlas cloud) Google Firestore (great for mobile/realtime) AWS DocumentDB Azure Cosmos DB CouchDB / PouchDB (offline sync)
Postgres can also store & index JSON (jsonb), giving you 80% of document flexibility while keeping SQL & transactions. Often the pragmatic middle ground.

How it stores it — a products collection

Look how each document has different fields. A T-shirt has sizes; a laptop has specs. No schema migration needed to add a new attribute.

{ "_id": "prod_1001", "name": "Cotton T-Shirt", "price": 19.99, "tags": ["apparel", "summer"], "sizes": ["S", "M", "L"], "stock": { "S": 12, "M": 40, "L": 7 } } { "_id": "prod_1002", "name": "14" Laptop", "price": 1299, "tags": ["electronics"], "specs": { "ram": "16GB", "cpu": "M3", "ssd": "512GB" }, "warranty_months": 24 } { "_id": "prod_1003", "name": "E-book: SQL Basics", "price": 9.99, "tags": ["digital"], "download_url": "https://…", "pages": 240 }

When to use / when not to

✅ Use when
  • Records vary in shape or evolve fast (catalogs, CMS, user-generated content)
  • Your data is naturally nested (an order with line-items inside it)
  • You want to move fast without schema migrations
  • You mostly read/write whole documents at once
🚫 Avoid when
  • Data is highly relational with many joins (→ SQL)
  • You need multi-document transactions everywhere (possible but not the sweet spot)
  • Strong consistency & complex reporting are central (→ SQL)
  • The "flexible schema" becomes "no one knows the schema" — discipline required

Sample queries (MongoDB)

// Insert a document — any shape you like
await db.products.insertOne({
  _id: "prod_1001", name: "Cotton T-Shirt",
  price: 19.99, tags: ["apparel"], sizes: ["S","M","L"]
});

// Find all products under $20 tagged "apparel"
await db.products.find({
  price: { $lt: 20 },
  tags: "apparel"
});

// Query a NESTED field (stock of size M > 10)
await db.products.find({ "stock.M": { $gt: 10 } });

// Update: add a field to one doc, no migration needed
await db.products.updateOne(
  { _id: "prod_1002" },
  { $set: { on_sale: true } }
);

🧠 Vector Databases — the AI one

This is what makes agents "know your data." It searches by meaning, not keywords. The backbone of RAG (Retrieval-Augmented Generation) and long-term agent memory.

Definition — in plain English

An embedding model turns any text (or image/audio) into a long list of numbers — a vector — that captures its meaning. Similar meanings produce vectors that sit close together in space. A vector database stores millions of these vectors and, given a query vector, finds the nearest neighbors insanely fast (using an index like HNSW). That's semantic search.

"How do I reset my password?" → embedding model → [0.021, -0.88, 0.13, … 1536 numbers] → find nearest → 📄 "Account recovery guide"
Key features

Semantic / similarity search Approximate nearest neighbor (ANN) Metadata filtering Powers RAG & agent memory Handles text, images, audio

How it stores it — a knowledge base of doc chunks

Each row = one chunk of a document, its embedding vector (shortened here — real ones are 384–3072 numbers), and filterable metadata. A query embeds your question and returns the closest rows by cosine similarity.

chunk_01[0.02, -0.88, 0.13, 0.44, …]📄 doc:"billing-faq" · text:"To reset your password, click…"
chunk_02[0.91, 0.10, -0.22, 0.05, …]📄 doc:"pricing" · text:"The Pro plan costs $29/mo…"
chunk_03[0.03, -0.85, 0.19, 0.40, …]📄 doc:"account" · text:"Account recovery is handled via…"
chunk_04[-0.44, 0.67, 0.31, -0.12, …]📄 doc:"api" · text:"Authenticate with a Bearer token…"
chunk_05[0.05, -0.90, 0.11, 0.47, …]📄 doc:"security" · text:"We hash passwords with bcrypt…"
Notice chunk_01, chunk_03, chunk_05 have very similar numbers — they're all about passwords/accounts, so they cluster together. A keyword search for "reset password" would miss chunk_03 ("account recovery") — vector search catches it because the meaning matches.

Providers

Dedicated vector DBs
Pinecone (managed, popular)Qdrant (open-source + cloud)WeaviateMilvus (scale)Chroma (local/dev)
Add-ons to existing DBs
pgvector (Postgres)Redis vector searchMongoDB Atlas VectorElasticsearch kNNAzure AI Search
💡 Starting out? Use pgvector if you already have Postgres — one less system to run. Reach for Pinecone/Qdrant/Milvus when you have tens of millions of vectors or need specialized scale & latency.

When to use / when not to

✅ Use when
  • Building RAG — let an LLM answer using your docs
  • Long-term agent memory ("remember what the user told me weeks ago")
  • Semantic search, recommendations, dedup, "find similar"
  • Matching by meaning where keywords fail (synonyms, paraphrases)
🚫 Avoid / not needed when
  • Exact lookups or structured filters are enough (→ SQL/key-value)
  • You need precise keyword/boolean matching (→ search DB, or hybrid)
  • Tiny dataset — a plain array + cosine similarity in code may do
  • It's not a system of record — keep source text/metadata elsewhere too

Sample queries

# Pinecone (Python) — the core RAG loop
from openai import OpenAI
from pinecone import Pinecone

oa = OpenAI();  pc = Pinecone();  index = pc.Index("kb")

# 1) Embed & store a document chunk
vec = oa.embeddings.create(model="text-embedding-3-small",
        input="To reset your password, click Forgot Password…").data[0].embedding
index.upsert([("chunk_01", vec, {"doc": "billing-faq"})])

# 2) At query time: embed the question, find nearest chunks
q = oa.embeddings.create(model="text-embedding-3-small",
        input="how do I recover my account?").data[0].embedding
hits = index.query(vector=q, top_k=3,
        filter={"doc": {"$ne": "archived"}},  # metadata filter
        include_metadata=True)

# 3) Feed the retrieved text to the LLM as context (RAG)
context = "\n".join(h.metadata["text"] for h in hits.matches)
-- pgvector (Postgres) — same idea, in SQL
CREATE EXTENSION vector;
CREATE TABLE chunks (id text, embedding vector(1536), doc text, body text);

-- <=> is cosine distance; ORDER BY it to get nearest neighbors
SELECT id, body
FROM chunks
ORDER BY embedding <=> '[0.02,-0.88, …]'
LIMIT 3;

🕸️ Graph Databases & Neo4j

When the relationships are the point — "who knows whom," "what depends on what," knowledge graphs for agents. Is Neo4j good? Yes — and here's when to actually use it.

Definition

Data is stored as nodes (things: people, docs, tickets) connected by edges/relationships (verbs: KNOWS, REPORTS_TO, MENTIONS). Both nodes and edges can carry properties. The database is optimized to traverse these connections — "friends of friends," "3 hops away" — which would be brutal multi-join queries in SQL.

Key features

Fast multi-hop traversals Relationships are first-class Pattern matching queries Great for knowledge graphs Path finding (shortest route)

Providers & options

Property graph (nodes + edges)
Neo4j (the leader, Cypher query lang)Amazon NeptuneArangoDB (multi-model)Memgraph (in-memory, fast)TigerGraph (scale)
RDF / triple stores (semantic web)
GraphDBBlazegraphAmazon Neptune (also RDF)
Also worth knowing: Postgres can model simple graphs with recursive queries, and Apache AGE adds Cypher to Postgres. Fine for shallow graphs; a real graph DB wins as hops & scale grow.

How it stores it — a knowledge graph

Nodes (circles) and relationships (arrows). This is exactly the structure agents use for "knowledge graph memory" — entities and how they relate.

Ask "which tickets block a ticket assigned to someone who reports to Meera?" — that's a 3-hop traversal, trivial in a graph DB, ugly in SQL.

When to use / when not to

✅ Use when
  • Relationships & traversals are the main question (social, org charts, dependencies)
  • Knowledge graphs for agents / GraphRAG (entities + how they connect)
  • Fraud rings, recommendations, "shortest path," impact analysis
  • The connections go many hops deep and vary in length
🚫 Avoid when
  • Your data is mostly flat records with few relationships (→ SQL)
  • You need heavy aggregations / analytics over columns (→ SQL/warehouse)
  • Team has no graph experience & the graph is shallow (Postgres joins fine)
  • Simple parent→child hierarchy only (a foreign key does it)
🤖 For agents specifically: "GraphRAG" combines a graph DB (structured relationships) with a vector DB (semantic recall). The graph answers "how are these entities connected," the vectors answer "what's relevant to this question." Increasingly common in serious agent memory systems.

Sample queries (Neo4j — Cypher)

// Create nodes and a relationship
CREATE (a:Person {name:'Alex'})-[:REPORTS_TO]->(m:Person {name:'Meera'});

// Alex works on a ticket, tag it
MATCH (a:Person {name:'Alex'})
CREATE (a)-[:WORKS_ON]->(t:Ticket {id:'PIXB-42'})-[:TAGGED]->(:Label {name:'backend'});

// The magic: multi-hop pattern match
// "Tickets that block a ticket assigned to someone reporting to Meera"
MATCH (m:Person {name:'Meera'})<-[:REPORTS_TO]-(p:Person)
      <-[:ASSIGNED]-(t:Ticket)<-[:BLOCKS]-(blocker:Ticket)
RETURN blocker.id, t.id, p.name;

// Shortest path between two people
MATCH p = shortestPath(
  (a:Person {name:'Alex'})-[:KNOWS*]-(z:Person {name:'Priya'}))
RETURN p;

📊 Wide-Column Stores

Built for firehose write volume at global scale. Think "spreadsheet with billions of rows and flexible columns per row."

Definition

Rows are grouped by a partition key and, within a partition, sorted by clustering columns. Unlike SQL, each row can have different columns, and data is spread ("sharded") across many machines automatically. Optimized for huge write throughput and predictable reads by key — with tunable consistency.

Key features

Linear horizontal scale Write-optimized Tunable consistency No single point of failure Time-ordered data friendly

Providers

Apache Cassandra (open-source) ScyllaDB (faster C++ Cassandra) Google Bigtable HBase (Hadoop) DataStax Astra (managed Cassandra)
DynamoDB is philosophically close (partition + sort key, massive scale). Rule of thumb: pick these when you're past what a single big Postgres box can handle and your access is key-based.

How it stores it — chat events, partitioned by room

All messages for one room live together (same partition key), sorted by time (clustering column) so "latest 50 in this room" is one fast sequential read.

room_id (partition)ts (clustering ↓)usermsg+ ad-hoc cols
room#pune-eng09:00:01.221alex"deploy done"—
room#pune-eng09:00:04.870meera"👍"reaction=true
room#pune-eng09:01:12.004sam"link?"edited=false
room#design09:00:02.100priya"new mocks up"attachment=fig.png
room#design09:03:44.512tom"loving it"—

When to use / when not to

✅ Use when
  • Enormous write volume — telemetry, chat, feeds, IoT, event logs
  • Global, always-on, must survive node/datacenter failure
  • Access is by partition key + time range
  • You'll outgrow a single relational server
🚫 Avoid when
  • You need joins, ad-hoc queries, or transactions (→ SQL)
  • Data volume is modest — this is operational overkill
  • Access patterns aren't known up front (like DynamoDB, design keys first)
  • Strong immediate consistency everywhere is required

Sample queries (Cassandra — CQL, looks like SQL)

-- Table designed around the query: "messages in a room, newest first"
CREATE TABLE messages (
  room_id text,
  ts      timestamp,
  user    text,
  msg     text,
  PRIMARY KEY ((room_id), ts)          -- partition key, clustering key
) WITH CLUSTERING ORDER BY (ts DESC);

INSERT INTO messages (room_id, ts, user, msg)
VALUES ('room#pune-eng', toTimestamp(now()), 'alex', 'deploy done');

-- Fast: hits ONE partition, reads sequentially
SELECT user, msg, ts FROM messages
WHERE room_id = 'room#pune-eng'
LIMIT 50;

-- ✗ This would be REJECTED — no filtering on non-key columns at scale
-- SELECT * FROM messages WHERE user = 'alex';  (design a new table instead)

🔎 Search Engines

Full-text search with typo tolerance, ranking, and filters. What powers "search-as-you-type" and site search.

Definition

A search engine builds an inverted index — a map from every word to the documents containing it — so it can find matches in milliseconds across huge corpora. It adds relevance ranking (BM25), typo tolerance, synonyms, facets (filter counts), and highlighting. Different from vector search: this is keyword-based (though modern engines do both — "hybrid search").

Key features

Inverted index Relevance ranking (BM25) Typo / fuzzy tolerance Facets & filters Highlighting & autocomplete

Providers

Elasticsearch / OpenSearch (the standard) Typesense (fast, simple, OSS) Meilisearch (dev-friendly) Algolia (managed, instant search) Postgres full-text (tsvector) for light needs
Elasticsearch/OpenSearch also do log analytics (the "ELK stack") and kNN vector search — often it's the one engine doing search + observability + hybrid retrieval.

How it stores it — inverted index for a product catalog

Left: the documents. Right: the inverted index it builds — each word points to the docs (and positions) where it appears, which is why lookups are instant.

When to use / when not to

✅ Use when
  • User-facing search boxes: catalogs, docs, help centers
  • Typo tolerance, autocomplete, "did you mean," faceted filtering
  • Log/event analytics at scale (ELK/OpenSearch)
  • Hybrid search (keywords + vectors together) for RAG quality
🚫 Avoid when
  • It's your only store — it's a secondary index, not a source of truth
  • You need transactions / strong consistency (index lags writes slightly)
  • Simple exact lookups (a DB index is enough)
  • Pure semantic matching with no keywords (→ vector DB)

Sample queries (Elasticsearch)

# Index a document

{ "title": "Red cotton t-shirt", "price": 19.99, "color": "red" }

# Fuzzy full-text search + filter + facet, ranked by relevance
POST /products/_search
{
  "query": {
    "bool": {
      "must":   { "match": { "title": { "query": "cottn shrt", "fuzziness": "AUTO" } } },
      "filter": { "range": { "price": { "lte": 25 } } }
    }
  },
  "aggs": { "by_color": { "terms": { "field": "color" } } }   # facet counts
}
# "cottn shrt" (typos) still matches "Red cotton t-shirt" thanks to fuzziness

⏱️ Time-Series Databases

Purpose-built for "measurements over time" — metrics, IoT, and (for us) tracking every LLM call your agent makes.

Definition

Optimized for data that's timestamped, append-only, and queried by time windows. They compress heavily (values change little second to second), handle millions of writes/sec, and make time aggregations ("average latency per minute over the last day") trivial and fast — where a relational DB would choke.

Key features

Time-window queries & rollups Extreme compression Downsampling & retention policies High-ingest / append-only

Providers

InfluxDB TimescaleDB (Postgres extension) Prometheus (metrics/monitoring) Amazon Timestream VictoriaMetrics, QuestDB
Already on Postgres? TimescaleDB gives you time-series superpowers without a new database or query language. Nice default.

How it stores it — LLM call telemetry

Each point = a timestamp + tags (labels you filter/group by) + fields (the numbers). Perfect for an agent's observability: latency, tokens, cost per call.

When to use / when not to

✅ Use when
  • Metrics, monitoring, IoT sensors, financial ticks
  • Agent observability: latency/token/cost dashboards over time
  • High write rate, queried as time ranges & aggregates
  • You need auto-retention ("drop raw data older than 30 days")
🚫 Avoid when
  • Data isn't fundamentally about time
  • You need to update/delete individual old records often
  • Rich relational joins are the point (→ SQL)

Sample queries

-- TimescaleDB / SQL: avg latency & total cost per model, per minute (last hour)
SELECT time_bucket('1 minute', time) AS minute,
       model,
       avg(latency_ms)  AS avg_latency,
       sum(cost_usd)    AS spend
FROM llm_calls
WHERE time > now() - interval '1 hour'
GROUP BY minute, model
ORDER BY minute DESC;
# InfluxDB (Flux) — p95 latency for opus over 24h, 5-min windows
from(bucket: "agent")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "llm_calls" and r.model == "opus")
  |> aggregateWindow(every: 5m, fn: (tables=<-, column) =>
        tables |> quantile(q: 0.95))

⚡ Cache / In-Memory Stores

Not always a "database" — a speed layer. Keeps hot data in RAM for sub-millisecond access. Redis is the swiss-army knife here.

Definition

Data lives in memory (RAM) instead of disk, so reads/writes are microsecond–millisecond fast. Usually a key-value model, often used in front of a slower database to absorb repeated reads. Data may be volatile (lost on restart) or optionally persisted. Redis also offers rich types: lists, sets, sorted sets, streams, pub/sub, and TTLs.

Key features

Sub-millisecond latency TTL / auto-expiry Rich data types & atomic ops Pub/sub & queues Rate limiting, locks, leaderboards

Providers

Redis / Valkey (the standard) Memcached (simple caching) AWS ElastiCache / MemoryDB Upstash (serverless Redis) Redis Cloud, Dragonfly
Redis is so versatile it moonlights as cache, session store, queue, rate-limiter, pub/sub bus, and even a vector index. In agent apps it's often the "working memory" layer.

When to use / when not to

✅ Use when
  • Caching expensive DB/LLM results (huge cost & latency wins)
  • Sessions, rate limiting, distributed locks, feature flags
  • Real-time leaderboards, counters, queues, pub/sub
  • Agent "working memory" / short-lived state between steps
🚫 Avoid when
  • It's your only copy of important data (RAM is expensive & volatile)
  • You need complex queries, joins, or big historical datasets
  • Data far exceeds RAM budget (memory is pricey)

Sample: cache-aside pattern

# Classic "cache-aside": check cache first, fall back to DB, then cache it
def get_user(uid):
    cached = r.get(f"user:{uid}")
    if cached:
        return json.loads(cached)          # fast path (<1ms)
    user = db.query("SELECT … FROM users WHERE id=%s", uid)  # slow path
    r.set(f"user:{uid}", json.dumps(user), ex=300)   # cache 5 min
    return user

# Rate limit: allow 100 requests/min per user, atomically
key = f"rl:{uid}:{minute}"
count = r.incr(key)
if count == 1: r.expire(key, 60)
if count > 100: raise RateLimited()

How a single user question flows through them

1. Request hits API→ 2. Redis: check session + rate limit→ 3. Postgres: who is this user, what plan→ 4. DynamoDB: load conversation history→ 5. Vector DB: retrieve relevant docs (RAG)→ 6. Neo4j: pull related entities→ 7. LLM answers→ 8. DynamoDB: save the new turn→ 9. TimescaleDB: log latency/tokens/cost

Rules of thumb to remember

  • Start with Postgres. It stretches further than you think (JSON, vectors via pgvector, time-series via Timescale, geo). Add specialized DBs only when a real access pattern demands it.
  • Match the DB to the read pattern, not the write. Ask "how will I get this back out?"
  • Key-value / DynamoDB = you know the key & want scale + zero ops. Design keys around queries up front.
  • Vector = "find things that mean the same." The heart of RAG & agent memory.
  • Graph = the relationships are the query, many hops deep.
  • Every extra database is operational cost. Fewer, well-chosen stores beat a zoo of trendy ones.

Managed vs self-hosted, quickly

  • Managed / serverless (DynamoDB, Aurora, Pinecone, Atlas, Upstash): they run it, patch it, scale it. You pay more per unit but save enormous ops time. Best default for small teams.
  • Self-hosted (Postgres on a VM, Cassandra cluster, Neo4j on-prem): cheaper at scale, full control, more responsibility (backups, upgrades, failover). Choose when cost/control/compliance justifies the ops burden.
On AWS, the "recommend DynamoDB" instinct is really "you're on AWS, you need a scalable keyed store, and you don't want to babysit servers." Perfectly valid — just make sure your queries fit the key-value model before committing.
