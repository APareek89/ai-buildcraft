Questions you were probably about to ask

Does tomorrow's session load yesterday's summary?

No. The compaction summary is a space-saving artifact of session 1's view. When a new session starts, its message list starts empty. The summary stays in the DB attached to s1 — used only if the product offers "resume yesterday's conversation" (which literally means: reload s1's view and keep going). The bridges between days are: the profile (long-term memory), episodes (if recalled), and state (cart, orders — fetched by tools).

Then how did the agent know about the Herrera brogues on Day 2?

Two honest routes, and neither is "it remembered the conversation": (1) the user's question forced a get_cart tool call — the cart is state in the commerce backend, and it still holds the Herrera; (2) the episode written at session end ("researched brogues, chose Herrera") can be recalled if the new query is similar. The transcript itself was never loaded.

Is the model remembering anything between API calls?

Nothing. The API is stateless. The only reason turn 12 "remembers" turn 3 is that your code re-sends turns 1–11 (or their summary) with every call. That's why the middle panel is rebuilt at every step — that rebuild IS the memory system.

What if the conversation grows past the budget again after compacting?

Compaction just runs again. The next pass summarizes [old summary + the turns after it] into a new summary row with a higher covers_up_to. A very long conversation ends up as: newest summary + recent turns — always bounded, indefinitely.

Alex said "size 9" on Day 1, turn 4. Why wasn't it in memory immediately?

Because at that moment it lives in the transcript — which is enough for the rest of that session (it's in the context). It becomes long-term memory only when extraction runs at session end and promotes it to the profile. (A production system can also write mid-session when the user says "remember this" — that's an optimization, same pipeline.)

What ever gets deleted?

Raw conversation rows (and their summary rows) — via TTL after the retention window, ~90 days. The profile is never bulk-deleted, only curated: merged, expired ("wedding Sept 14" after Sept 14), decayed (year-old unconfirmed inferences), or deleted on user request. Episodes persist (small). Orders are a business ledger — kept per accounting rules, untouchable by "forget me".

Where do prices live in all this?

Nowhere. Prices are state owned by the catalog system — fetched by a tool inside the turn that needs them, never stored in any memory layer. Stored prices are stale prices.
