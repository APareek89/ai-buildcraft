      Three use cases, three deployment patterns

      This is the most useful idea on the page. The loop is the same, but how you deploy depends on when the answer is needed. There are only three patterns. If you can name which pattern a use case needs, you sound like you have built it.

      Predictive order for sales reps Pattern: nightly batch

      Every night, score every store × SKU for next week. Write the top 10 per store into a table. The Sales App reads the table. Nobody waits for a model at 9am; the answer is already there.

      Demand forecasting for distributors and suppliers Pattern: weekly batch, hierarchical

      Forecast cases per SKU, per region, per week for the next 8–13 weeks. Distributors use it to buy stock and plan trucks. Suppliers use it to plan production. One forecast, many levels.

      The word to use is hierarchical: forecasts at SKU → store → zone → region must add up. You forecast at a level with enough data (SKU × zone), then split down or roll up.

The baseline to beat is seasonal naive — last year same week.

      Delivery arrival and service-time prediction Pattern: real-time API

      A dispatcher plans routes at 6am and a driver's app needs "how long will this stop take" and "when will I reach the next store" while on the road. The answer is needed in under a second, for one stop at a time. That is a real-time endpoint.

      CI/CD for ML: software CI/CD plus two gates

      Software CI/CD tests code and ships it. ML CI/CD does the same, but the thing being shipped is code + data + model. So you add two gates: does the data look right, and is the new model actually better.

      1. Commit codeFeature code, training code, pipeline definition go to Git. A pull request opens.
      2. Code testsUnit tests on feature functions. Lint. Container builds. Same as any software.
      Gate A: data checkSchema unchanged? Row counts normal? No nulls where none expected? Fails → stop.
      3. Train + evaluatePipeline trains on latest data, evaluates on the held-out time period, logs metrics.
      Gate B: model checkBeats baseline? Beats current production model? Within fairness / business rules? Fails → stop, notify.
      4. Register + deployModel registered → staging → shadow or canary → production. Rollback = point to previous version.

      Continuous integration vs continuous delivery vs continuous training

      TermMeansTrigger
      CIEvery code change is tested automatically and built into a container.A commit or pull request.
      CDA tested model moves through staging → production without manual copying.Model passes Gate B.
      CTContinuous training: the pipeline retrains on a schedule or when drift is detected, with no code change.Weekly cron, or a drift alarm.

      Environments

      Dev — data scientists experiment; small data. Staging — same setup as production; the pipeline runs end to end on real data; nothing reaches users. Production — real users. Promotion between them is automatic once gates pass; a human approves only high-risk models (pricing).

      Say thisML CI/CD is normal CI/CD with two extra gates — a data check before training and a model check before deploy. Nothing reaches production unless it beats the baseline and the current model on a time-based holdout. Rollback is pointing the endpoint or the batch job at the previous registered version.

      Monitoring: four layers, one dashboard

      Most teams monitor only the first layer and wonder why the model quietly stops working. Name all four.

      1. System healthDid the job run? Endpoint up? Latency, errors, cost.Alarm: job failed, p95 latency > 300ms.
      2. Data driftAre today's inputs like the training data? Distribution of gap_ratio, share of promo rows, missing store types.Alarm: a feature's distribution shifts (PSI > 0.2).
      3. Prediction driftIs the model saying different things? Average predicted probability, share of stores with zero suggestions.Alarm: mean prediction moves > 20% week on week.
      4. Business outcomeThe truth, once it arrives. Precision@10 vs actual orders. WAPE vs actual demand. Rep acceptance rate. Order value.Alarm: acceptance drops 3 weeks running.

      Why layer 4 arrives late — and what to do about it

      You only know if the order prediction was right after the week ends. Layers 2 and 3 are early-warning signs while you wait for layer 4. For real-time delivery predictions, actuals come within hours; for forecasting, weeks. Design the monitoring to the lag.

      Drift, in plain words

      Data drift: the world changed, the inputs look different. Example: a new tax makes every price feature jump. Concept drift: the inputs look the same but the relationship changed. Example: after a competitor launches, the same gap_ratio no longer means "about to reorder". Data drift is easy to detect; concept drift shows up only in layer 4.

      Say thisI monitor four things: is the system up, do inputs still look like training data, has the model's output distribution moved, and is the business metric holding once actuals arrive. The first three are early warnings for the fourth.

      Improvement: the loop closes

      Where the feedback comes from

      Use caseFeedback signalBecomes
      Order predictionRep accepts / edits / rejects a suggestion; actual order placed.New labels for training + the acceptance KPI.
      Demand forecastActual depletions each week.Backtest error; new training rows.
      Delivery timeActual arrival and departure from the driver app.Labels within hours; canary comparison.

      When to retrain

      On a schedule (weekly for orders, weekly for forecasts, monthly for delivery time) because new data keeps arriving. On a trigger when a drift alarm fires or the business metric drops. On a change when you add a feature or fix data. Every retrain goes through the same gates — retraining is not an excuse to skip evaluation.

      Champion / challenger

      The production model is the champion. Each retrain produces a challenger. The challenger must beat the champion on the same holdout and, for important models, in shadow or canary for a set period. Then it becomes the champion. Old versions stay in the registry for rollback.

      The improvement that is not about the model

      Half of the gains come from outside the model: better data (fix the store master), better features (add promo calendar), better UX (show the reason for a suggestion), better business rules (cap quantities). A CoE lead watches all four, not just accuracy.

      Say thisImprovement is a loop, not a project. Feedback from reps and actuals becomes training data, retraining runs on a schedule and on drift triggers, and every challenger has to beat the champion through the same gates before it ships.

      Questions they will ask, and short answers

      Batch or real-time — how do you decide?

      Ask when the answer is needed and for how many things at once. Needed tomorrow for everyone → batch. Needed now for one thing → real-time. Batch is cheaper and simpler; start there. In the worked distributor example, order prediction and forecasting are batch; delivery time on the road is real-time.

      What is training-serving skew and how do you avoid it?

      The features at training time are computed differently from the features at prediction time, so the model sees data it was never trained on. Avoid it by using the same feature code for both, ideally through a feature store, and by logging what the model actually received in production.

      How do you version a model?

      Three things get versioned together: the code (Git commit), the data (snapshot or date range in S3), and the model file (registry version with metrics). If you cannot rebuild a model from those three, it is not reproducible.

      How do you roll back?

      Point the batch job or endpoint at the previous registered model version. It is a config change, not a rebuild. That only works if every model is in the registry and every deploy is by version number.

      Where does the data live? Do you train on the production database?

      No. Production DBs (Aurora / RDS) serve the product. ML reads a nightly copy in S3 via DMS or Glue. Training on production tables slows the product and mixes concerns.

      What does CI/CD look like for a model?

      Same as software plus two gates: a data validation gate before training and a model evaluation gate before deploy. Code goes through tests and containers; the model goes through registry → staging → canary or shadow → production.

      How do you know the model is still good three months later?

      Four monitoring layers: system health, data drift, prediction drift, and business KPI once actuals arrive. Alerts on each. Scheduled retraining plus drift-triggered retraining, with challengers gated against the champion.

      What would you build first, and what would you skip?

      First: S3 lake, one Glue feature job, one SageMaker training pipeline, the registry, a batch scoring job, CloudWatch alarms, and a dashboard. Skip for v1: feature store, real-time endpoints, custom drift tooling. Add them when the second and third use cases need them.

      How do you handle a high-risk model like pricing?

      Human approval on every recommendation, hard guardrails on price moves, full audit trail (CloudTrail + a decision log table), shadow mode for weeks before anyone sees it, and a manual approval step in the pipeline before production.

      Where does GenAI fit in this stack?

      Same loop, different artifacts. The "model" is a prompt + retrieval index + tool set. Version prompts like code, keep an eval set as the gate, monitor cost and answer quality, and serve through Bedrock behind the same API Gateway. RAG index refresh is the "retraining".

      Glossary — one line each

      Data lake
      Cheap storage of all raw and cleaned data as files. On AWS: S3.
      Warehouse
      A database built for analytics queries over big tables. Redshift, Snowflake, or Athena over S3.
      CDC
      Change data capture — copy only the rows that changed in the source DB. AWS DMS does this.
      Parquet
      A compressed column file format. Standard for lake data.
      Feature
      One input column the model uses, like days_since_last_order.
      Feature store
      A shared library of features with history, so training and serving match.
      Pipeline
      A fixed sequence of steps — ingest, features, train, evaluate, register — run by a scheduler.
      Experiment tracking
      A log of every training run and its results. MLflow, SageMaker Experiments.
      Model registry
      Versioned catalogue of trained models with metrics and approval status.
      Batch inference
      Score many rows at once on a schedule; write results to a table.
      Endpoint
      A model served behind an HTTPS URL for one-at-a-time predictions.
      Latency / p95
      Response time; p95 means 95% of requests are faster than this number.
      Drift
      The data or the relationship the model learned has changed since training.
      PSI
      Population stability index — a number for how much a feature's distribution moved. Above 0.2 is a warning.
      Champion / challenger
      Current production model vs a candidate that must beat it.
      Shadow / canary
      Run new model silently beside the old one / send it a small slice of real traffic.
      Infra as code
      Cloud resources defined in files (Terraform, CDK) so environments are reproducible.
      IAM
      AWS permissions — which role can read which bucket, deploy which model.
      WAPE / MAE / precision@10
      Forecast error as a % of volume / average error in units / share of top-10 suggestions that were correct.
