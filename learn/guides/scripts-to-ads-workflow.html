What is an agentic workflow — and why does it matter here?

In plain wordsAn agentic workflow is like a small production studio: instead of one person doing everything, each specialist handles their lane, and the script moves down the line.
Before reading on, predict: if you had to turn a one-line ad brief into a finished video ad, what distinct jobs would need to happen in order? Hold that answer — you'll see how it maps to the architecture below.

An is a system where one or more AI models plan, act, observe results, and repeat until a goal is complete. Unlike a single chatbot call, the model can use external tools and adapt each next step based on what it learns.

The core unit is an : an wired into a loop with a specific job. It receives input, reasons about it, takes an action, and passes a result forward.

A chains several agents together, each owning one job. An — the director — decides which agent runs next. It also passes — the shared memory of what has happened — between them.

Why not just write one big prompt?

A single giant prompt tries to research, write copy, check brand tone, and generate image instructions at once. That overloads the model, mixes concerns, and makes errors hard to trace. Focused agents can each be tested, swapped, or improved independently. You can also insert a human review step between agents without rebuilding everything.

The four core agent roles in an ad-generation workflow

  • Brief Analyst — reads the raw brief and extracts the goal, audience, and constraints.
  • Script Writer — turns the structured brief into a draft ad script with hooks and a call to action.
  • Brand Reviewer — checks the script against tone-of-voice guidelines and flags off-brand language.
  • Asset Director — converts the approved script into image-generation prompts and layout instructions.

Each role is a separate agent with its own , its own tools, and a clear output contract. The orchestrator holds shared state and routes the script from agent to agent.

How a script travels through the ad-generation workflow

Each step is one agent. The output of each step becomes the input of the next.

Imagine you're a PM at a sportswear brand. Your brief is: "Summer sale, 30% off, target audience 18–35, upbeat and energetic tone, Instagram Story format."

Step 1 — Brief Analyst receives the raw text

The Brief Analyst reads the sentence and outputs a structured object. Result: goal = drive sales, discount = 30%, audience = 18–35, tone = upbeat, format = Instagram Story. This is stored in shared so every downstream agent can read it.

Step 2 — Script Writer drafts the ad

The Script Writer reads the structured brief from state. It produces — Hook: "Summer just got 30% cheaper." Body: "Shop the drop before it's gone." CTA: "Tap to shop now." — saved as draft_v1.

Step 3 — Brand Reviewer checks the draft

The Brand Reviewer compares the draft against the brand's tone guide. It flags "Shop the drop" as too informal and returns a revision note.draft_v2 reads: "Explore the collection before it sells out."

Step 4 — Asset Director generates image prompts

With the approved script in state, the Asset Director writes an image prompt. Output: "Bright outdoor scene, young adult running, bold text overlay '30% OFF', Instagram Story 9:16 ratio, energetic color palette." This prompt is ready to pass to an image-generation tool.

Notice what the orchestrator did: it held shared state, chose which agent ran next, and managed the revision loop — without any agent knowing about the others.
# LangGraph — four-agent ad workflow blueprint
from typing import TypedDict, Optional
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

# --- 1. Define shared state ---
class AdState(TypedDict):
    raw_brief: str
    structured_brief: Optional[dict]
    script_draft: Optional[str]
    review_notes: Optional[str]
    asset_prompt: Optional[str]

# --- 2. Define each agent node ---
llm = ChatOpenAI(model="gpt-4o", temperature=0.3)

def brief_analyst_node(state: AdState) -> AdState:
    """Extract goal, audience, tone from the raw brief."""
    result = llm.invoke(
        f"Extract goal, audience, tone, format as JSON.\nBrief: {state['raw_brief']}"
    )
    state["structured_brief"] = result.content  # simplified; use structured_output in practice
    return state

def script_writer_node(state: AdState) -> AdState:
    """Write hook, body, and CTA from the structured brief."""
    result = llm.invoke(
        f"Write a short ad script (hook, body, CTA).\nBrief: {state['structured_brief']}"
    )
    state["script_draft"] = result.content
    return state

def brand_reviewer_node(state: AdState) -> AdState:
    """Check the draft against brand tone; add revision notes or approve."""
    result = llm.invoke(
        f"Review this ad for brand tone. Reply APPROVED or list issues.\nScript: {state['script_draft']}"
    )
    state["review_notes"] = result.content
    return state

def asset_director_node(state: AdState) -> AdState:
    """Turn the approved script into an image-generation prompt."""
    result = llm.invoke(
        f"Write an image-generation prompt for this ad script.\nScript: {state['script_draft']}"
    )
    state["asset_prompt"] = result.content
    return state

# --- 3. Route: if reviewer flagged issues, loop back ---
def route_after_review(state: AdState) -> str:
    if "APPROVED" in (state["review_notes"] or ""):
        return "asset_director"
    return "script_writer"  # revision loop

# --- 4. Build the graph ---
workflow = StateGraph(AdState)
workflow.add_node("brief_analyst", brief_analyst_node)
workflow.add_node("script_writer", script_writer_node)
workflow.add_node("brand_reviewer", brand_reviewer_node)
workflow.add_node("asset_director", asset_director_node)

workflow.set_entry_point("brief_analyst")
workflow.add_edge("brief_analyst", "script_writer")
workflow.add_edge("script_writer", "brand_reviewer")
workflow.add_conditional_edges("brand_reviewer", route_after_review)
workflow.add_edge("asset_director", END)

app = workflow.compile()

# --- 5. Run it ---
result = app.invoke({"raw_brief": "Summer sale, 30% off, audience 18-35, upbeat, Instagram Story"})
print(result["asset_prompt"])

Use when
Give a job its own agent when it has a distinct input/output contract, needs its own prompt or tool, or must be reviewable and replaceable independently. Examples: brand review, image-prompt generation, legal compliance check.
Avoid when
Don't split a job into its own agent when it's a trivial transformation (e.g. formatting a date), when it shares the exact same context and prompt as the previous step, or when the overhead of passing state outweighs the benefit. Folding two tightly coupled steps into one node is fine.
Rule of thumb
If you'd hire a different specialist for the job in a real agency, it probably deserves its own agent. If it's just the same person doing the next sentence, keep it in one node.

Common failure modes to watch for

  • Infinite revision loops. If the Brand Reviewer never outputs "APPROVED", the graph loops forever between writer and reviewer. Fix: add a max-revision counter in state and route to END (or a human) after N attempts.
  • State pollution. If an early agent writes a vague or malformed value to state, every downstream agent inherits the error. Fix: use typed state (TypedDict or Pydantic) and validate outputs before passing them on.
  • Over-splitting. Creating ten micro-agents for a five-step job adds latency and makes debugging painful. Fix: start with four roles; only split when a node's prompt grows unwieldy or you need independent testing.
  • Missing the human gate. Fully automated ad generation can ship off-brand or legally risky copy without anyone noticing. Fix: add a checkpoint after Brand Review before the Asset Director runs.

How to verify AI-generated workflow code before trusting it

  • Check every edge is wired. Print or draw the compiled graph and confirm no node is an island (no incoming or outgoing edge).
  • Trace the state at each node. Log the state dict after each node runs and confirm the expected field was written and nothing was overwritten unexpectedly.
  • Test the revision loop explicitly. Feed a brief that will fail brand review and confirm the graph loops back — not that it silently skips to asset generation.
  • Confirm the entry point and END are correct. AI-generated LangGraph code often wires the entry point to the wrong node or forgets to add the final edge to END.

Designing your ad schema — what fields to extract

In plain wordsA schema is like a job application form: it decides exactly which boxes must be filled in before the application can move forward.

Before asking an to parse anything, decide what you want back. For a marketing ad, four fields cover most cases.

  • product — the name or short description of what's being advertised.
  • audience — who the ad targets (e.g. "first-time homebuyers").
  • tone — the emotional register: playful, urgent, professional, etc.
  • call_to_action — the one action you want the reader to take next (e.g. "Book a free demo").

Each field needs a type (usually string) and a required flag. Required fields must be present before data moves on. Optional fields can fall back to a sensible default.

From raw script to validated JSON — the parsing pipeline

Imagine your copywriter sends this script for a new fitness app launch:

"FitFlow is the app busy professionals have been waiting for. No gym required — just 15 minutes a day. It's fun, it's fast, and it actually works. Download it free today."

A human instantly reads: product = FitFlow, audience = busy professionals, tone = energetic/playful, CTA = download free. But the image-generation agent needs those as named fields, not buried in a paragraph.

Send the script to an LLM with this prompt: "Extract as JSON: product, audience, tone (one of: playful, urgent, professional, inspirational), call_to_action." The LLM returns:

{ "product": "FitFlow", "audience": "busy professionals", "tone": "playful", "call_to_action": "Download it free today" }

Validation confirms all four fields are present and tone is a valid enum value. The object is written to shared . Every downstream agent — copy refiner, image generator, audience targeter — reads from it directly.

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from pydantic import BaseModel, Field

# 1. Define the schema — the "form" the LLM must fill in
class AdFields(BaseModel):
    product: str = Field(description="Name or short description of the product")
    audience: str = Field(description="Who the ad targets")
    tone: str = Field(description="Emotional register, e.g. playful, urgent")
    call_to_action: str = Field(description="The single action the reader should take")

# 2. Set up the LLM with structured output enforced
llm = ChatOpenAI(model="gpt-4o", temperature=0)
structured_llm = llm.with_structured_output(AdFields)

# 3. Write the extraction prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are an expert marketing analyst. "
               "Extract the ad fields from the script below. "
               "If a field is not clearly stated, infer it from context."),
    ("human", "{script}")
])

# 4. Chain prompt → structured LLM
extraction_chain = prompt | structured_llm

# 5. Run it — result is a validated AdFields object, not raw text
raw_script = (
    "Hey, so we're launching FlowDesk — it's a project tool "
    "for remote teams who hate Jira. Keep it fun and a bit cheeky. "
    "We want people to sign up for the beta."
)
result = extraction_chain.invoke({"script": raw_script})

print(result.product)        # FlowDesk — a project tool for remote teams
print(result.audience)       # remote teams who dislike complex project tools
print(result.tone)           # fun, cheeky
print(result.call_to_action) # Sign up for the beta

How script parsing breaks in practice

Common failure modes

  • Missing field — silent gap. The script never mentions a call-to-action. The LLM invents one or returns an empty string. Downstream agents get a blank field and generate a useless ad.
  • Hallucinated field value. The LLM confidently fills in "audience: millennials" when the script gave no audience signal at all. Validation passes, but the data is wrong.
  • Overly long field. The LLM returns a 200-word "product" description instead of a short label. Downstream copy agents get confused or hit token limits.
  • Schema mismatch on retries. If you retry a failed parse with a slightly different prompt, the LLM may return a different field name (e.g. "CTA" instead of "call_to_action"). Pydantic will reject it, but you need a retry strategy.

Non-obvious failure to watch for

Validation passing doesn't mean the data is correct. Pydantic only checks types and required fields. A tone of "banana" passes validation. Add an enum or Literal type for fields like tone to catch nonsense values early.

Rule of thumb: treat any field the LLM inferred (not explicitly stated in the script) as low-confidence. Log it, flag it, or route it to a human review step before it drives creative decisions.

When an AI tool writes your extraction chain, run through this checklist before wiring it into your workflow.

  • Does the schema mark the right fields as required? Check that product and call_to_action are required, not optional — a missing CTA is a broken ad.
  • Does it use with_structured_output, not just a plain LLM call? A plain call returns raw text; you need the structured wrapper to get a validated object.
  • Does it handle a missing field gracefully? Test with a script that omits the call-to-action. Does it raise a clear error, or silently return an empty string?
  • Are tone values constrained? Check whether tone is a free string or a Literal/enum. Free strings let nonsense values through.
  • Does the prompt include field descriptions? Without Field(description=...) hints, the LLM guesses what each field means and accuracy drops.
Use when
Use strict validation (required fields + enum constraints) when the parsed data feeds automated agents with no human review step — errors must be caught at the gate, not discovered in a live ad.
Avoid when
Avoid strict validation when scripts are exploratory drafts or when a human will review the output anyway — overly strict schemas will reject valid but unusual scripts and slow the team down.
Rule of thumb
Start strict on the fields that directly drive creative output (product, call_to_action). Be lenient on inferred fields (tone) until you have enough real scripts to know what values actually appear.

Prompt design: the copywriter's interface

In plain wordsA prompt is like a creative brief handed to a freelance copywriter — the more clearly it names the audience, tone, and deliverable format, the less you have to fix later.

A is not magic phrasing. It is the interface between what you want and what the produces.

Good prompts split into two layers. The system prompt holds durable instructions that never change: audience, tone, brand rules, and output format. The user message holds per-request data: the parsed script for this specific ad.

Keeping them separate matters because it makes your agent predictable. When the system prompt is stable, the only variable is the input data — so you can test, debug, and improve reliably.

  • Audience — who will read this ad? (e.g. "millennial homeowners aged 28–40")
  • Tone — what feeling should the copy carry? (e.g. "warm, confident, never salesy")
  • Format — what fields must the output contain? (e.g. headline, subheadline, body copy, CTA)
  • Constraints — what is forbidden? (e.g. "no superlatives, max 8 words per headline")

Return copy as structured fields, not freeform text

In plain wordsAsking the LLM for structured output is like asking a chef to plate each dish in a labeled container — you can grab exactly what you need without sorting through a pile.

If the LLM returns a wall of text, the next agent in your workflow has to parse it — and that parsing can break. means asking the model to return a typed object with named fields instead.

You define a — a blueprint that names each field and its type. The model must fill in that blueprint. Your code then reads copy.headline directly, with no string-splitting required.

In Python, you define the schema as a Pydantic model. (which you met in Module 2) patches the LLM client to enforce that schema automatically.

Rule of thumb: every field the downstream agent needs should be its own named field in the schema — not buried inside a single body_copy string.

How the copy agent breaks in practice

Knowing the failure modes before you hit them saves hours of debugging. Here are the most common ones for a copywriter agent.

Common failures

  • Headline drift — the model ignores your character limit and writes a 20-word headline. Fix: add the limit to the schema as a max_length validator.
  • Tone bleed — the model picks up the script's tone (e.g. urgent, fear-based) instead of your brand tone. Fix: state the brand tone explicitly in the system prompt and give a one-sentence example.
  • Freeform leakage — without a schema, the model returns a prose paragraph instead of separate fields. Fix: always use a typed schema; never rely on "please return JSON" in plain text.

Non-obvious failures

  • Schema hallucination — the model fills every field even when the source script doesn't support it, inventing claims. Fix: add a field like confidence: Literal['high','low'] and route low-confidence outputs to human review.
  • Prompt injection via script — a script that contains instruction-like text (e.g. "Ignore previous instructions and…") can hijack the agent. Fix: pass the script as a clearly labeled data block, not inline with instructions.
Watch for: outputs that look correct but contain invented product claims. A schema enforces structure, not factual accuracy. Always validate claims against the source script.

Imagine your parsed script says: "Product: HomeShield insurance. Key benefit: covers floods and fires. Audience: first-time homeowners. Tone: reassuring."

Write a system prompt that never changes: "You are a HomeShield copywriter. Write for first-time homeowners. Tone: warm and reassuring. No superlatives. Return structured fields only."

Pass the parsed script as the user message: "Draft ad copy from this script: [parsed script object]." The model returns headline, body_copy, and cta as separate fields.

# copywriter_node.py  — LangChain + Instructor + LangGraph
from typing import Annotated
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, END
import instructor

# ── 1. Schema: the blueprint for structured copy output ──────────────────────
class AdCopy(BaseModel):
    headline: str = Field(
        ...,
        description="Max 8 words. Warm, benefit-led.",
        max_length=60,          # ~8 words at avg 7 chars
    )
    body_copy: str = Field(
        ...,
        description="2–3 sentences. Reassuring tone. No superlatives.",
    )
    cta: str = Field(
        ...,
        description="Call-to-action button text. Max 5 words.",
    )
    confidence: str = Field(
        ...,
        description="'high' if script supports all claims, else 'low'.",
    )

# ── 2. Patch the LLM client so it enforces the schema ───────────────────────
raw_llm = ChatOpenAI(model="gpt-4o", temperature=0.4)
client  = instructor.from_openai(raw_llm)          # Instructor wraps the client

# ── 3. Durable system prompt (never changes per request) ────────────────────
SYSTEM_PROMPT = """
You are a copywriter for HomeShield insurance.
Audience: first-time homeowners aged 28–40.
Tone: warm, reassuring. Never use superlatives.
Return ONLY the structured fields — no extra prose.
"""

# ── 4. Copywriter node for LangGraph ────────────────────────────────────────
def copywriter_node(state: dict) -> dict:
    parsed_script = state["parsed_script"]   # output from Module 2 parser

    ad_copy: AdCopy = client.chat.completions.create(
        model="gpt-4o",
        response_model=AdCopy,               # TODO: what does this line enforce?
        messages=[
            {"role": "system",  "content": SYSTEM_PROMPT},
            {"role": "user",    "content": f"Draft ad copy from this script:\n{parsed_script}"},
        ],
    )
    return {"ad_copy": ad_copy}

# ── 5. Wire the node into a LangGraph workflow ───────────────────────────────
builder = StateGraph(dict)
builder.add_node("copywriter", copywriter_node)
builder.set_entry_point("copywriter")
builder.add_edge("copywriter", END)
graph = builder.compile()

How the validation loop breaks in practice

Common failure modes

  • Infinite retry loop. If you forget to cap retries, a stubborn failure will loop forever and burn tokens. Always set a MAX_RETRIES constant and test that the escalation path actually fires.
  • Vague failure reasons. If the validator writes "ad is bad" into state, the copywriter has nothing useful to act on. The failure reason must be specific and actionable — treat it like a code error message.
  • State mutation bugs. Each node should return a new state dict ({**state, "key": new_value}), not mutate the existing one. Mutating state in place can cause subtle bugs where old values bleed into the next node.

Non-obvious failure modes

  • Validator drift. If your validator is itself an LLM, it can give inconsistent verdicts — passing the same ad one run and failing it the next. Add deterministic rule checks (word count, keyword presence) as a first gate before the LLM judge.
  • Human checkpoint never resumed. If a reviewer forgets to call graph.invoke() after editing state, the workflow stays paused indefinitely. Build an alert or timeout into your ops process.
  • Retry counter not reset between runs. If you reuse a thread ID across different ad campaigns, the retry counter from a previous run can carry over. Always initialise state fresh for each new job.

Checklist: before trusting AI-generated LangGraph code for this pattern

  1. Does the routing function cover ALL three outcomes — pass, retry, and escalate? A missing branch silently routes to the wrong node.
  2. Is interrupt_before actually set in compile()? AI often writes the human_review node but forgets to wire the interrupt — the graph will skip it entirely.
  3. Does the copywriter node read failure_reason from state and inject it into the prompt? Without this, retries are blind repetitions, not improvements.
  4. Is there a hard cap on retries? Check that the counter increments correctly and that the escalation branch fires when the cap is hit.
  5. Does each node return a new state dict rather than mutating the input? Run a quick test with two consecutive failures and inspect state after each node.

In plain wordsPydantic is like a customs officer at an airport: it checks every piece of data against a declared list of rules before it is allowed through — wrong type, wrong shape, or missing field gets rejected on the spot.

Pydantic is a Python library. It lets you describe the exact shape of your data using a class. It then checks that incoming data matches that shape.

You define a by writing a class that inherits from BaseModel. Each field has a name and a type — for example, headline: str or word_count: int.

When data arrives — say, a JSON blob from an — Pydantic parses it. It raises a clear error if anything is wrong. Bad data cannot silently flow into the next step of your .

In your ad-generation workflow, Pydantic is the contract between the LLM and the pipeline. It guarantees the copywriter agent always returns a headline, a body_copy, and a call_to_action — never a surprise.

How Pydantic breaks in practice — and what to watch for

In plain wordsPydantic validation errors are like a form that rejects your submission — helpful when the rules are right, but frustrating when the rules themselves are wrong.

Common failure modes

  • LLM returns extra fields. By default Pydantic ignores unknown fields, so a rogue slogan key is silently dropped. You may never know the LLM drifted from your schema.

  • Nested models fail silently. If a nested Pydantic model has a default value, a missing sub-field fills in silently — the error never surfaces.

Use model_config = ConfigDict(extra='forbid') in your BaseModel to make Pydantic raise an error on unexpected fields instead of silently ignoring them. This catches LLM schema drift early.

  2. Numeric fields have explicit range constraints (ge/le) where business logic demands — e.g. confidence can't exceed 1.0.
  3. The model inherits from BaseModel, not a plain Python class — without this, no validation runs.

What Pydantic is and why it exists

In plain wordsPydantic is like a customs officer at an airport: it checks every piece of data against a strict list of rules before it's allowed through — wrong type, wrong shape, rejected.

Pydantic is a Python library that lets you define the exact shape and type of your data using plain Python classes. When data arrives — from an LLM, an API, or a user — Pydantic checks it automatically. If something is wrong (a missing field, a number where a string is expected), it raises a clear error immediately.

The core building block is a BaseModel: a class you write once that describes your data's fields and their types. Pydantic then enforces those rules every time you create an instance of that class.

In an , agents pass data between each other constantly. Without Pydantic, a typo or a missing field can silently break a downstream step — and you won't know until something crashes much later.

  • Defines data shape with typed fields (e.g. headline: str, score: int)
  • Validates data automatically on creation — no manual if-checks needed
  • Produces clear error messages that tell you exactly what went wrong and where
  • Converts compatible types automatically (e.g. the string "42" becomes the integer 42)

Pydantic models as schemas for structured output

In plain wordsA Pydantic model is like a form template: it defines every field that must be filled in, and the LLM's job is to fill in the blanks correctly.

An naturally returns free text. But your workflow needs reliable, machine-readable data — not a paragraph. A Pydantic model acts as a : it tells the LLM exactly what fields to return and in what format.

Libraries like and LangChain's .with_structured_output() use your Pydantic model to constrain the LLM's response. The result is a validated Python object, not a raw string you have to parse yourself.

This is the bridge between the LLM world and your code. Once the output is a Pydantic object, every downstream agent or node can access fields like result.headline with confidence — no guessing, no string splitting.

Predict first: if an LLM returns { "headline": "Buy Now", "score": "nine" } and your model declares score: int, what do you think Pydantic will do? (Guess before reading on.)

Answer: Pydantic will raise a ValidationError because "nine" cannot be converted to an integer. This is exactly the safety net you want — catch the bad data at the boundary, not deep inside your workflow.

How strict should your Pydantic model be?

Slide to see the tradeoff between flexibility and safety in your Pydantic model design.

Imagine your agentic workflow generates Facebook ad copy from a product script. The copywriter agent returns a headline, body text, and a quality score. Without a contract, the LLM might return the score as a word ("high") or skip the body entirely.

You define a Pydantic model called AdCopy with three fields: headline: str, body: str, and quality_score: int.

When the LLM responds, LangChain's feature uses your AdCopy model to parse and validate the response. If the score is missing, you get an error immediately — before the validation agent ever sees bad data.

The validation agent downstream can then safely access ad.quality_score and ad.headline as real Python values. No parsing, no guessing — just clean, typed data flowing through your workflow.

from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# 1. Define the schema — the "form template" the LLM must fill in
class AdCopy(BaseModel):
    headline: str = Field(description="Short, punchy ad headline")
    body: str = Field(description="2-3 sentence ad body text")
    quality_score: int = Field(description="Quality score from 0 to 100")

# 2. Create the LLM and bind it to your schema
llm = ChatOpenAI(model="gpt-4o")
structured_llm = llm.with_structured_output(AdCopy)

# 3. Write the prompt
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a marketing copywriter. Generate ad copy from the script."),
    ("human", "{script}")
])

# 4. Build the chain and invoke it
chain = prompt | structured_llm

script = "New running shoes with carbon-fibre soles. Lightweight. For serious runners."
result = chain.invoke({"script": script})

# result is a validated AdCopy object — not a raw string
print(result.headline)       # e.g. "Run Faster. Feel Nothing."
print(result.quality_score)  # e.g. 87  (always an int, never "high")

It still works — Pydantic coerces the integer 87 into the string "87" automatically. But now your downstream code can't do math on it (e.g. `if result.quality_score > 70` will fail). This is a silent type bug — the model accepts it, but the logic breaks later.

How Pydantic breaks in practice — what to watch for

Common failure modes

  • The LLM ignores the schema and returns plain text. This happens when the model doesn't support tool/function calling. Always check your model supports structured output before relying on it.
  • A field is optional in the model but required by your logic. If you declare quality_score: Optional[int] = None, Pydantic won't complain when it's missing — but your downstream code will crash.
  • Nested data breaks silently. If your model has a nested Pydantic model (e.g. metadata: AdMeta) and the LLM returns a flat dict, validation fails with a confusing error.
  • Type coercion hides bugs. Pydantic converts "87" to 87 silently. This is helpful, but it can mask an LLM that's returning the wrong format.

Non-obvious failure: the schema is too strict for the LLM

If your model has many required fields with tight constraints, the LLM may fail to satisfy them all in one shot. The result is a ValidationError loop — the LLM retries, fails again, and your workflow stalls. Start with fewer required fields and add constraints incrementally.

Watch for: a ValidationError that repeats on every retry usually means the schema is asking for something the LLM can't reliably produce — not a bug in your code.

When you ask an AI assistant to generate a Pydantic model for your workflow, check these things before using it:

  1. Every field has an explicit type. Watch for Any — it disables validation entirely.
  2. Required fields match what your LLM can actually return. Test with a real LLM call; don't just trust the model definition looks right.
  3. Optional fields are intentional. If a field is Optional, confirm your downstream code handles the None case.
  4. Field descriptions are clear and specific. Vague descriptions produce vague LLM outputs — the description is part of your .
  5. Run a quick smoke test: pass a known-bad input and confirm Pydantic raises an error. If it doesn't, the model is too permissive.
