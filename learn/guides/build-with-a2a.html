The Coordination Problem A2A Solves

In plain wordsA2A is like a universal power adapter standard — without it, every device needs its own custom plug, but with it, anything connects to anything.

Modern AI products rarely run on a single agent. A checkout assistant might hand off to a fraud-detection agent, which consults an inventory agent, which calls a pricing agent. Each of these may be built on different frameworks — LangGraph, ag2, a custom Python service — by different teams or vendors.

Without a shared contract, every pair of agents needs custom glue code: bespoke HTTP calls, hand-rolled serialization, and one-off auth schemes. That's an O(n²) integration problem — ten agents means up to 45 custom bridges.

is Google's open that collapses this to O(n): every agent speaks the same language, so any two can interoperate without custom code. It defines how agents advertise capabilities, delegate , stream results, and authenticate — all over standard .

A2A sits at the agent-to-agent layer. It complements (which handles agent-to-tool calls) rather than replacing it. Think of MCP as how an agent picks up a tool, and A2A as how one agent hands work to another agent.

A2A's Core Design Principles

In plain wordsDesigning A2A around existing web standards is like building a new shipping container on the same dimensions as every existing truck and crane — instant compatibility with the whole logistics network.

A2A is built on four deliberate design choices that make it practical to adopt without rewriting existing infrastructure.

  • Standard transport. All communication runs over using . No new wire protocol to learn or firewall-punch.
  • Capability discovery via Agent Cards. Each agent publishes an at a — a JSON document listing its , input/output formats, and auth requirements. Callers discover what an agent can do before sending any work.
  • Async-first task model. Work is wrapped in a object with a lifecycle (). Long-running jobs stream incremental updates via rather than blocking the caller.
  • Built-in auth. The protocol includes hooks so agents can enforce access control without bolting on a separate security layer.

These choices mean A2A agents are opaque by design: a delegates to a without knowing its internal implementation. The contract is the interface, not the internals.

Key distinction: A2A governs (agent → agent). MCP governs (agent → tool/API). Both can coexist in the same system.

Imagine you're a PM at an e-commerce platform. You've shipped three AI agents: a Returns Agent (handles refund logic), an Inventory Agent (checks warehouse stock), and a Carrier Agent (books return shipments). Each was built by a different team.

Without A2A, the Returns Agent needs custom code to call each sibling. Each sibling has different request shapes, auth tokens, and error formats. Adding a fourth agent — say, a Fraud Agent — means writing three more custom integrations.

With A2A, each agent publishes an at its well-known URL. The Returns Agent reads those cards and delegates via standard A2A tasks. Adding the Fraud Agent means one new card — no new glue code.

Booking a shipment can take 30 seconds. Instead of blocking, the Carrier Agent streams updates (submitted → working → completed) over SSE. The customer sees a live status update, not a spinner.

For PMs, this changes the build calculus. Each new capability is a new agent to plug in — not a new integration sprint.

How A2A Connects Two Agents

import httpx, json

# 1. Discover what the Carrier Agent can do
card_url = "https://carrier-agent.example.com/.well-known/agent.json"
card = httpx.get(card_url).json()

print("Skills available:", [s["name"] for s in card["skills"]])
# → Skills available: ['book_return_shipment', 'track_parcel']

# 2. Build a Task message
task_payload = {
    "jsonrpc": "2.0",
    "method": "tasks/send",
    "id": "task-001",
    "params": {
        "message": {
            "role": "user",
            "parts": [
                {
                    "type": "text",
                    "text": "Book a return shipment for order #ORD-9921 to warehouse WH-3."
                }
            ]
        }
    }
}

# 3. Send the task and receive the initial state
response = httpx.post(
    "https://carrier-agent.example.com/",
    json=task_payload,
    headers={"Authorization": "Bearer <token>"}
).json()

task_id = response["result"]["id"]
state    = response["result"]["status"]["state"]
print(f"Task {task_id} is now: {state}")
# → Task task-001 is now: submitted

# 4. Poll or stream for completion (streaming shown as comment)
# For SSE streaming, open an EventSource to the agent's stream endpoint
# and listen for state transitions: submitted → working → completed

Client Agent and Remote Agent: Who Does What

In plain wordsThink of the Client Agent as a store manager placing a work order, and the Remote Agent as the specialist warehouse team that fulfills it — each has a clear, separate role.

Every exchange involves exactly two roles. The initiates work — it decides what needs doing and sends a structured request. The receives that request, executes the work, and returns a result.

Neither role is tied to a specific model or vendor. Any agent can act as a Client Agent in one exchange and a Remote Agent in another. This symmetry is what makes composable: agents delegate to each other without a central controller.

The Remote Agent exposes its capabilities through an — a machine-readable manifest served at a . The Client Agent reads this card before sending work, so it knows what are available and how to authenticate.

  • Client Agent — the caller; owns the goal and decides when the task is complete.
  • Remote Agent — the worker; owns execution and reports back.
  • Agent Card — the contract; tells the caller what the worker can do.

Transport Layer: HTTP, JSON-RPC 2.0, and SSE

In plain wordsJSON-RPC 2.0 is like a standardized order form — every request has the same fields (method, params, id) so any system can read it without custom parsing.

A2A runs over plain and uses as its message format. Every call is a JSON object with a fixed envelope: jsonrpc, method, params, and id. This predictable shape means any HTTP client can speak A2A without a custom SDK.

For short tasks, the protocol uses standard request-response: the Client Agent POSTs a request and waits for a single JSON reply. For long-running or streaming tasks, A2A switches to — the server pushes incremental updates over a persistent HTTP connection.

SSE is one-directional (server → client) and works through standard HTTP, so it needs no WebSocket upgrade. The Remote Agent streams changes and partial as they become available, keeping the Client Agent informed without polling.

Key tradeoff: request-response is simpler to implement and debug; reduces perceived latency for tasks that produce output incrementally (e.g., generating a long product description).

Message Path: From Initiation to Response

Imagine your platform has a Catalog Agent (the Client Agent) that orchestrates content tasks, and a Copywriting Agent (the Remote Agent) that generates product descriptions.

  1. The Catalog Agent fetches the Copywriting Agent's from /.well-known/agent.json and confirms it has a 'write-product-copy' .
  2. It POSTs a request: method tasks/send, params include a with a text containing the product SKU and attributes.
  3. Because descriptions can be long, the Copywriting Agent responds with an SSE stream. The Catalog Agent receives tokens as they arrive — no polling needed.
  4. When the stream closes with = completed, the Catalog Agent reads the output and writes the copy to the product database.

From a PM perspective: the two agents are independently deployable and replaceable. Swap the Copywriting Agent for a different vendor's model without touching the Catalog Agent — as long as the Agent Card contract is honored.

import json, requests, sseclient

REMOTE_AGENT_URL = "https://copywriter.example.com/a2a"
AUTH_TOKEN = "Bearer <token>"

# 1. Build the JSON-RPC 2.0 envelope
payload = {
    "jsonrpc": "2.0",
    "id": "task-001",
    "method": "tasks/send",
    "params": {
        "id": "task-001",
        "message": {
            "role": "user",
            "parts": [
                {"type": "text", "text": "Write a 50-word description for SKU-9821: noise-cancelling headphones."}
            ]
        }
    }
}

# 2. POST and request an SSE stream
headers = {
    "Authorization": AUTH_TOKEN,
    "Content-Type": "application/json",
    "Accept": "text/event-stream"   # signals: stream the response
}

response = requests.post(REMOTE_AGENT_URL, json=payload, headers=headers, stream=True)

# 3. Consume the SSE stream
client = sseclient.SSEClient(response)
for event in client.events():
    data = json.loads(event.data)
    state = data.get("status", {}).get("state")
    print(f"State: {state}")
    if state == "completed":
        artifact_text = data["artifacts"][0]["parts"][0]["text"]
        print("Result:", artifact_text)
        break
Syntax breakdown
"jsonrpc": "2.0"
Declares the JSON-RPC version; required on every request so the server knows which protocol rules apply.
"method": "tasks/send"
The A2A RPC method name — tells the Remote Agent to create and start a new task.
"id": "task-001"
A client-chosen identifier that links the request to its response; useful for correlating async replies.
"parts": [...]
The content units inside a Message. A Part can be text, a file, or structured data — here it's a plain text prompt.
"Accept": "text/event-stream"
HTTP header that tells the server to respond with an SSE stream instead of a single JSON blob.
stream=True
Keeps the HTTP connection open so the client can read chunks as they arrive, rather than waiting for the full body.
sseclient.SSEClient(response)
Wraps the raw streaming response and parses each SSE event into a structured object with a .data field.
data["artifacts"][0]["parts"][0]["text"]
Navigates the A2A Task object to the first Artifact's first Part — where the Remote Agent placed the generated text.

The code above shows the full round-trip: build the envelope, POST it with an SSE accept header, then iterate over events until the reaches completed. The output lands in an — a structured result object separate from the task metadata.

If the Remote Agent doesn't support SSE, omit the Accept: text/event-stream header. The server will return a single JSON response instead, and you can skip the SSEClient loop.

What an Agent Card Is and Why It Exists

In plain wordsAn Agent Card is like a product listing on a marketplace — it tells buyers exactly what the product does, what formats it accepts, and what credentials are needed to purchase.

In the , every agent publishes an . This is a structured JSON document served at a (typically /.well-known/agent.json). It is the agent's public contract: capabilities, communication method, and required credentials.

happens before any task is delegated. A fetches the card and inspects it. It checks whether the has the right and acceptable requirements before sending any message.

Core fields in an Agent Card

  • name / description — human-readable identity of the agent.
  • url — the base endpoint for calls.
  • skills[] — array of objects, each with an id, name, description, and supported input/output modes.
  • capabilities — flags for or push-notification support.
  • authentication — the required scheme (e.g. Bearer token, API key, none).
  • version — the agent's version string, used for compatibility checks.
The card is read-only and public by design. Sensitive credentials are never stored in it. Only the scheme is included (e.g. "Bearer") so callers know how to authenticate.

How a Client Agent Uses a Card to Decide on Delegation

In plain wordsReading an Agent Card before delegating is like checking a contractor's license and specialties before hiring them for a job — you verify fit before committing.

When a task, it runs a lightweight matching process against the card.

  1. Fetch the card from /.well-known/agent.json.
  2. Match skillsskill id or description aligns with the task intent.
  3. Check modalities — confirm the skill accepts the required input type (text, file, structured data).
  4. Evaluate authauthentication scheme.
  5. Delegate or skip — if all checks pass, send the task; otherwise try another agent or fail gracefully.

This process is what makes real: agents from different vendors can collaborate because the card provides a shared, machine-readable contract.

A mismatch on any of the three checks (skill, modality, auth) should abort delegation. Partial matches lead to runtime errors that are hard to debug.

The A2A Task State Machine

In plain wordsA task is like a customer order: it's submitted, the warehouse works on it, it might pause waiting for your address confirmation, and finally it's either delivered or cancelled.

Every task moves through a defined state machine managed by the . The valid states are submitted, working, input-required, completed, failed, and cancelled. Transitions only flow forward — a task can't go back to submitted once it's working.

The input-required and the task resumes to working.

  • submitted → task received, not yet processed
  • working → agent is actively executing
  • input-required → agent paused, waiting for caller input
  • completed ready for pickup
  • failed → unrecoverable error; inspect the status message
  • cancelled → caller or system aborted the task
Only completed and failed are terminal states. cancelled is also terminal but is initiated externally, not by the agent's own logic.

Messages vs. Artifacts: In-Flight vs. Final

In plain wordsMessages are the back-and-forth emails during a project; the Artifact is the finished deliverable you actually ship.

A2A distinguishes two kinds of content: and . Messages carry the conversational exchange — instructions, clarifying questions, status updates. Artifacts carry the completed output the caller actually consumes.

Both are composed of : typed content units that can be text, file, or structured data. A single Message or Artifact can mix Part types — for example, a text summary alongside a JSON data payload.

  • Message — role is user or agent; used during task execution
  • Artifact — produced only on completed; has a name and optional index for multi-part outputs
Don't treat a streaming Message chunk as a finished Artifact. Wait for the completed state before reading Artifacts — intermediate Messages may still change.

Use when
Use synchronous tasks/send when the task is short-lived (under ~5 s), the caller can block, and you don't need incremental output — simpler to implement and debug.
Avoid when

import httpx, json

AGENT_URL = "https://copy-agent.example.com/a2a"

def send_message(task_id, text, session_id=None):
    payload = {
        "jsonrpc": "2.0",
        "method": "tasks/send",
        "id": 1,
        "params": {
            "id": task_id,
            "sessionId": session_id,
            "message": {
                "role": "user",
                "parts": [{"type": "text", "text": text}]
            }
        }
    }
    response = httpx.post(AGENT_URL, json=payload)
    return response.json()["result"]

def run_task(initial_prompt):
    import uuid
    task_id = str(uuid.uuid4())

    task = send_message(task_id, initial_prompt)

    while task["status"]["state"] not in ("completed", "failed", "cancelled"):
        state = task["status"]["state"]

        if state == "input-required":
            # Agent is waiting — read its clarifying question
            question = task["status"]["message"]["parts"][0]["text"]
            print(f"Agent asks: {question}")
            user_reply = input("Your answer: ")  # or fetch from campaign brief
            task = send_message(task_id, user_reply)

        elif state == "working":
            # Poll again after a short wait
            import time; time.sleep(2)
            task = send_message(task_id, "")  # empty re-poll

    if task["status"]["state"] == "completed":
        for artifact in task.get("artifacts", []):
            for part in artifact["parts"]:
                if part["type"] == "text":
                    print("Final copy:", part["text"])
    else:
        print("Task ended with state:", task["status"]["state"])

run_task("Write a lifestyle product description for SKU-4821, a Gen Z sneaker.")

"jsonrpc": "2.0"
Marks this as a JSON-RPC 2.0 request — the wire format A2A uses for all method calls.
"method": "tasks/send"
The A2A method name for sending a message to a task (creating it on first call, continuing it on subsequent calls).
"id": task_id
The stable task identifier — reuse the same ID across all turns of a multi-turn conversation.
"role": "user"
Marks this Message as coming from the caller side; the agent's replies carry role: 'agent'.
"parts": [{"type": "text", ...}]
A Message is a list of Parts; here just one text Part, but you could add file or data Parts alongside it.
task["status"]["state"]
The current task state string — poll this to drive the while-loop through the state machine.
task.get("artifacts", [])
Artifacts only appear when state is 'completed'; each has its own parts list with the final output content.

The loop polls the task state and branches on input-required vs. working. In production you'd replace the input() call with a lookup against your campaign brief store or a human-in-the-loop queue.

For streaming, replace tasks/send with tasks/sendSubscribe event stream. Each event carries a partial task object with the current state — the same state machine applies.

Two Protocols, Two Layers

In plain wordsMCP is like a power outlet — it gives an agent a standard way to plug into any tool; A2A is like a phone line between offices — it lets one agent hand a job to another agent entirely.

and solve different problems at different layers of a .

MCP connects an to external tools and data — think search APIs, databases, or inventory feeds. It standardises how the agent makes a and reads the result back.

A2A connects agents to other agents. One delegates a whole to a , which owns execution and reports back a and an .

The key distinction: MCP is about calling a function; A2A is about delegating a goal. In practice, an agent often uses MCP internally while being reachable via A2A from the outside.

  • MCP scope: agent ↔ tool/data source (one hop, synchronous or streamed result)
  • A2A scope: agent ↔ agent (multi-step task, stateful, asynchronous-friendly)
  • They are complementary — not competing — and are routinely layered together

def handle_user_request(request: str, context: dict):
    """
    Route an incoming request to the right protocol layer.
    """
    if requires_specialist_agent(request):
        # A2A path — delegate the whole task to a remote agent
        agent_card = discover_agent(well_known_url="https://agents.example.com/inventory/.well-known/agent.json")
        task = send_a2a_task(
            agent_card=agent_card,
            message={"role": "user", "parts": [{"text": request}]},
        )
        result = poll_until_done(task_id=task["id"])   # returns artifact when complete
        return result["artifact"]

    else:
        # MCP path — call a tool directly
        tool_result = call_mcp_tool(
            tool_name="product_search",
            params={"query": request, "max_price": context.get("budget")},
        )
        return tool_result


def requires_specialist_agent(request: str) -> bool:
    # Heuristic: multi-step goals go to an agent; simple lookups stay as tool calls
    multi_step_keywords = ["find and order", "compare and recommend", "check then book"]
    return any(kw in request.lower() for kw in multi_step_keywords)

The Three Moving Parts of an A2A System

In plain wordsBuilding an A2A system is like setting up a franchise network: the Remote Agent is the branch store with a posted menu (Agent Card), the Task Manager is the kitchen tracking each order's status, and the Client Agent is the customer-facing rep who reads the menu and places the order.

An implementation has three concrete pieces that must fit together. The is an HTTP server that advertises its capabilities and accepts task requests. The is the state machine inside that server, tracking every from submission to completion. The is the caller that discovers the remote agent and delegates work to it.

Discovery happens via the — a JSON document served at a (typically /.well-known/agent.json). It declares the agent's name, supported , and requirements. A Client Agent fetches this card before sending any task.

Tasks flow over on an . Each task carries a unique ID, a with one or more , and moves through defined : submitted → working → completed (or failed/canceled).

Long-running tasks can push incremental updates via (Server-Sent Events), so the client doesn't have to poll. This path is optional but important for tasks that take more than a few seconds.

End-to-End A2A Request Lifecycle

How a Client Agent discovers, delegates, and receives results from a Remote Agent.

Imagine your platform has an Orchestrator Agent that handles incoming customer orders. When an order needs fraud screening, it delegates to a specialist Fraud-Check Remote Agent — a separate service owned by the risk team.

Step 1 — Remote Agent scaffolding

The Fraud-Check Remote Agent serves an Agent Card at /.well-known/agent.json. The card lists one skill: "screen_order", and declares it requires a Bearer token. Any caller — including your Orchestrator — reads this card first.

Step 2 — Task Manager state machine

When a task arrives, the Task Manager creates a record: { id, state: 'submitted', messages: [...] }. It immediately moves to 'working', runs the fraud model, then writes 'completed' with a risk-score artifact. If the model call times out, it writes 'failed' so the caller knows to retry or escalate.

Step 3 — Client Agent delegation

The Orchestrator Agent fetches the card, confirms the skill exists, attaches its token, and sends a tasks/send call with the order payload. It waits for the completed artifact, then routes the order: approve, flag, or reject.

Product angle: The risk team can update their fraud model independently. As long as the Agent Card and task schema stay stable, the Orchestrator needs zero changes — that's the payoff of A2A.

def handle_agent_card(handler):
    """Serve the Agent Card at the well-known URL."""
    handler.send_response(200)
    handler.send_header("Content-Type", "application/json")
    handler.end_headers()
    handler.wfile.write(json.dumps(AGENT_CARD).encode())

def handle_task_send(payload, auth_token):
    """Receive a task, run the state machine, return result."""
    if not validate_token(auth_token):
        return {"error": {"code": -32001, "message": "Unauthorized"}}

    task_id = payload.get("id", str(uuid.uuid4()))
    messages = payload["message"]["parts"]

    # State: submitted → working
    task_store[task_id] = {"id": task_id, "state": "submitted", "messages": messages}
    task_store[task_id]["state"] = "working"

    try:
        risk_score = run_fraud_model(messages)          # your model call here

        task_store[task_id]["state"] = "completed"
        task_store[task_id]["artifact"] = artifact
        return {"id": task_id, "state": "completed", "artifact": artifact}
    except Exception as e:
        task_store[task_id]["state"] = "failed"
        return {"id": task_id, "state": "failed", "error": str(e)}

import urllib.request

def discover_and_delegate(base_url, order_payload, token):
    """Fetch Agent Card, then send a task."""
    # 1. Capability discovery
    card_url = base_url + "/.well-known/agent.json"
    with urllib.request.urlopen(card_url) as r:
        card = json.loads(r.read())

    assert any(s["id"] == "screen_order" for s in card["skills"]), \
        "Remote agent lacks required skill"

    # 2. Delegate the task
    rpc_body = json.dumps({
        "jsonrpc": "2.0", "method": "tasks/send", "id": 1,
        "params": {
            "id": str(uuid.uuid4()),
            "message": {"parts": [{"type": "text", "text": json.dumps(order_payload)}]}
        }
    }).encode()

    req = urllib.request.Request(
        card["endpoint"],
        data=rpc_body,
        headers={"Content-Type": "application/json", "Authorization": f"Bearer {token}"}
    )
    with urllib.request.urlopen(req) as r:
        result = json.loads(r.read())

    return result   # contains state + artifact

Use when
Use signed JWTs (or mTLS) when Remote Agents are exposed beyond a single trusted internal network — especially when crossing team or org boundaries.
Avoid when
Avoid raw shared-secret strings (like the stub in the code example) in any environment where the token could appear in logs, error messages, or version control.
Rule of thumb
Treat every agent-to-agent call like an API call from an untrusted client: authenticate the caller, authorize the skill, and log the task ID for audit.
Putting it together

Synthesis

A2A gives multi-agent systems a shared contract for discovery, delegation, and task tracking — replacing ad-hoc integrations with a standard protocol.

The key moving parts are the Agent Card (who I am and what I do), the Task Manager (state machine), and the Client/Remote Agent pair communicating over HTTP + JSON-RPC.

Use A2A between agents and MCP within an agent for tools — they complement each other at different layers of your stack.
