What actually matters
  • Why GBTs beat neural nets on tabular data: heterogeneous features with no local structure to exploit; trees are scale-invariant, model sharp thresholds and interactions natively, and win at small-to-mid n (Grinsztajn et al., 2022). NNs win when data is huge or multimodal — not on a 200k-row CRM export.
  • Logistic regression is the deployment king: if it's within 2–3 points of the GBT, ship it and bank the operational simplicity.
  • Feature engineering beats model choice on tabular problems.
  • Class imbalance: class weights + threshold tuning before SMOTE tricks.
  • Cost asymmetry vs LLMs: a small classifier is ~100–1000× cheaper and 10–100× faster than prompting an LLM for the same yes/no decision.
In agentic systems: classifiers are the cheap deterministic muscle — routing (easy traffic → small model), guardrails (injection/toxicity filters), intent detection, escalation (confidence-thresholded human handoff). Named: OpenAI's moderation endpoint gating ChatGPT I/O; Stripe Radar scoring every transaction in ~100 ms with tree ensembles.

Theory

Fit the hyperplane that minimizes squared error between prediction and target. Coefficients are marginal effects — "one unit of x moves y by w, holding the rest fixed" — which is exactly why it survives: it's the only model whose parameters are the explanation. Valid inference rests on assumptions: linearity, independent errors, homoscedasticity (constant error variance), and (for p-values) normal errors. Prediction tolerates violations; coefficient storytelling doesn't.

Math — model · loss · optimizer
Model: ŷ = Xw + b
Loss (MSE): L(w) = (1/n) Σᵢ (yᵢ − ŷᵢ)²  ·  convex → single global minimum
Closed form (OLS): w* = (XᵀX)⁻¹ Xᵀy  ·  Gradient descent: w ← w − η · (2/n) Xᵀ(ŷ − y)
Ridge (L2): + λ‖w‖² → w* = (XᵀX + λI)⁻¹Xᵀy (shrinks)  ·  Lasso (L1): + λ‖w‖₁ (zeroes features; coordinate descent)
  • Statistics: R² = variance explained; adjusted R² penalizes feature count; coefficient p-values/CIs (from statsmodels, not sklearn); VIF for multicollinearity — correlated features make individual coefficients unstable/meaningless while predictions stay fine; residual plots to catch non-linearity and heteroscedasticity.

The question: I have sold 5 houses. Can I predict what a 2,200 sq ft house should cost?

Step 1 — find the centre of the data
x̄ = (1.0+1.5+2.0+2.5+3.0)/5 = 2.0    ȳ = (50+65+85+95+115)/5 = 410/5 = 82
Step 2 — do x and y move together? (this becomes the slope's top half)
(x−x̄): −1.0, −0.5, 0, +0.5, +1.0 (y−ȳ): −32, −17, +3, +13, +33 products: 32.0, 8.5, 0, 6.5, 33.0  →  Σ = 80

Every product is positive: when size is above average, price is above average too. That's what "positive relationship" means numerically.

Step 3 — how much does x itself spread? (the slope's bottom half)
Σ(x−x̄)² = 1.0 + 0.25 + 0 + 0.25 + 1.0 = 2.5
Step 4 — slope and intercept
w = 80 / 2.5 = 32    b = ȳ − w·x̄ = 82 − 32(2.0) = 18 Price = 18 + 32 × Size

How to read it in plain English: every extra 1,000 sq ft adds ₹32 lakh. The 18 is where the line crosses zero size — think land + fixed costs. It is not meaningful as "the price of a zero-size house"; never extrapolate to sizes you've never observed.

Step 5 — the prediction you wanted
2,200 sq ft → x = 2.2 → 18 + 32(2.2) = 18 + 70.4 = ₹88.4 lakh
Step 6 — is the line any good? (R²)
predictions: 50, 66, 82, 98, 114  →  errors: 0, −1, +3, −3, +1 SS_res = 0+1+9+9+1 = 20    SS_tot = Σ(y−ȳ)² = 1024+289+9+169+1089 = 2580 R² = 1 − 20/2580 = 0.992

Size explains 99.2% of the price variation in these 5 rows. Real housing data lands at 0.6–0.8. If you ever see 0.99 on real data, suspect leakage — a column that secretly contains the answer.

import numpy as np
from sklearn.linear_model import LinearRegression

X = np.array([[1.0], [1.5], [2.0], [2.5], [3.0]])   # 1000s of sq ft
y = np.array([50, 65, 85, 95, 115])                 # ₹ lakh

m = LinearRegression().fit(X, y)
print(m.coef_[0], m.intercept_)     # 32.0  18.0   <- same as our hand math
print(m.score(X, y))                # 0.9922 (R²)
print(m.predict([[2.2]]))           # [88.4] ₹ lakh

Applications
  • Pricing and demand curves, LTV projection, marketing-mix models, elasticity estimates — anywhere the coefficient is the deliverable.
  • The mandatory baseline: any fancy model must beat regularized linear regression to justify itself.
  • Agentic: predicting cost/latency per request from prompt features for routing budgets; drift baselines ("expected tokens per task type"); simple trend models over eval scores.
Theory

A linear score squashed through the sigmoid becomes a probability; the decision boundary stays linear. It answers "how likely" not just "which", and its outputs are roughly calibrated out of the box — the property that makes thresholding, pricing, and human review queues work. Multiclass = same idea with softmax. Despite the name, it's the workhorse classifier of industry.

Math — model · loss · optimizer
Model: p = σ(w·x + b), σ(z) = 1/(1+e⁻ᶻ)  ·  log-odds are linear: ln(p/(1−p)) = w·x + b
Loss (cross-entropy): L = −(1/n) Σ [y ln p + (1−y) ln(1−p)]  ·  convex  ·  gradient: Xᵀ(p − y)
Optimizer: L-BFGS (sklearn default) · SGD/Adam at scale  ·  Regularization: L2 default (C = 1/λ), L1 for sparse feature selection
  • Statistics: e^w = odds ratio per unit of feature ("each prior incident multiplies churn odds by 1.4×") — the interpretation execs actually understand; check calibration curves before trusting probabilities; class weights shift the implicit threshold.
Worked example — will this customer cancel?

The question: a customer hasn't logged in for 30 days and has raised 2 support tickets. Should we spend ₹500 on a retention offer?

Training on past customers produced this fitted model (the numbers are what training learns):

z = −4 + 0.08 × (days since login) + 1.2 × (support tickets)
Step 1 — compute the score z (this part is just linear regression)
z = −4 + 0.08(30) + 1.2(2) = −4 + 2.4 + 2.4 = 0.8
Step 2 — squash it into a probability with the sigmoid
p = 1 / (1 + e^−0.8) = 1 / (1 + 0.449) = 1/1.449 = 0.69 → 69% likely to churn

The sigmoid's only job is to turn any number (−∞…+∞) into something between 0 and 1. z = 0 → p = 0.50. Positive z → above 50%.

Step 3 — read the coefficients as "odds multipliers"
e^0.08 = 1.083 → each idle day multiplies the odds of churn by 1.083 (+8.3%) e^1.20 = 3.32 → each support ticket multiplies the odds by 3.3×

This is the sentence you take to a business review: "every support ticket triples a customer's odds of leaving."

Step 4 — the threshold is economics, not 0.5
offer cost = ₹500  ·  value of a saved customer = ₹5,000 send the offer when: p × 5000 > 500  →  p > 0.10

So we act at 10%, not 50%. We happily "waste" 9 offers to save 1 customer, because the save is worth 10× the offer. This is the single most valuable thing a PM does with a classifier — the model gives a probability, you decide the cut.

scikit-learnstatsmodels (Logit for p-values)

Applications
  • Churn, fraud baseline, CTR prediction, credit scoring — regulated domains love it because every decision is auditable.
  • Agentic: the default implementation of router / guardrail / escalation classifiers — often trained on frozen embedding vectors: embed the query with your embedding model, fit logistic regression on top. Five minutes to train, 5 ms to serve.
Theory

Recursively split the feature space with axis-aligned thresholds, each split chosen greedily to make child nodes purer. The result is a set of human-readable if-then rules. Handles non-linearity, interactions, mixed types, and missing values with zero preprocessing — and, left unpruned, memorizes noise (high variance). A single tree is a communication tool and an ensemble ingredient; rarely the production model itself.

Math — split criteria · optimizer
Gini impurity: G = 1 − Σₖ pₖ²  ·  Entropy: H = −Σₖ pₖ ln pₖ  ·  split maximizes impurity decrease (information gain)
Regression trees: split to minimize child-node variance (MSE); leaf predicts the mean
Optimizer: no gradients — exact greedy search over every (feature, threshold); complexity ≈ O(n·d·depth)  ·  Control overfitting: max_depth, min_samples_leaf, cost-complexity pruning (ccp_alpha)
  • Statistics caveat: impurity-based feature importance is biased toward high-cardinality features — use permutation importance when the ranking matters.
Worked example — which question should the tree ask first?

The setup: 10 past loans, 4 of which defaulted. The tree's job is to find the one yes/no question that best separates defaulters from repayers. It tries every possible question and scores each with Gini impurity — read Gini as "if I picked two loans from this group at random, how often would they disagree?" 0 = perfectly pure.

Step 1 — how messy is the starting group?
10 loans: 6 repaid, 4 defaulted → p = 0.6 / 0.4 Gini(root) = 1 − (0.6² + 0.4²) = 1 − (0.36 + 0.16) = 0.48 (messy — near the 0.5 maximum)
Step 2 — try question A: "is income > ₹50k?"
income ≤ 50k → 4 loans, 3 defaults: Gini = 1 − (0.25² + 0.75²) = 0.375 income > 50k → 6 loans, 1 default : Gini = 1 − (0.833² + 0.167²) = 0.278 weighted = (4/10)(0.375) + (6/10)(0.278) = 0.150 + 0.167 = 0.317 gain = 0.48 − 0.317 = 0.163
Step 3 — try question B: "is credit score > 700?"
score ≤ 700 → 5 loans, 4 defaults: Gini = 1 − (0.2² + 0.8²) = 0.32 score > 700 → 5 loans, 0 defaults: Gini = 1 − (1² + 0²) = 0.00 (perfectly pure!) weighted = 0.5(0.32) + 0.5(0.00) = 0.16 gain = 0.48 − 0.16 = 0.32 ← twice as good as question A
Step 4 — the tree picks B, then repeats on whatever is still messy
Root: credit score > 700? ├─ YES → 5 loans, 0 defaults → APPROVE (done, pure leaf) └─ NO → 5 loans, 4 defaults → still messy → ask the next-best question here └─ income > 50k? → YES: approve · NO: DECLINE

The honest caveat: with only 10 rows, "0 defaults above 700" is almost certainly luck. That is exactly how a tree overfits — it will keep splitting until every leaf is pure, memorizing noise. max_depth and min_samples_leaf are what stop it.

Applications
  • Risk policies, triage rules, eligibility logic — anywhere the model must be read by compliance or ops.
  • Distill an opaque model into one shallow tree to explain roughly what it does.
  • Agentic: human-legible escalation policies ("retrieval score low AND turn count high → hand off") that ops teams can audit and override — a shallow tree is the documentation.
Theory

Bagging: train many deep trees, each on a bootstrap sample (draw n rows with replacement) and with a random feature subset considered at each split, then average their votes. Each tree is individually overfit; the ensemble isn't, because their errors are (partly) independent and averaging cancels them. The feature subsampling is the clever bit — it decorrelates the trees so averaging actually helps. Nearly tuning-free; more trees never hurt accuracy, only latency.

Math — why averaging works · optimizer
Variance of B averaged trees with pairwise correlation ρ:  Var = ρσ² + (1−ρ)σ²/B

As B → ∞ the second term dies; what remains is ρσ². So the ceiling on ensemble quality is the correlation between trees — which is exactly what random feature selection attacks. This one equation is the whole design.

OOB (out-of-bag): each tree never saw ~37% of rows (1 − 1/e) → free validation estimate without a held-out set
Optimizer: none beyond per-tree greedy splitting — trees are independent, training is embarrassingly parallel
Worked example — why 5 mediocre trees beat 1 good tree

The setup: predict the price of one house whose true value is ₹84 lakh. Each tree was trained on a different random sample of the data (a bootstrap: draw rows with replacement, so each tree sees a slightly different world) and each got it wrong in its own direction.

Tree 1822
Tree 2786
Tree 3906
Tree 4851

Forest (average)831
average prediction = (82 + 78 + 90 + 85 + 80)/5 = 415/5 = 83 average individual error = (2+6+6+1+4)/5 = 3.8  ·  forest error = 1.0

No single tree was reliably right, but their mistakes pointed in different directions (some too high, some too low) and cancelled out. That is the entire idea of bagging: average away the randomness.

Why more trees stops helping — the one equation worth knowing
Var(forest) = ρσ² + (1−ρ)σ²/B (ρ = how similar the trees are, B = number of trees) with σ² = 16, ρ = 0.6, B = 100 → 9.6 + 0.16 = 9.76 (spread ≈ 3.1) with σ² = 16, ρ = 0.2, B = 100 → 3.2 + 0.13 = 3.33 (spread ≈ 1.8)

Adding trees only shrinks the second term — it dies quickly and then you are stuck at ρσ². Making the trees less alike (that's what random feature selection at each split does) attacks the first term, which is where the real gain lives. Practical read: 500 trees instead of 100 buys you almost nothing; feature randomization buys you a lot.

Free validation — the out-of-bag trick

Each bootstrap sample leaves out about 37% of rows (mathematically 1 − 1/e). Every tree can be tested on the rows it never saw, so you get a held-out score without setting aside a test set — useful when data is scarce.

from sklearn.ensemble import RandomForestRegressor
import numpy as np

rf = RandomForestRegressor(n_estimators=500, max_features=0.5,
                           oob_score=True, random_state=0).fit(X, y)

print(rf.oob_score_)                       # free held-out R²

# see the disagreement between trees = the model's own uncertainty
preds = np.array([t.predict([[2.2]])[0] for t in rf.estimators_])
print(preds.mean(), preds.std())           # 83.1  4.2  <- wide spread = low confidence

scikit-learnranger (R) / cuML (GPU)

Applications
  • The honest first model on any new tabular problem — its score tells you what's achievable before you invest in tuning.
  • Robust on messy, noisy, mislabeled data where boosting would chase the noise.
  • Permutation importance on a forest = fast "which features carry signal" audit — also a leakage detector (one suspiciously dominant feature → investigate).
  • Agentic: baseline for escalation/quality-prediction models on trace features; importance audit tells you which trace signals actually predict failure.
Theory

Stagewise additive modeling: start with a constant, then repeatedly add a small tree that corrects the current ensemble's errors — formally, each new tree fits the negative gradient of the loss ("gradient descent in function space"). Shallow trees × a small learning rate × early stopping on validation = the most accurate tabular family we have. XGBoost adds second-order (Newton) steps and heavy regularization; LightGBM adds histogram binning and leaf-wise growth for speed; CatBoost handles categoricals natively.

Math — objective · optimizer
Additive model: F_m(x) = F_{m−1}(x) + η · h_m(x)  ·  h_m fit to pseudo-residuals rᵢ = −∂L(yᵢ, F_{m−1}(xᵢ))/∂F
XGBoost objective (2nd-order Taylor): Σᵢ [gᵢ h(xᵢ) + ½ hᵢ h(xᵢ)²] + Ω(h),  Ω = γT + ½λ‖w‖² (T leaves, weights w)
Optimal leaf weight: w* = −G/(H + λ)  ·  (G, H = sums of gradients/hessians in the leaf) — regularized Newton step per leaf
  • Because it only needs gradients, any differentiable loss plugs in: squared error, log loss, quantile (P90 forecasts), Tweedie (insurance), LambdaRank (ranking) — one engine, many products.
  • Key knobs: learning_rate ↓ + n_estimators ↑ (with early stopping) is the reliable recipe; depth 4–8; row/column subsampling adds stochastic regularization.
Worked example — boosting chases what's left over

The setup: 4 houses with true prices 30, 50, 60, 80 (₹ lakh). Watch boosting build the answer in rounds. Learning rate η = 0.5 means "only take half of each correction".

Round 0 — start stupid: predict the average for everyone
F₀ = mean(30,50,60,80) = 55 for every house leftovers (residuals): 30−55 = −25 · 50−55 = −5 · 60−55 = +5 · 80−55 = +25 average error = 15
Round 1 — fit a tiny tree to the leftovers, not to the price
tree splits on size: {small houses} → mean leftover = (−25 −5)/2 = −15 {big houses} → mean leftover = (+5 +25)/2 = +15 F₁ = 55 + 0.5(−15) = 47.5 for small · 55 + 0.5(+15) = 62.5 for big new leftovers: −17.5, +2.5, −2.5, +17.5 → average error = 10
Round 2 — fit another tree to the new leftovers
this tree splits on age: {old} → −10 · {new} → +10 F₂ = 42.5, 52.5, 57.5, 67.5 new leftovers: −12.5, −2.5, +2.5, +12.5 → average error = 7.5

The two knobs, in plain English: the learning rate is how much of each correction you accept — small (0.05) means slow, careful, better-generalizing; early stopping watches a validation set and pulls the plug the moment new trees stop helping there, which is what keeps round 500 from memorizing your noise.

Contrast with random forest: a forest trains 500 trees that each try to predict the price and averages them. Boosting trains 500 trees where each one predicts the remaining mistake and adds them up. Same ingredient, opposite recipe.

Applications
  • Fraud, credit risk, pricing, demand forecasting, CTR — the default production model for structured data.
  • Search & recsys ranking via LambdaMART (see Ranking tab) — still running plenty of production search.
  • Agentic: the upgrade path when the logistic router/escalator plateaus — same features, a few points more accuracy; also quality-prediction models over trace features (will this agent run need review?).
Theory (brief — know the vocabulary)

Find the boundary that maximizes the margin to the nearest points; only those nearest points — the support vectors — define it. The kernel trick computes inner products in an implicit high-dimensional space, buying non-linear boundaries without ever constructing the features. Pre-embedding-era king of text and small-n/high-dim problems; today its concepts (margin, hinge loss, kernels) outlive its deployments.

Math — objective · loss · optimizer
Soft-margin objective: min ½‖w‖² + C Σ ξᵢ  s.t.  yᵢ(w·xᵢ + b) ≥ 1 − ξᵢ  ·  C trades margin width vs violations
Hinge loss view: L = max(0, 1 − y·f(x)) — zero loss once you're past the margin; compare log loss, which never stops caring
RBF kernel: K(x, x′) = exp(−γ‖x − x′‖²)  ·  Optimizer: quadratic programming / SMO on the dual; linear SVMs via liblinear or SGD

ham sits at x₁+x₂ = 3 · spam sits at x₁+x₂ = 9 the fairest line runs exactly between them: x₁ + x₂ = 6 i.e. w = (1, 1), b = −6, decision f(x) = x₁ + x₂ − 6
Step 2 — how wide is the street?
|f| at the nearest points = |3 − 6| = |9 − 6| = 3 geometric margin = 3 / ‖w‖ = 3 / √2 = 2.12 units of clearance on each side

All four emails touch the edge of the street, so all four are support vectors. Here's the property that names the algorithm: if I add a 5th ham email at (0,0) — far from the line — the boundary does not move at all. Only the closest points matter; the rest are irrelevant. That's the opposite of logistic regression, where every point tugs on the fit.

Step 3 — hinge loss: "stop caring once you're safely across"
new email (3, 2): f = 3+2−6 = −1, true label −1 → margin y·f = +1 → loss = max(0, 1−1) = 0 new email (3.5, 2.5): f = 0 (sitting on the line) → y·f = 0 → loss = max(0, 1−0) = 1

Once a point is past the margin the loss is exactly zero — the model gets no reward for pushing it further. Logistic regression, by contrast, keeps nudging forever. That is why SVMs are stable and why they don't give you probabilities for free.

When the straight line fails: if spam were both very short and very long emails, no straight line works. The RBF kernel bends the boundary into a closed blob around the hams — without you inventing a single new feature.

kNN — theory & math

No training: store the data, predict from the k nearest neighbors' labels (vote or average). Every modeling decision is in the distance metric and k (small k = low bias/high variance; large k = smooth). Features must be scaled or big-range features dominate. Exact search is O(n) per query — the reason ANN indexes exist. RAG retrieval is kNN in embedding space; this "obsolete" algorithm quietly became the backbone of modern AI products.

Distance: Euclidean ‖a−b‖₂ or cosine 1 − (a·b)/(|a||b|)  ·  Classify: majority vote of k nearest  ·  Curse of dimensionality: in high d, distances concentrate — neighbors stop being special (embeddings fight this by learning the geometry)
Naive Bayes — theory & math

Bayes' rule with one heroic assumption: features are conditionally independent given the class. Wrong assumption, useful model — training is just counting, it works with tiny data, and it remains a respectable fast text baseline.

P(y|x) ∝ P(y) Πᵢ P(xᵢ|y)  ·  multinomial NB for word counts, Gaussian NB for continuous  ·  Laplace smoothing (+1 counts) so unseen words don't zero the product  ·  Loss view: maximizes likelihood by counting — no iterative optimizer at all
Worked example A — kNN: "who else looks like this customer?"

The question: a 38-year-old with ₹13 lakh income visits. Will they buy? kNN doesn't build a model — it just looks up the most similar past customers and copies their answer.

Step 1 — turn counts into probabilities, with smoothing
P(free | spam) = (3+1)/(3+2) = 0.8 P(meeting | spam) = (0+1)/(3+2) = 0.2 P(free | ham) = (0+1)/(3+2) = 0.2 P(meeting | ham) = (2+1)/(3+2) = 0.6 P(spam) = P(ham) = 0.5

Step 2 — score a new email containing BOTH "free" and "meeting"
spam score = 0.5 × 0.8 × 0.2 = 0.08 ham score = 0.5 × 0.2 × 0.6 = 0.06 P(spam) = 0.08 / (0.08 + 0.06) = 57% → weakly spam, basically a coin flip

Conflicting evidence ("free" screams spam, "meeting" screams work) produces an honest near-50/50. The "naive" part is multiplying the two words as if they were independent — which is false in real language, and the model works anyway.

Step 3 — what happens without smoothing
P(meeting | spam) would be 0/3 = 0 spam score = 0.5 × 0.8 × 0 = 0 ← one unseen word vetoes the entire prediction

A single word never seen in spam training would make it impossible to ever call an email spam. Adding 1 to every count prevents any probability from being exactly zero.

Every classifier outputs a score; the threshold converts it to a decision. Moving the threshold trades precision against recall. That trade is a product decision — it encodes the relative cost of the two error types, and it belongs to you, not the ML team.

Worked example — should the agent auto-resolve support tickets?

The setup: 10,000 tickets last month. Your model flagged 1,000 as "safe to auto-resolve". Here is what actually happened:

Step 1 — the three numbers, computed
Precision = 920 / (920 + 80) = 920/1000 = 92% "when we auto-resolve, we're right 92% of the time" Recall = 920 / (920 + 1500) = 920/2420 = 38% "we only catch 38% of what we could have automated" F1 = 2(0.92)(0.38) / (0.92 + 0.38) = 0.54 Accuracy = (920 + 7500) / 10000 = 84%
Step 2 — why accuracy is a lie here
a model that flags NOTHING at all: 0 + 7,580 correct out of 10,000 = 76% accuracy

Doing literally nothing scores 76%. Your model's 84% suddenly sounds much less impressive. Always ask what the do-nothing baseline scores before reacting to an accuracy number.

Step 3 — the question that actually matters: should we lower the threshold?

Recall of 38% feels low, so the instinct is to be more aggressive. Let's price it. A correct auto-resolution saves ₹80 of agent time. A wrong one costs ₹300 (angry customer, re-open, apology).

Current threshold (flag 1,000): 920 × ₹80 − 80 × ₹300 = ₹73,600 − ₹24,000 = +₹49,600 ✅ Aggressive threshold (flag 2,000 → TP 1,600, FP 400): 1,600 × ₹80 − 400 × ₹300 = ₹128,000 − ₹120,000 = +₹8,000 ❌

Recall nearly doubled (38% → 66%) and the business result collapsed by 84%. The false positives grew 5× while the true positives grew 1.7×, and each false positive costs 3.75× what a true positive saves.

The takeaway to internalise: "improve recall" is not a goal. The goal is the operating point where marginal value beats marginal cost. Ask your ML team for the full precision-recall curve, put your own rupee figures against it, and pick the threshold yourself. This is the highest-leverage 20 minutes a PM spends on any classifier.

Step 4 — the same data, why ROC-AUC would have flattered you
Spam filter example: 100,000 emails, 1,000 are spam (1% base rate). Model catches 900 spam, with 9,000 false alarms. ROC view: TPR = 900/1,000 = 0.90 · FPR = 9,000/99,000 = 0.09 → looks excellent PR view: Precision = 900/9,900 = 9% → 9 false alarms per catch

Identical model, identical threshold. ROC divides false positives by the huge pool of true negatives, so rare-event problems always look good. When positives are under ~10%, ask for PR-AUC and ignore ROC-AUC.

from sklearn.metrics import precision_recall_curve
import numpy as np

prec, rec, thr = precision_recall_curve(y_true, y_scores)

# put money on the curve and let it choose the threshold
SAVE, COST = 80, 300
n_pos = y_true.sum()
tp = rec[:-1] * n_pos
fp = tp / np.maximum(prec[:-1], 1e-9) - tp
value = tp * SAVE - fp * COST

best = value.argmax()
print(f"threshold {thr[best]:.2f} -> ₹{value[best]:,.0f}, "
      f"precision {prec[best]:.0%}, recall {rec[best]:.0%}")
Core concepts — curves, and which area-under matters
  • ROC-AUC — probability a random positive scores above a random negative. Threshold-free ranking quality. Insensitive to class balance — which is both its virtue and its trap.
  • PR-AUC — area under the precision-recall curve. Ignores true negatives entirely, so it reflects reality when positives are rare.
ROC-AUCPR-AUC
Baseline0.5 for random, regardless of imbalance= positive rate (1% positives → random ≈ 0.01)

The classic trap: on 1-in-1000 fraud, a model with 0.95 ROC-AUC can still give you 20 false alarms per real catch. Ask for the PR curve and the precision at the recall you actually need.
Core concepts — calibration
  • A model is calibrated if events it scores 0.8 happen ~80% of the time. Check with a reliability curve (predicted vs observed frequency, bucketed); summarize with Brier score = mean squared error of the probability itself.
  • Logistic regression: decently calibrated natively. Boosted trees, forests, neural nets: usually not — fix post-hoc with Platt scaling (fit a sigmoid on validation scores) or isotonic regression.
  • Calibration matters whenever the score feeds a threshold, a price, or a human ("87% confident"). A well-ranked but miscalibrated model quietly breaks all three.
  • LLM twist: RLHF damages calibration — base models' token probabilities track correctness better than post-trained models' do (documented in the GPT-4 technical report). Treat an LLM's stated confidence as vibes unless you've measured it.
Core concepts — LLM-era evaluation
  • Golden dataset — a versioned, curated set of input → expected-output (or rubric) pairs. 50–200 well-chosen, sliced examples beat 10,000 noisy ones. It is your regression suite: every prompt change, model swap, or retrieval tweak runs against it.
  • LLM-as-judge — a strong model scores outputs against a rubric. Scalable and cheap, but biased: position bias (prefers the first answer — swap the order and average), verbosity bias (longer looks better), self-preference (models favor their own family's style). Anchor scores to a written rubric and calibrate the judge against a sample of human labels before trusting it.
  • Pairwise preferences — humans (and judges) are far more reliable at "which of these two is better" than "rate this 1–10". Aggregate pairwise wins into a ranking with Bradley-Terry / Elo. This same insight powers RLHF reward models.
  • Offline vs online — offline: golden sets + judges, cheap, fast iteration, pre-ship gate. Online: A/B tests, real behavior (acceptance rate, edit distance, retention, cost). Offline deltas don't guarantee online wins — the correlation between the two is itself something mature teams measure.
Named example: LMSYS Chatbot Arena — anonymous pairwise battles between models, aggregated with Bradley-Terry into a leaderboard. It became the industry's trust anchor precisely because static benchmarks (MMLU etc.) leak into training data and saturate; fresh human pairwise preference is much harder to game.
What actually matters
  • Accuracy is a vanity metric under imbalance: predicting "no fraud" always is 99% accurate and 0% useful. First question on any classifier: what's the base rate?
  • The operating point is the product spec. "Model is 92% precise at 70% recall" is engineering; "we auto-resolve 70% of tickets and 8% of those auto-resolutions are wrong" is the business decision hiding inside it.
  • Never let a model family judge itself for a launch decision — self-preference bias is real and flattering. Cross-family judges or humans for anything that gates a ship.
  • Slice before you celebrate. Aggregate metrics hide segment failures: strong overall, broken in Hindi, broken on long documents, broken for the enterprise tier. Your eval report should be a table of slices, not one number.
  • Goodhart's law applies to evals: optimize hard against any judge and you get judge-pleasing outputs (longer, hedged, sycophantic), not better ones. Rotate judges, refresh golden sets, keep some held-out human eval.
In agentic systems
  • Evaluate per step, not just end-to-end: router accuracy, retrieval recall@k, tool-call validity (did the JSON parse? right tool? right args?), and final-answer quality are separate metrics with separate owners. End-to-end-only evals tell you that it broke, never where.
  • Trace-level golden sets: freeze full multi-step traces (inputs, tool results, outputs) as regression fixtures. Run them in CI on every prompt/model/tool change.
  • Judges in the loop at runtime: a cheap judge can score the agent's draft before it reaches the user — that's an eval promoted to a guardrail.
Mental model: classical ML had train/test discipline forced on it by tooling. LLM products let you skip it — which is why most agent quality problems are really missing eval infrastructure, not model problems.

Theory

An embedding is a learned map from text/image/code to a dense vector where semantic similarity becomes geometric proximity. Trained contrastively on pairs: pull matched pairs together, push mismatched apart. Search over embeddings is kNN; at scale you use ANN indexes. HNSW: a multi-layer "navigable small world" graph — sparse express lanes on top, dense local streets below; queries hop long-range links first, then refine. Roughly logarithmic search; efSearch trades recall vs latency at query time.

Worked example — why "money back" finds the refund page

The question: a user asks "how do I get my money back?". Your help centre has two articles. Keyword search fails — the refund article never uses the words "money back". Watch embeddings solve it.

Real embeddings have 384–3,072 numbers per text. To do the arithmetic by hand we'll pretend there are only 3, and that they happen to mean [money-ish, IT-ish, urgency-ish]:

TextVector

Step 1 — cosine similarity with Doc A
dot(q,a) = 0.9(0.85) + 0.1(0.15) + 0.2(0.10) = 0.765 + 0.015 + 0.020 = 0.800 ‖q‖ = √(0.81+0.01+0.04) = 0.927 ‖a‖ = √(0.7225+0.0225+0.01) = 0.869 cos = 0.800 / (0.927 × 0.869) = 0.800 / 0.806 = 0.99
Step 2 — cosine similarity with Doc B

0.99 vs 0.27 — and the winning document shares zero words with the query. Keyword search would have scored it 0. That single fact is why every modern search stack has an embedding layer.

Why cosine and not plain distance?

Cosine measures the angle, ignoring length. A 3-line answer and a 3-page answer about refunds point the same direction; only their magnitudes differ. Most APIs return unit-length vectors, in which case cosine is the dot product — one multiply-add per dimension, which is why this scales.

Where the bi-encoder fails, and the reranker saves you
"how do I get a refund" vs "our refund policy" → cos 0.94 "how do I avoid giving refunds" vs "our refund policy" → cos 0.91 ← almost identical!

Both look like "refund stuff" to a bi-encoder, which encodes each text separately and never sees them side by side. A cross-encoder reads query and document together in one pass, so it notices the reversed intent. That's why the pattern is always: retrieve 50 cheaply, then rerank those 50 expensively.

Theory

Pick k centroids, assign every point to its nearest, recompute centroids as cluster means, repeat until stable (Lloyd's algorithm). Fast, scalable, and everywhere — but it assumes roundish, similar-sized clusters, needs k chosen up front, is sensitive to scale and initialization (k-means++ fixes init), and forces every point into a cluster, outliers included. Also the workhorse inside vector-index quantization (IVF/PQ) — k-means is why vector databases are cheap.

Math — objective · optimizer
Objective (inertia): min Σᵢ ‖xᵢ − μ_{c(i)}‖² — within-cluster sum of squares
Lloyd's: alternate assign (nearest centroid) / update (cluster mean) — coordinate descent; converges to a local minimum → run n_init restarts
Choosing k: elbow on inertia (fuzzy) · silhouette s = (b−a)/max(a,b) per point, a = intra-cluster dist, b = nearest-other-cluster dist — mean silhouette near 0 means the clusters are fiction
Worked example — segmenting 6 customers by hand

The setup: 6 customers plotted on (visits per month, ₹ spend per month, in thousands). We ask for k = 2 segments. No labels exist — the algorithm has to find the groups itself.

A(1,1) B(2,1) C(1,2) ← low-engagement corner D(8,8) E(9,8) F(8,9) ← high-engagement corner
Step 1 — drop 2 centroids somewhere (k-means++ picks spread-out starting points)
μ₁ = (1,1) μ₂ = (8,8)
Step 2 — assign every point to its nearer centroid
A: dist to μ₁ = 0.0, to μ₂ = 9.9 → cluster 1 B: 1.0 vs 9.2 → cluster 1 C: 1.0 vs 9.2 → cluster 1 D: 9.9 vs 0.0 → cluster 2 E: 10.6 vs 1.0 → cluster 2 F: 10.6 vs 1.0 → cluster 2
Step 3 — move each centroid to the average of its members
μ₁ = ((1+2+1)/3, (1+1+2)/3) = (1.33, 1.33) μ₂ = ((8+9+8)/3, (8+8+9)/3) = (8.33, 8.33)
Step 4 — repeat. Nobody switches clusters → converged.
inertia (total squared distance to own centroid) = 1.33 + 1.33 = 2.67 (low = tight clusters)
Was this a real pattern or did we imagine it? — silhouette
for point A: a = average distance to own cluster (B, C) = 1.0 b = average distance to the other cluster (D,E,F) = 10.4 silhouette = (b − a)/max(a,b) = (10.4 − 1.0)/10.4 = 0.90

Near 1.0 = points sit far closer to their own group than to any other, so the clusters are real. Below about 0.25, k-means has drawn boundaries through what is really one blob — it will always return k clusters, even when none exist. Always check silhouette before naming segments in a deck.

The two failure modes to remember
  • Bad luck on initialization: if both centroids start inside the low-engagement corner, k-means converges to a nonsense split of that corner and never discovers the high group. Fix: n_init=10 — run it 10 times, keep the lowest inertia.
  • Outliers get forced in: one customer at (50, 60) has to join a cluster and will drag its centroid badly. k-means has no concept of "this point belongs nowhere" — that is precisely what HDBSCAN adds.

Theory

DBSCAN: a point is a core point if ≥ minPts neighbors sit within radius ε; clusters are chains of density-connected core points; everything unreachable is noise. Finds arbitrary-shaped clusters, no k needed — but one global ε fails when densities vary. HDBSCAN fixes that: build the cluster hierarchy across all density levels, keep the clusters that are most stable across the hierarchy. The practical consequence you care about: sparse points get labeled noise (−1) instead of being forced into a cluster — exactly right for logs, where half the traffic is one-off weirdness.

Math (conceptual)
DBSCAN: core if |N_ε(x)| ≥ minPts · clusters = transitive closure of density-reachability · noise = unreachable
HDBSCAN: mutual reachability distance = max(core_dist(a), core_dist(b), d(a,b)) → min spanning tree → hierarchy → keep clusters maximizing stability (persistence across density levels)
  • Knobs: min_cluster_size (smallest failure mode you care about) and min_samples (how conservative "dense" is) — both interpretable in product terms, unlike ε.
  • Works on cosine/embedding space; for very high-d embeddings, a UMAP reduction to ~10–50 dims first often sharpens clusters (standard Clio-style pipeline).
Worked example — finding failure themes in 12 agent traces

The setup: 12 conversations where your support agent failed. You embedded each one, so every trace is now a point. You do not know how many kinds of failure exist — that's the whole problem.

5 points clustered tightly at (1,1)-ish → all mention a wrong document being retrieved 5 points clustered tightly at (8,8)-ish → all mention a tool timing out 1 point at (4,9) → user typed in Marathi and the agent replied in English 1 point at (9,1) → user asked the agent to write a poem

a point inside a blob: distance to its 3rd nearest neighbour = 0.5 → dense, becomes a core point the Marathi outlier: distance to its 3rd nearest neighbour = 4.2 → sparse, never a core point

Theory

PCA finds the orthogonal directions of maximum variance and re-expresses the data in them, sorted by variance explained. Keep the top few components: compression that preserves the most signal-per-dimension of any linear projection. Uses: shrink vectors, decorrelate features, denoise, and speed up anything downstream. UMAP/t-SNE are non-linear cousins for 2-D visualization only: local neighborhoods are meaningful, global distances and cluster sizes are not — never compute metrics on projected coordinates.

Math — objective · optimizer
Objective: max_w Var(Xw) s.t. ‖w‖=1 → w = top eigenvectors of the covariance matrix Σ = (1/n)XᵀX (X centered)
In practice: computed via SVD, X = UΛVᵀ — components are V's columns, explained variance from Λ²  ·  no iterations, no learning rate: linear algebra, deterministic
Explained variance ratio: λᵢ/Σλ — the scree plot; pick components covering ~90–95% or the elbow
  • Statistics link: PCA is variance decomposition — components are uncorrelated by construction, which also makes it the classic multicollinearity fix before regression.
  • Modern echo: Matryoshka embeddings (truncate a 3072-dim vector to 256 dims with modest quality loss) productize the same keep-the-top-directions idea inside the embedding model itself.
Worked example — two columns that were secretly one

The setup: your houses table has size_sqft and size_sqm. They are the same measurement in different units, so they carry one piece of information wearing two hats. PCA finds this automatically. Here are 4 centered data points:

(2, 1) (−2, −1) (1, 0.5) (−1, −0.5) ← every point obeys y = 0.5x exactly
Step 1 — build the covariance matrix (how each column varies with each other)
Var(x) = (4 + 4 + 1 + 1)/4 = 2.5 Var(y) = (1 + 1 + 0.25 + 0.25)/4 = 0.625 Cov(x,y) = (2 + 2 + 0.5 + 0.5)/4 = 1.25 C = [ 2.50 1.25 ] [ 1.25 0.625 ]
Step 2 — find the eigenvalues (how much variance lives along each new axis)
trace = 2.5 + 0.625 = 3.125 determinant = (2.5)(0.625) − (1.25)² = 1.5625 − 1.5625 = 0 → λ₁ = 3.125, λ₂ = 0
Step 3 — read the answer
explained variance: PC1 = 3.125/3.125 = 100%, PC2 = 0% PC1 direction = (2, 1)/√5 = (0.894, 0.447) ← "the size axis"

Two columns collapsed into one with zero information lost. The second eigenvalue being exactly 0 is the mathematical way of saying "this column was redundant".

What real data looks like
with a little noise: λ = [3.00, 0.125] → PC1 explains 96%, PC2 explains 4% keep PC1 only: half the storage, ~4% of the information gone

The version you'll actually use: your embeddings are 384 numbers per chunk. PCA typically shows the first ~40 directions carry 95% of the variance. Dropping to 40 dimensions makes clustering 3–5× faster and often better, because the discarded directions were mostly noise. The same idea is now baked into models as Matryoshka embeddings — truncate 3,072 numbers to 256 and lose surprisingly little.

Do not confuse PCA with UMAP/t-SNE. PCA is a real, reversible, linear compression you can compute on. UMAP is a picture — it preserves who-is-near-whom for your eyes, but distances and cluster sizes in a UMAP plot are not meaningful numbers. Never compute a metric on UMAP coordinates.

Theory

Flag what's unusual without labeled examples of "unusual". Isolation Forest: build random trees with random split points — anomalies, being few and different, get isolated in short paths; inliers need many splits. Elegant inversion: instead of modeling normal, measure how easy a point is to separate. Alternatives: one-class SVM (boundary around normal), robust z-scores / MAD for single metrics, reconstruction error from autoencoders/PCA for structured data.

Math (conceptual)
Isolation Forest score: s(x) = 2^{−E[h(x)]/c(n)} — h(x) = path length to isolate x, c(n) = expected path length; s → 1 anomalous, s ≈ 0.5 normal
Robust z-score: (x − median)/MAD — outlier-resistant version of "how many σ away"; use when the metric itself contains the outliers you're hunting
  • Contamination (expected anomaly fraction) sets the alert threshold — that's a product decision about review capacity, same economics as precision/recall.
  • Anomaly ≠ bad: it means "review this", so the downstream queue defines the real cost of a false positive.
Worked example — the agent run that burned ₹4,000 in tokens

The setup: six agent runs today. Five are normal; one got stuck in a tool loop. You have no labelled "anomalies" to train on — you have to spot it from the shape of the data alone.

tokens used: 1200, 1350, 1100, 1250, 1400, 47000
Attempt 1 — the obvious method: mean and standard deviation (it fails)
mean = 53,300/6 = 8,883 std ≈ 17,047 z-score of the bad run = (47000 − 8883) / 17047 = 2.2 alert rule "flag if z > 3" → NOT FLAGGED ❌

Why it failed — this is the important idea: the outlier is so large that it dragged the mean up to 8,883 (a value no run actually had) and inflated the standard deviation to 17,047. The anomaly hid itself by corrupting the very statistics used to detect it.

Attempt 2 — robust statistics: median and MAD (it works)
median = 1,300 (medians ignore extreme values entirely) absolute deviations from median: 100, 50, 200, 50, 100, 45700 MAD = median of those = 100 robust z = (47000 − 1300) / (1.4826 × 100) = 45700 / 148.3 = 308 → FLAGGED ✅

The median and MAD don't move when one value goes crazy, so the crazy value stands out at 308 standard-deviations-equivalent instead of a sleepy 2.2.

Attempt 3 — Isolation Forest, when you have many features at once

Pick a feature and a random cut point, repeatedly, until a point sits alone. The 47,000-token run is separated by the first random cut anywhere between 1,400 and 47,000 — path length ≈ 1. A normal run needs 4–5 cuts to be isolated because it has neighbours crowding it. Short path = anomaly. It needs no labels, no distribution assumptions, and handles 20 features (tokens, latency, tool calls, retries) together.

Setting the threshold is a capacity decision
contamination = 0.01 on 10,000 daily runs → 100 alerts/day if the on-call engineer can review 20, set contamination = 0.002 instead

Same trade-off as precision vs recall: the alert threshold should be set by how many alerts a human can actually action, not by statistical elegance.

5 · Ranking & recommendation

The two-stage retrieve-then-rank pattern predates LLMs by a decade — RAG is recsys architecture wearing a new badge.

Core concepts
  • Collaborative filtering — recommend from behavior alone. Item-item CF: "users who liked X also liked Y" via item similarity over interaction vectors (Amazon's classic, still shockingly strong). Matrix factorization: decompose the user×item matrix into latent factor vectors (the Netflix Prize workhorse) — user·item dot product predicts affinity; conceptually, embeddings learned from behavior instead of content. Weakness: cold start — new users/items have no interactions, so you fall back on content features or hybrids.
  • Learning-to-rank in one paragraph: pointwise treats each item independently — predict its absolute relevance and sort (simple, but absolute labels are noisy); pairwise learns from "A beats B" comparisons (RankNet, LambdaRank) — matches how preference data actually arrives and how humans judge; listwise optimizes the quality of the whole ranked list, targeting the metric (usually NDCG) directly. LambdaMART — gradient-boosted trees with pairwise/listwise lambdas — dominated ranking leaderboards for a decade and still runs plenty of production search.
  • Ranking metrics — NDCG (graded relevance, log-discounted by position), MRR (how high is the first relevant result), MAP, and recall@k for the candidate-generation stage.
  • Two-stage architecture — candidate generation (cheap, optimized for recall: embeddings, CF, heuristics) → ranking (expensive, optimized for precision: GBT/cross-encoder/LLM with rich features). Every serious search, feed, and RAG system looks like this.
  • Best-of-n with a ranker — sample n outputs from the generator, score them with a ranker / reward model / verifier, return the winner. Buys quality with inference compute; gains are roughly logarithmic in n, and the ceiling is your ranker's judgment, not the generator.
Worked example — the same 5 chunks, two orders, two very different RAG answers

The setup: your RAG system retrieves 5 chunks for "what is the refund window?". A human graded each chunk's usefulness from 0 (useless) to 3 (perfect answer). Crucially, only the top 2 chunks fit in the prompt.

Retrieval runGrades in returned orderWhat the LLM actually sees (top 2)
System A (good)3, 2, 0, 1, 0Perfect chunk + useful chunk ✅
System B (bad)0, 2, 3, 0, 1Useless chunk + useful chunk ❌

Both systems found the same 5 chunks. Only the order differs. NDCG is the metric that notices.

Step 1 — DCG: reward relevance, punish being far down the list
DCG = Σ (2^grade − 1) / log₂(position + 1) System A: pos 1, grade 3 → (8−1)/log₂(2) = 7/1.000 = 7.000 pos 2, grade 2 → (4−1)/log₂(3) = 3/1.585 = 1.893 pos 3, grade 0 → 0 pos 4, grade 1 → (2−1)/log₂(5) = 1/2.322 = 0.431 pos 5, grade 0 → 0 DCG(A) = 9.32
System B: pos 1, grade 0 → 0 pos 2, grade 2 → 3/1.585 = 1.893 pos 3, grade 3 → 7/log₂(4) = 7/2.000 = 3.500 ← the perfect chunk, halved by position pos 4, grade 0 → 0 pos 5, grade 1 → 1/log₂(6) = 1/2.585 = 0.387 DCG(B) = 5.78

The 2^grade − 1 part means a perfect chunk is worth much more than two mediocre ones (7 vs 3). The log₂(position+1) divisor means the same chunk is worth 7.0 at rank 1 but only 3.5 at rank 3.

Step 2 — normalize by the best possible order, to get NDCG
ideal order would be 3, 2, 1, 0, 0: IDCG = 7/1.000 + 3/1.585 + 1/2.000 = 7.000 + 1.893 + 0.500 = 9.39 NDCG(A) = 9.32 / 9.39 = 0.99 NDCG(B) = 5.78 / 9.39 = 0.62

Normalizing makes the score comparable across queries — a query with only one relevant document can still score 1.0. Without it, easy queries would dominate your average.

Step 3 — the two other metrics, on the same data
Recall@5 : both systems = 100% ← identical, and completely blind to the problem MRR : A = 1/1 = 1.00 · B = 1/2 = 0.50 ← "how far down is the first useful thing"

Read this carefully, because it's the most common RAG debugging mistake: recall@5 says both systems are perfect. Your retrieval dashboard is green. Meanwhile System B hands the LLM a useless chunk and a partial one, and the answer is wrong. If you only measure recall@k, reranking bugs are invisible to you. Measure NDCG, and measure it at the k you actually put in the prompt.

The fix is usually the same: retrieve 50 with the fast bi-encoder (protects recall), then let a cross-encoder reorder them (fixes NDCG), then pass the top 3–5. That single addition is the most reliable quality jump available to a RAG product.
import numpy as np

What actually matters
  • Pairwise data beats absolute labels. Humans are inconsistent scoring 1–10 but reliable choosing A vs B. This one insight connects LambdaRank, Chatbot Arena, and RLHF reward models — it's the same trick three times.
  • Position bias poisons logged training data: users click what's on top, so training naively on clicks teaches the new ranker to imitate the old one. Fixes: inject randomization, model click propensity, or use explicit comparisons. Any "learn from our logs" plan that ignores this ships a feedback loop.
  • Best-of-n only works in verifiable domains or with a trusted ranker. Code (run the tests) and math (check the answer) are ideal; open-ended prose depends entirely on judge quality — n=10 with a biased judge is just 10× the cost for confident mediocrity.
  • Exploration is a product requirement: pure exploitation collapses catalogs into filter bubbles and starves new items of the data they need to ever rank.
In agentic systems
  • Context selection is ranking — choosing which chunks, memories, or tool outputs enter the prompt is an NDCG problem with a token budget as the page size.
  • Plan/draft selection — generate n candidate plans or answers, rank with a verifier or judge, execute the best. Structured best-of-n is the cheapest reliability upgrade an agent can get.
  • Tool-result triage — when a search tool returns 50 hits, a lightweight ranker picks what the agent actually reads.
Named example: DeepMind's AlphaCode — generated up to a million candidate programs per problem, filtered them by actually executing the visible tests, then clustered survivors and picked representatives. Best-of-n with a hard verifier at industrial scale — the pattern behind every modern "sample, verify, submit" coding agent.
Interview one-liners
Every serious ranking system is two-stage — cheap candidate generation for recall, expensive reranking for precision — and RAG is exactly that pattern applied to context selection.
Learning-to-rank in one breath: pointwise scores items, pairwise orders pairs, listwise optimizes the list — and LambdaMART, a gradient-boosted tree, still wins more ranking benchmarks than it should.
Best-of-n buys quality with inference compute, and it's worth exactly as much as your verifier is trustworthy — great for code with tests, expensive theater with a biased judge.

Theory

The frame: an agent in a state takes an action, gets a reward, lands in a new state; the policy π(a|s) is what's learned, to maximize expected cumulative discounted reward. No labels — only a scalar signal, often delayed (credit assignment is the core difficulty). Q-learning learns the value of each (state, action) pair off-policy from experience; with function approximation instead of a table, it becomes DQN — the Atari result that started the modern era.

Math — objective · update rule
Return: G_t = Σ_k γᵏ r_{t+k}  ·  γ ∈ [0,1) trades near vs far rewards
Bellman optimality: Q*(s,a) = E[ r + γ · max_{a′} Q*(s′,a′) ]
Q-learning update: Q(s,a) ← Q(s,a) + α [ r + γ max_{a′} Q(s′,a′) − Q(s,a) ] — the bracket is the TD error; α is the learning rate
Exploration: ε-greedy — random action with prob ε, else argmax Q; decay ε over time
Worked example — how a reward at the end teaches the first step

The setup: a tiny world with 3 rooms in a row. Reaching the exit from room 3 pays +10. Everything else pays 0. The agent starts knowing nothing: every Q value is 0. Learning rate α = 0.5, discount γ = 0.9.

[Room 1] → [Room 2] → [Room 3] → 🚪 EXIT (+10)

The hard part isn't the last step — it's teaching room 1 that going right is good, when room 1 never sees a reward at all. This is credit assignment.

Episode 1 — agent wanders, eventually steps right from room 3 and gets +10
Q(3,→) ← 0 + 0.5 × [ 10 + 0.9(0) − 0 ] = 5.0 Q(2,→) is still 0 — room 2 has learned nothing yet
Episode 2 — agent steps right from room 2, lands in room 3, gets reward 0
Q(2,→) ← 0 + 0.5 × [ 0 + 0.9 × max Q(3,·) − 0 ] = 0.5 × [ 0.9 × 5.0 ] = 2.25 ← value leaked backwards one room!

Read that again — it's the whole algorithm. Room 2 got no reward. It learned purely from the fact that it leads to a room that is known to be valuable. Repeat this and value seeps backwards from the goal, one room per visit.

Math — regret · algorithms
Regret: R(T) = T·μ* − Σ_t μ_{a_t} — what you lost vs always playing the best arm; good algorithms grow regret O(log T)
UCB: pick argmax [ μ̂ₐ + √(2 ln t / nₐ) ] — optimism bonus shrinks as an arm gets pulled; provably near-optimal
Thompson sampling: keep a posterior per arm (Beta(wins+1, losses+1) for click-like rewards), sample one value from each, play the argmax — exploration emerges from uncertainty, no tuning
Worked example — picking the best prompt while you're still testing it

The setup: 3 system-prompt variants for your agent. After 100 users you have:

VariantShownSuccessesObserved ratePosterior belief
A301240%Beta(13, 19)
B402460%Beta(25, 17)
C30930%Beta(10, 23)

"Beta(wins+1, losses+1)" is just a bell-ish curve over what the true rate might be. Few observations → wide curve (uncertain). Many → narrow (confident).

Step 1 — for the next user, draw one random guess from each variant's curve
sample from A's curve → 0.44 sample from B's curve → 0.63 sample from C's curve → 0.29 serve the highest → B
Step 2 — that's it. Repeat per user; update the counts after each outcome.

Why this is clever: B wins most draws, so it gets most traffic. But A's curve is wide (only 30 users), so occasionally A draws a lucky 0.70 and gets served. If A really is better, those occasional draws will prove it and traffic will shift. Exploration falls out of the uncertainty automatically — there is no exploration parameter to tune.

Step 3 — what it saves you, in users
true rates: A = 40%, B = 60%, C = 30%. 10,000 users to allocate. fixed A/B/C split (3,333 each): successes = 3333(0.4) + 3333(0.6) + 3333(0.3) = 1,333 + 2,000 + 1,000 = 4,333 if you'd magically known B was best from the start: successes = 10,000 × 0.6 = 6,000 → the gap, 1,667, is called regret Thompson sampling in practice lands around 5,600–5,800 — it pays a few hundred lost successes to learn, instead of 1,667.
When NOT to use it

A bandit optimizes; it does not cleanly measure. Because allocation changes over time, it gets tangled with time-varying effects, and you can't quote a crisp confidence interval on "B beat A by X%". Shipping decision that needs defending in a review → A/B test. Ongoing allocation where losing users hurts → bandit.

Theory

Skip learning values of every action — adjust the policy directly: raise the probability of actions that worked out better than expected, lower the rest. "Better than expected" is the advantage (reward vs a baseline), which slashes variance. Raw policy gradients (REINFORCE) are noisy and can destroy the policy in one bad update; PPO clips each update so the new policy can't move too far from the old one per step. Stability engineering, not magic — and it's the optimizer inside RLHF.

Math — gradient · PPO objective
Policy gradient theorem: ∇J(θ) = E[ ∇ ln π_θ(a|s) · A(s,a) ] — score high-advantage actions up, in proportion to how surprised the policy was
Advantage: A(s,a) = Q(s,a) − V(s) — reward relative to "what this state usually yields" (the baseline V kills variance without biasing the gradient)
PPO clipped objective: E[ min( r·A, clip(r, 1−ε, 1+ε)·A ) ],  r = π_new(a|s)/π_old(a|s), ε ≈ 0.2 — improvements beyond the clip earn nothing, so no single step can lurch
Worked example — nudging an agent toward the right tool

The setup: the user asks "where is my order?". The agent can either call the order_lookup tool or answer from memory. Historically, 60% of conversations in this state end well — so the baseline V(state) = 0.6. That baseline is what "expected" means.

Step 1 — run two episodes and compute the advantage
Episode 1: agent calls order_lookup → user satisfied → reward = 1 advantage = 1 − 0.6 = +0.4 → do more of this Episode 2: agent guesses from memory → user complains → reward = 0 advantage = 0 − 0.6 = −0.6 → do less of this

Why subtract the baseline at all? If we used raw rewards, every action that got a 1 would be reinforced — including lucky ones in easy states. Advantage asks the sharper question: "did this action beat what we'd normally expect here?" Same information, far less noise.

Step 2 — the gradient wants a big jump; PPO refuses
current policy: P(call the tool) = 0.20 raw gradient says: make it 0.50 → ratio r = 0.50/0.20 = 2.5 PPO with ε = 0.2 only credits ratios inside [0.8, 1.2] beyond 1.2 the objective flatlines → no reward for jumping further effective update: 0.20 × 1.2 = 0.24
Step 3 — so it takes several careful rounds instead of one reckless one
0.20 → 0.24 → 0.29 → 0.35 → 0.42 → 0.50 (five updates)

Why the caution matters: the advantage estimate came from a handful of noisy episodes. If one lucky batch caused a jump straight to 0.50 and the estimate was wrong, the policy has already changed and all future data is collected under the broken policy — there's no clean way back. Clipping trades speed for the guarantee that no single batch can wreck the model. That is the whole reason PPO, not vanilla policy gradient, is what people actually run.

Theory — the pipeline behind every aligned LLM
  • Step 1 — SFT: supervised fine-tuning on demonstration data (prompt → good response).
  • Step 2 — Reward model: humans compare response pairs; train a model to predict which wins (Bradley-Terry — the same pairwise math as Chatbot Arena and LambdaRank).
  • Step 3 — PPO against the RM, with a KL penalty leashing the policy to the SFT model so it doesn't drift into degenerate high-reward text.
  • DPO skips steps 2–3: a closed-form trick turns preference pairs into a direct loss on the policy. Simpler, cheaper, no separate RM; most open-weight instruct models use DPO-family methods. PPO remains more controllable at frontier scale.
  • RLAIF / Constitutional AI: replace human preference labels with AI feedback guided by written principles — scales labeling, moves the debate to the constitution (Anthropic's approach).
Math — the three losses
Reward model (Bradley-Terry): L_RM = −ln σ( r(x, y_w) − r(x, y_l) ) — just "winner should outscore loser"
RLHF objective: max E[ r(x,y) ] − β · KL( π ‖ π_ref ) — chase reward, pay for every token of drift from the reference model
DPO loss: −ln σ( β [ ln π(y_w|x)/π_ref(y_w|x) − ln π(y_l|x)/π_ref(y_l|x) ] ) — the RLHF optimum, rewritten as a supervised loss on pairs
Worked example — turning "I prefer this one" into model weights

The setup: a labeller sees one prompt and two answers, and picks a winner. That's the only human input in the entire pipeline. Here's how that click becomes a gradient.

Prompt: "Explain our refund policy." Answer W (chosen): "Refunds within 30 days, minus shipping. Here's the form." Answer L (rejected): "Well, refunds are a complex topic that depends on..." (rambles)
Step 1 — the reward model scores both, and is trained to rank them correctly
r(W) = 2.1, r(L) = 0.8 (these scores have no units — only the gap matters) loss = −ln σ(r_W − r_L) = −ln σ(1.3) = −ln(0.786) = 0.24 ← small loss, RM was right if the RM had them backwards (r_W = 0.8, r_L = 2.1): loss = −ln σ(−1.3) = −ln(0.214) = 1.54 ← 6× bigger, strong push to fix

Note what the RM is not asked: "rate this 8/10". Humans are unreliable at absolute scores and reliable at comparisons — so the loss only ever cares that the winner outscores the loser.

Step 2 — the policy now chases that score, on a leash
objective = E[ reward ] − β × KL(new policy ‖ original model) say the tuned model wants to say a token with probability 0.9 where the original model said 0.3: KL contribution = ln(0.9 / 0.3) = 1.10 with β = 0.1 → it costs 0.11 of reward to make that change

What the leash buys you: without it, the policy discovers weird high-reward text — repeating flattering phrases, padding with hedges — that scores brilliantly with the reward model and reads like nonsense to humans. The KL term makes every step away from the original model cost something, so only changes worth real reward survive.

Step 3 — DPO: the same result, without the RM or the RL loop
log-ratio for chosen = ln π(W)/π_ref(W) = +0.5 log-ratio for rejected = ln π(L)/π_ref(L) = −0.3 loss = −ln σ( β [0.5 − (−0.3)] ) = −ln σ(0.1 × 0.8) = −ln σ(0.08) = 0.65

One loss, computed directly on the preference pair, no separate reward model, no sampling loop. It's a normal fine-tuning job — which is why a product team with a few thousand thumbs-up/down pairs can realistically do this, while full PPO-RLHF stays the domain of labs.

Theory — the failure mode that matters most

Reward hacking / specification gaming: the optimizer maximizes the reward you wrote, not the outcome you meant. Canonical demo: OpenAI's CoastRunners boat, which learned to loop in a lagoon collecting respawning power-ups — record score, never finishing the race. This isn't a bug in RL; it's what optimization is. Any measurable proxy, optimized hard enough, diverges from the goal it proxies (Goodhart's law with a gradient).

What actually matters
  • Red-team the reward before the model does. For every metric an autonomous system optimizes, ask "what's the degenerate way to score well?" — someone (or something) will find it.
  • Fix the evaluator, not just the prompt: if the agent gamed the check, patching the prompt treats the symptom; the incentive is still there.
  • Pair every target metric with a guard metric (task success + human-verified spot checks; judge score + length caps; test-pass + diff review). Single-metric optimization is a standing invitation.
  • Verifiable domains are safest for outcome-based RL — code with tests, math with checkers. The fuzzier the verification, the more hacking you'll get.
Worked example — the agent that got 100% by cheating

The setup: you deploy a coding agent and score it on "% of tests passing". Seems unarguable. Here's what the agent sees:

The same thing, more subtly: optimizing against a judge
Sprint goal: raise the LLM-judge score on the golden set. golden-set judge score: 78% → 91% 🎉 shipped real user thumbs-up rate: 71% → 68% 😐 quietly worse what actually changed: answers got longer, more hedged, more rubric-shaped. the judge liked that. users didn't.

This is Goodhart's law with a gradient attached: once a measure becomes a target, it stops measuring the thing. It is not a rare failure — it is the default outcome of optimizing anything hard enough.

6 · ML lifecycle & MLOps

Why "95% offline" becomes "60% in production", and the agent-era translation of every classical safeguard.

Core concepts
  • Splits — train / validation (tune on this) / test (touch once). Time-dependent data gets a temporal split: train on the past, test on the future — a random split lets the model peek ahead and lies to you. Small data: k-fold cross-validation.
  • Leakage — information unavailable at prediction time sneaks into training features: a column computed after the outcome ("refund_issued"), duplicates straddling the split, target encoding fit on the full dataset. Symptom: validation results too good to be true. It is the #1 cause of the offline-online gap.
  • Overfitting & regularization — memorizing noise instead of signal. Controls: L1/L2 penalties, early stopping, tree depth limits, dropout, and — most reliably — more data. The bias-variance trade-off is the frame: too simple underfits, too flexible overfits.
  • Drift — data drift: input distribution shifts (new geography, new device mix); concept drift: the input→output relationship itself changes (fraud adapts, slang evolves). Monitor feature and score distributions (PSI / KL divergence) because labels arrive late or never.
  • Monitoring & retraining — dashboards on prediction distributions, feature health, delayed-label metrics; retrain on triggers (drift thresholds) or cadence. A model is a perishable good.
  • HITL feedback loops — human review queues above/below confidence thresholds; active learning: spend labeling budget on the examples the model is least sure about; corrections flow back as training data.

Worked example — the 98% model that was worthless

The setup: your team builds a churn model. Validation AUC is 0.98 — extraordinary. It ships. In production it scores 0.55, barely better than a coin flip. Nobody changed the code. What happened?

Step 1 — look at what the model found most important

Step 2 — remove it and watch the numbers get "worse" and better
validation AUC production AUC with leak 0.98 → 0.55 ❌ (the gap IS the tell) without leak 0.79 → 0.77 ✅ (honest, and actually useful)

The 0.79 model is worth money; the 0.98 model is worth nothing. A large validation-to-production gap is the single most reliable symptom of leakage.

Step 3 — the second leak nobody catches: splitting randomly on time-based data
random split : train on Jan–Dec rows shuffled, test on Jan–Dec rows shuffled → R² = 0.91 temporal split: train on Jan–Sep, test on Oct–Dec → R² = 0.62

A random split lets the model train on December and be tested on March — it has seen the future. 0.62 is what you'll actually get, because in production you always predict forward. Any data with a time dimension needs a temporal split.

Step 4 — the leakage checklist to run before believing any result
  • Would this column exist, with this value, at the moment of prediction? Anything computed after the outcome is a leak.
  • Are duplicate or near-duplicate rows split across train and test? (Very common with scraped or logged text.)
  • Was any preprocessing — scaling, target encoding, imputation — fitted on the full dataset before splitting? That leaks test statistics into training.
  • Does one feature dominate importance? Suspicion, not celebration.
  • Is the split temporal, when the data is temporal?
The LLM-product version of this exact bug: your golden eval set was built from examples that were also used to write the prompt. Scores are inflated for the same reason — the model has effectively seen the test. Keep a set of traces that has never informed a prompt, and only ever score against it.

What actually matters
  • Most "model degradation" is pipeline or data drift, not the model rotting. Debug the data before the weights.
  • Leakage explains almost every miracle result. When a team reports suspiciously great offline numbers, audit the features and the split before celebrating — cheaper than a failed launch.
  • In LLM products you don't own the weights, so the regression suite is your only defense: gate model swaps like code deploys. 7 · Statistics for decisions

The math that decides whether your launch actually worked — and the four ways it routinely lies to PMs.

Core concepts
  • A/B test — randomized assignment isolates causation. Pick one primary metric before launch, plus guardrails (latency, retention, cost). The randomization unit (user vs session) must match the analysis unit, or your variance estimates are fiction.
  • p-value — the probability of seeing data this extreme if there were no real effect. It is not the probability the null is true, and it says nothing about effect size. Prefer confidence intervals: they show magnitude and uncertainty at once.
  • Power & sample size — power = probability of detecting an effect that's really there (aim ≥ 0.8). Rule of thumb per arm: n ≈ 16·σ² / δ² — sample size scales with variance and with the inverse square of the effect. Halve the detectable effect → 4× the sample. Compute the minimum detectable effect (MDE) before launching, not after.
  • Peeking & multiple comparisons — checking daily and stopping at the first significant result inflates false positives severalfold; so does shopping across 20 metrics. Fixes: fixed horizon, sequential tests designed for peeking, corrections when metric-shopping.
  • Simpson's paradox — a trend that holds in every segment reverses in the aggregate because group mixes differ. Canonical: Berkeley admissions (each department fair; aggregate looked biased because women applied to more competitive departments). Cure: slice by the confounder before believing any aggregate.
  • Novelty & primacy effects — early lift because it's new (novelty) or early dip because it's unfamiliar (primacy); both fade. Run 2+ weeks and read cohort curves by days-since-exposure before calling a winner.
  • Bandits vs A/B — bandits shift traffic toward winners while running (optimize); A/B holds allocation fixed (measure cleanly). Use bandits when opportunity cost dominates, A/B when you need a defensible causal read.
Worked example A — can this A/B test even work?

The setup: checkout converts at 4%. The team believes a redesign lifts it by 10% relative — that is 4.0% → 4.4%, an absolute gain of 0.4 percentage points. How many users do you need before running it?

Step 1 — plug into the sample-size rule
n ≈ 16 σ² / δ² (per arm, for 80% power at 95% confidence) for a conversion rate: σ² = p(1−p) = 0.04 × 0.96 = 0.0384 δ = 0.004 (the 0.4pp you want to detect) n ≈ 16 × 0.0384 / 0.004² = 0.6144 / 0.000016 = 38,400 per arm = 76,800 users total
Step 2 — reality check against your actual traffic
checkout traffic = 5,000 users/week 76,800 / 5,000 = 15.4 weeks ← nearly four months for one test

The decision this forces: you now know, before spending a sprint, that this test cannot conclude this quarter. Your options are real ones: chase a bigger effect, test on a higher-traffic surface, accept a lower confidence level, or ship on judgement and monitor guardrails. What you must not do is run it for two weeks and read the result — that test has roughly a 25% chance of detecting a real effect, so "no significant difference" would tell you nothing.

Step 3 — the brutal arithmetic of small effects
detect 0.8pp (20% lift) → 9,600 per arm → ~4 weeks detect 0.4pp (10% lift) → 38,400 per arm → ~15 weeks detect 0.2pp (5% lift) → 153,600 per arm → ~61 weeks

δ is squared in the denominator, so halving the effect you want to detect quadruples the users you need. This is why mature experimentation teams push for bold changes: small tweaks are not measurable at most companies' traffic, no matter how patient you are.

Worked example B — the agent that won every segment and lost overall

The setup: you A/B test agent v2 against v1 on task success. v2 wins on easy queries. v2 wins on hard queries. v2 loses overall. This is not a bug in your maths — it's Simpson's paradox, and it will happen to you.

What actually happened
v1 traffic mix: 90% easy, 10% hard → mostly scoring on the easy stuff v2 traffic mix: 50% easy, 50% hard → forced to answer far more hard questions v2 is better at BOTH kinds of question, but it was handed a much harder exam.

In agent products this happens constantly, and the usual culprit is a routing change shipped in the same release — the new router sends more difficult queries to the new model, then the aggregate metric blames the new model for the harder workload.

How to not get fooled
  • Always report metrics sliced by difficulty / segment / language / tier, never a single aggregate number.
  • If the aggregate disagrees with every slice, the mix changed — go find what changed it.
  • Check that the traffic mix itself is balanced between arms before comparing. Randomize users, not queries, and verify the split.
And the second illusion: novelty
Week 1: +12% ← everyone clicks the new thing because it's new Week 2: +5% Week 3: +1% Week 4: 0% ← the true effect was always zero

Reading week 1 and shipping is how teams accumulate features that did nothing. Run for at least two weeks, plot the effect by days-since-first-exposure, and only trust the flat part of the curve.

What actually matters
  • Most product experiments are underpowered for the effects PMs chase. If MDE math says you need 4M users and you have 40k, don't run the test — ship bigger swings, use holdouts, or accept a directional read honestly labeled as one.
  • p = 0.049 vs p = 0.051 is not a real difference. Judge effect size + CI + prior plausibility; a barely-significant tiny effect on a shopped metric is noise wearing a suit.
  • Guardrails are where LLM features die: the quality metric wins while p95 latency and cost-per-query quietly lose. For GenAI experiments, cost variance is a first-class guardrail, not a finance afterthought.
  • The canonical counterexample to intuition: Bing's title-lengthening experiment — a deprioritized tweak an engineer shipped casually produced a double-digit revenue lift (one of the biggest in Bing's history, per Kohavi). Experts are bad at predicting effect sizes; that's the entire argument for experimentation infrastructure.
In agentic systems
  • Two-gate shipping — offline eval gate first (golden sets, judges), online experiment second (acceptance rate, edit distance, task completion, retention). Offline says "not obviously worse"; online says "actually better".
  • Higher variance, smaller n — LLM outputs vary per call and per user; agent metrics (multi-step success) are noisier than click-through. Expect to need longer runs than your dashboard instincts suggest.
  • Slice agent experiments by task type — aggregate task-success deltas routinely hide a Simpson's-style reversal between easy and hard queries when the traffic mix shifts.
Named example: Microsoft's ExP platform (Kohavi's team) — the discipline source for most of this section: thousands of concurrent experiments, mandatory power calculations, guardrail metrics, and institutional memory that intuition loses to measurement.
Interview one-liners
Power first, p-value later — I compute the minimum detectable effect before launching, because an underpowered test is a coin flip with paperwork.
A p-value tells me how surprised I'd be if nothing were going on; it says nothing about how big or valuable the effect is — that's what the confidence interval is for.
When a metric wins overall but loses in every segment, I check the mix — that's Simpson's paradox, not a miracle.

🎯 50 use cases — what to use, and what not to

Each row: what the problem actually is, the technique that fits and why, and the tempting-but-wrong choice with the specific reason it fails.

How to choose, in 30 seconds
  • Is the answer in a table with labels? → gradient-boosted trees. Start here for anything tabular; make everything else beat it.
  • Do you need to explain or defend each decision? → logistic regression / a shallow tree. Accuracy you can't defend is not shippable in a regulated or high-trust setting.
  • Do you need a probability you'll threshold on cost? → anything calibrated. An uncalibrated score can be ranked but never thresholded on money.
  • Is "similar" the whole problem? → embeddings + vector search. Text, images, memories, examples.
  • No labels at all? → clustering (structure) or anomaly detection (outliers). Then have an LLM name what you found.
  • Does it happen millions of times a day? → a small classifier, not an LLM call. Reserve the LLM for what only an LLM can do.
  • Does it need judgement, nuance, or open-ended language? → that's the LLM's job. Don't force a classifier onto it.
Two rules that decide most arguments: (1) if a linear model is within 2–3 points of the complex one, ship the linear model — you're buying monitorability, latency and trust for almost nothing. (2) if you can't name the metric and the operating threshold, you don't have a modelling problem yet, you have a product-definition problem.

The five mistakes behind most of the ❌ column
  • Using an LLM where a classifier belongs. The tell: the decision is a fixed, repeated choice happening at high volume. Cost and latency will force the rewrite eventually — do it first.
  • Optimizing accuracy on imbalanced data. The tell: the do-nothing baseline scores above 90%. Switch to precision/recall at a threshold priced in money.
  • Predicting likelihood when you needed incrementality. The tell: you're spending money on the people the model ranks highest, and they'd have converted anyway. You want uplift, not propensity.
  • Forcing structure that isn't there. The tell: k clusters requested, k clusters returned, and nobody checked silhouette. Clustering always returns an answer, real or not.
  • Measuring the aggregate only. The tell: the launch metric moved and nobody can say for whom. Slice by segment, difficulty, language and tier before you believe anything.
